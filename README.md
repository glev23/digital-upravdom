# Цифровой Управдом

Чат-бот (+ опциональное мини-приложение) для платформы MAX, который помогает
жителям МКД быстро понять, куда обращаться при аварии, узнать статус заявки и
получать уведомления об отключениях. Трек «Умный город» (Минобрнауки России).

**Статус:** 🟢 идея, архитектура и контракт MAX Bot API зафиксированы;
каркас, модель данных и транспорт MAX (приём/отправка сообщений) —
реализованы и проверены, включая живой диалог в MAX. Полный срез —
[progress_dev.md](./documentation/progress_dev.md).

## Чем отличается от существующих сервисов

ГИС ЖКХ, «Госуслуги Дом» и приложения УК отвечают на вопрос **«как подать
заявку»** — это форма, в которой житель сам выбирает категорию и адресата.
Ни один из них не отвечает на вопрос **«кому»**, хотя именно отсутствие этого
знания и является проблемой: 37% жителей МКД не знают даже свою управляющую
компанию (ВЦИОМ, 02.07.2025).

«Цифровой Управдом» забирает это решение на себя: житель описывает проблему
своими словами, а бот определяет зону ответственности (УК / РСО / собственник
/ муниципалитет) и показывает норму, по которой граница проходит именно так.
Второе отличие — следствие первого: массовые обращения об одной аварии
схлопываются в одну заявку с несколькими подписчиками.

Подробное сравнение — [шаг 3.5 в idea_and_scope.md](./documentation/idea_and_scope.md).

## Основной пользовательский сценарий

1. Житель сканирует QR-код со стенда в подъезде — бот открывается с уже
   привязанным домом, вводить адрес не нужно.
2. Один раз даёт согласие на обработку персональных данных.
3. Пишет о проблеме свободным текстом («сифонит из стены за ванной»).
4. Получает мгновенное подтверждение приёма, затем — определённую зону
   ответственности со ссылкой на норматив, номер заявки и нормативный срок.
5. В любой момент запрашивает статус заявки внутри бота.
6. Если о той же аварии уже сообщили соседи — присоединяется к существующей
   заявке вместо создания дубликата.
7. Получает проактивные уведомления о плановых и аварийных отключениях.

## Быстрый старт

Стек: Python 3.12, `uv`, FastAPI, PostgreSQL 16, Qdrant — см.
[architecture.md](./documentation/architecture.md). На данный момент (после
INIT-001) реализован только каркас: `/health`, `/ready` и пустые модули по
границам архитектуры — без бизнес-логики. Все команды ниже реально
выполнены и проверены.

### Вариант 1 — только Docker (рекомендуется для проверки решения)

```bash
cp .env.example .env
docker compose up --build -d
curl http://localhost:8000/health
curl http://localhost:8000/ready
```

Ожидаемо: `{"status":"ok"}` и `{"status":"ok","postgres":true,"qdrant":true}`.
Холодная сборка каркаса (без эмбеддингов — см. известные ограничения) —
около 1 минуты, укладывается в бюджет ≤5 минут из формата сдачи кейса.

Остановка и повторный запуск без потери данных (тома `postgres_data` и
`qdrant_data` сохраняются):

```bash
docker compose down
docker compose up -d
```

### Вариант 2 — локальная разработка через venv

Postgres и Qdrant поднимаются в Docker, а приложение — локально через `uv`,
с автоперезагрузкой при правке кода:

```bash
cp .env.example .env
uv sync
docker compose up -d postgres qdrant
uv run alembic -c db/alembic.ini upgrade head
uv run uvicorn upravdom.main:app --reload --port 8000
```

`.env` в этом сценарии указывает на `localhost` с нестандартными портами
(`POSTGRES_PORT=55432`, `QDRANT_PORT=56333`) — специально, чтобы не
конфликтовать с локально установленными Postgres/Qdrant на машине
разработчика. При полном `docker compose up` (вариант 1) те же переменные
для контейнера `app` переопределяются на внутренние адреса сети —
подробности в [architecture.md §12.1](./documentation/architecture.md).

### Проверки

Единая команда (ruff, mypy, pytest, `docker compose config`, проверка
секретов):

```bash
bash scripts/check.sh
```

## Работа с данными

- Контакты аварийно-диспетчерских служб, ресурсоснабжающих организаций,
  дома и уведомления об отключениях в MVP — **смоделированные тестовые
  данные**, помеченные флагом `is_test_data`. Реальной интеграции с ГИС ЖКХ
  или системами конкретной УК нет.
- Нормативная база (ЖК РФ, ПП РФ №416, №354, №626, №40) — подготовленные
  тексты первоисточников, версионируемые по дате вступления в силу.
- Обработка персональных данных: однократное согласие при онбординге,
  во внешний LLM-сервис передаётся только обезличенный фрагмент описания —
  см. [architecture.md §11](./documentation/architecture.md).

## Живой бот в MAX и внешний сервис, не воспроизводимый в Docker

Бот доступен в MAX: **`t449_hakaton_max_bot`** (ник выдан организаторами,
не меняется). Основной сценарий проверяется прямо в MAX — не через
адрес ниже.

Для приёма и отправки сообщений MAX требует настоящий публичный
HTTPS-адрес с доверенным сертификатом (самоподписанный не принимается —
это требование самой платформы, не наше решение). Такой адрес — внешняя,
непрерывно работающая инфраструктура, а не то, что поднимается локальной
командой `docker compose up` из этого репозитория:

- прод-деплой крутится на отдельной VM, конфигурация — в [`deploy/`](./deploy)
  (`compose.vm.yaml`, `Caddyfile`), не подменяет и не изменяет корневой
  `compose.yaml`;
- TLS — Caddy + Let's Encrypt, домен — бесплатный DuckDNS;
- дополнительно: `platform-api2.max.ru` использует сертификат,
  выпущенный Russian Trusted CA (Минцифры) — без явного добавления этого
  корневого центра в доверенные (см. `docker/certs/`,
  `docker/app.Dockerfile`) исходящие запросы к MAX не проходят TLS-проверку
  ни в каком окружении, включая тот же `docker compose up` в корне.

`docker compose up` в корне репозитория поднимает и проверяет **локальную
сборку** решения (см. «Быстрый старт») — этого достаточно, чтобы
убедиться, что код рабочий и воспроизводимый. Публичный адрес и живой
диалог с ботом — отдельная, уже развёрнутая часть, которую не нужно (и
не следует) поднимать заново для проверки кода.

## Известные ограничения

Полный перечень — [architecture.md §15](./documentation/architecture.md).
Кратко: нет реальных интеграций с внешними системами ЖКХ, нет рабочего места
диспетчера УК, нет админки онбординга управляющих компаний, обработка
персональных данных закрыта частично (согласие есть, сроков хранения и
удаления по запросу субъекта нет).

> Разделы формата сдачи, которые появятся до дедлайна: запуск одной командой
> через Docker, используемые порты, зависимости, внешние сервисы, порядок
> работы с тестовыми данными, пошаговый сценарий проверки, примеры ожидаемого
> поведения, порядок остановки и повторного запуска.
