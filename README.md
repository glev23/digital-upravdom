# Цифровой Управдом

Чат-бот в MAX, который по свободному описанию проблемы определяет, **кто
отвечает** за её устранение, сразу создаёт заявку с нормативным сроком и
показывает норму, по которой граница ответственности проходит именно так.

Трек «Умный город» (Минобрнауки России × MAX).

**Бот в MAX:** `t449_hakaton_max_bot` — основной сценарий проходится прямо в
нём (ник выдан организаторами и не меняется).

## Назначение решения

Житель многоквартирного дома при аварии должен сам понять, кто отвечает — УК,
ресурсоснабжающая организация, он сам как собственник или муниципалитет — и
найти рабочий контакт. Граница ответственности по воде и отоплению проходит по
первому отключающему устройству и регулярно становится предметом судебных
споров; 37% жителей МКД не знают даже свою управляющую компанию (ВЦИОМ,
02.07.2025); роботизированный обзвон Минстроя нашёл сотни недействующих номеров
аварийно-диспетчерских служб.

ГИС ЖКХ, «Госуслуги Дом» и приложения УК отвечают на вопрос **«как подать
заявку»** — это форма, в которой житель сам выбирает категорию и адресата.
Ни один из них не отвечает на вопрос **«кому»**, хотя отсутствие именно этого
знания и является проблемой.

«Цифровой Управдом» забирает это решение на себя:

- определяет тип проблемы и зону ответственности по тексту жителя;
- показывает основание — дословную цитату нормы со ссылкой на пункт;
- честно говорит «не берусь определить» вместо уверенной ошибки;
- схлопывает массовые обращения об одной аварии в одну заявку с подписчиками;
- предупреждает об отключениях сам, не дожидаясь, пока житель куда-то зайдёт.

Подробное сравнение с существующими сервисами —
[idea_and_scope.md, шаг 3.5](./documentation/idea_and_scope.md).

## Основной пользовательский сценарий

1. Житель сканирует QR-код со стенда в подъезде — бот открывается с уже
   привязанным домом (deep-link со стартовым параметром), вводить адрес не
   нужно. Запасной путь — ввод адреса текстом, если ссылка была без параметра.
2. Один раз даёт согласие на обработку персональных данных (две кнопки).
3. Пишет о проблеме свободным текстом: «из стены за ванной сифонит вода».
4. Получает мгновенное «Принял, обрабатываю…», затем — заявку с номером,
   ответственной организацией, контактом её АДС, нормативным сроком и
   основанием — ссылкой на пункт норматива с короткой цитатой. Полный текст
   пункта — по кнопке «Показать норму».
5. В любой момент спрашивает «статус 12» или «статус» — видит состояние и
   историю переходов заявки.
6. Спрашивает «что в доме» — видит, о чём уже сообщили соседи (тип, статус,
   дата), без текстов их обращений.
7. Если о той же аварии уже сообщили — присоединяется к существующей заявке;
   если это другая проблема, выходит из склейки кнопкой.
8. Получает уведомления о смене статуса своей заявки и об отключениях в доме.
9. Спрашивает о своих правах своими словами: «за сколько часов приедет мастер» —
   получает ответ строго по подтверждённым фрагментам нормативов и документов
   своей УК либо честный отказ.
10. Пишет о том, что заявкой не решается — «в подъезде орут по ночам», «что
    делать, если затопит сосед», — и получает совет, куда обращаться, без
    заявки в УК. Уборка и поломки при этом остаются заявками.

## Состав и архитектура решения

Монолит на FastAPI с явными границами модулей — масштаб MVP не требует
микросервисов, но границы проведены так, чтобы их можно было разнести
(`architecture.md` §8, §16).

```
MAX Bot API ──webhook──► bot_gateway ──► inbox (Postgres, идемпотентность по mid)
                              ▲                    │
                              │                    ▼
                          outbox ◄──── flow (диалог: интенты → статус → права → classify)
                        (Postgres,                 │
                      повторы с backoff)           ├─► classifier ──► masking ──► OpenRouter
                              ▲                    │         └─────► knowledge (RAG, Qdrant)
                              │                    ├─► dedup (склейка обращений)
                          scheduler ───────────────┼─► tickets (заявки, статусы, адресаты)
                     (APScheduler в том же         ├─► rights (справка по нормативам)
                      процессе: inbox, outbox,     └─► consult (совет без заявки)
                      уведомления)
```

| Модуль | Ответственность |
|---|---|
| `bot_gateway` | Вебхук с проверкой подписи, идемпотентный inbox, outbox с повторами, лимитер частоты |
| `onboarding` | Deep-link, поиск дома по адресу, согласие на ПДн и его версии |
| `flow` | Диалог: бытовые интенты, статус, список по дому, классификация, роутинг по намерению из ответа модели |
| `classifier` | Маскирование → RAG → LLM → проверка основания → порог уверенности → журнал |
| `knowledge` | Корпус нормативов, чанкинг, эмбеддинги, поиск с фильтром редакции и УК |
| `masking` | Телефоны, e-mail, ФИО, номера квартир — до отправки во внешнюю модель |
| `tickets` | Заявки, короткие номера, адресаты, сроки, статусы, уведомления подписчикам |
| `dedup` | Склейка массовых обращений об одной аварии, выход из склейки |
| `notifications` | Рассылка об отключениях жителям дома с действующим согласием |
| `rights` | Справка о правах строго по подтверждённым фрагментам нормативов и документов УК |
| `consult` | Совет по ситуациям, которые не решаются заявкой: шум, соседи, посторонние; без телефонов и номеров актов, которых модель не видела |

Полное описание — [architecture.md](./documentation/architecture.md).

## Запуск всех локальных компонентов одной командой

```bash
cp .env.example .env
```

```bash
docker compose up --build -d
```

Поднимаются три контейнера: `app` (API + воркер + планировщик), `postgres`,
`qdrant`. Контейнер `app` на старте сам применяет миграции, наполняет
справочники и демо-данные и загружает векторы базы знаний — отдельных команд
не нужно.

Холодная сборка без кэша — **2 мин 46 с** (замер `docker compose build
--no-cache app`, без учёта загрузки базовых образов), бюджет кейса ≤ 5 минут.
Основное время занимает первый стейдж, где модель эмбеддингов один раз
экспортируется в ONNX; в рантайм-образ `torch` не попадает.

Проверка, что всё поднялось:

```bash
curl http://localhost:8000/health
```

```bash
curl http://localhost:8000/ready
```

Ожидается `{"status":"ok"}` и `{"status":"ok","postgres":true,"qdrant":true}`.

## Необходимые параметры окружения

Без внешних ключей локальный стек поднимается и отвечает на `/health` и
`/ready`, но диалог с ботом не работает: сообщения приходят из MAX, а
классификация обращается к внешней модели. Чтобы пройти сценарий целиком,
нужны:

| Параметр | Зачем | Где взять |
|---|---|---|
| `MAX_BOT_TOKEN` | Приём и отправка сообщений | Токен бота от организаторов хакатона |
| `MAX_WEBHOOK_SECRET` | Проверка подлинности вебхука; без него заявки может создать любой, кто узнал URL | Любая случайная строка, `openssl rand -hex 24` |
| `MAX_BOT_USERNAME` | Сборка deep-link на привязку дома | Ник бота, после создания не меняется |
| `PUBLIC_BASE_URL` | Адрес вебхука и deep-link | Публичный HTTPS-адрес сервиса |
| `OPENROUTER_API_KEY` | Классификация и справка по нормативам | Ключ OpenRouter; используются только бесплатные модели (`:free`) |

MAX требует публичный HTTPS с доверенным сертификатом — самоподписанный не
принимается. Поэтому вебхук нельзя принять на `localhost`: для живого диалога
нужен внешний адрес (см. «Внешние сервисы»). Проверка самого кода публичного
адреса не требует — см. «Пошаговый сценарий проверки».

Секреты в репозиторий не попадают: в `git` только `.env.example` без значений,
а `scripts/check.sh` отдельным шагом ищет непустые токены в отслеживаемых
файлах.

## Зависимости

Версии зафиксированы в [`uv.lock`](./uv.lock) (менеджер — `uv`), состав — в
[`pyproject.toml`](./pyproject.toml).

**Рантайм:** `fastapi`, `uvicorn[standard]`, `pydantic-settings`,
`sqlalchemy[asyncio]`, `asyncpg`, `alembic`, `qdrant-client` (>=1.12,<1.19 —
совместимость с сервером v1.17), `httpx`, `apscheduler`, `onnxruntime`,
`tokenizers`, `numpy`.

**Разработка:** `ruff`, `mypy`, `pytest`, `pytest-asyncio`.

**Только для сборки образа:** `torch`, `sentence-transformers`,
`optimum[onnxruntime]` — отдельная группа `embedding-export`. Они живут в
первом стейдже `docker/app.Dockerfile`, где модель эмбеддингов один раз
экспортируется в ONNX, и **в рантайм-образ не попадают**: веса модели не
хранятся в репозитории (490 МБ), а `torch` не нужен для инференса.

**Образы:** `python:3.12-slim`, `postgres:16`, `qdrant/qdrant:v1.17.0`,
`caddy:2-alpine` (только прод).

## Внешние сервисы и интеграции

| Сервис | Роль | Что будет без него |
|---|---|---|
| **MAX Bot API** (`platform-api2.max.ru`) | Приём и отправка сообщений, кнопки, deep-link | Нет диалога; локальный стек поднимается и проходит тесты |
| **OpenRouter** | Классификация и справка по нормативам, только бесплатные модели | Деградация: классификация по прототипам в памяти, справка честно отказывает (`architecture.md` §10) |
| **Let's Encrypt + DuckDNS + Caddy** | Публичный HTTPS для вебхука (прод) | Живой диалог в MAX невозможен |
| PostgreSQL, Qdrant | Состояние и векторы | Поднимаются тем же `docker compose up` |

Особенность, которая не видна из кода: сертификат `platform-api2.max.ru`
выпущен Russian Trusted CA (Минцифры), которого нет в доверенных у
`httpx`/`certifi`. Корневой и промежуточный сертификаты добавлены в образ
(`docker/certs/`, `docker/app.Dockerfile`) — без этого **ни одно** исходящее
сообщение в MAX не проходит TLS-проверку.

Реальной интеграции с ГИС ЖКХ или системами конкретной УК нет — это
смоделированные данные, см. ниже.

## Работа с данными

- **Нормативы** — дословные тексты первоисточников (ЖК РФ, ПП РФ №491, №416,
  №354, №626, №40), нарезанные по пунктам, с датами вступления в силу: норма,
  не вступившая в силу на дату обращения, в поиск не попадает. Исходники —
  `data/kb/sources/`, предпосчитанные векторы — `data/kb/` (не вычисляются при
  старте).
- **Персональные данные.** Однократное согласие при онбординге с версией
  текста; во внешнюю модель уходит только замаскированный фрагмент
  (`[ТЕЛЕФОН]`, `[ФИО]`, `[КВАРТИРА]`, `[EMAIL]`, `[НОМЕР]`). Немаскированный
  текст остаётся в базе — он нужен диспетчеру. Журналы и тексты ошибок
  хранят только маскированный текст. Житель может отозвать согласие
  командой «отозвать согласие».
- **Доступ.** Заявка по номеру видна только её подписчику; список обращений по
  дому содержит тип, статус, дату и число присоединившихся — без текстов
  чужих обращений.
- **Хранение.** Заявки, события, журналы классификации — в PostgreSQL;
  векторы нормативов и обращений — в Qdrant. События заявки — append-only
  (триггер в БД).

Подробно — [architecture.md §5, §11](./documentation/architecture.md).

## Порядок работы с тестовыми данными

**Все организации, дома и уведомления в решении — смоделированные,** помечены
флагом `is_test_data` и словом «(тест)» в названии. Это требование
ограничения №10 кейса.

Демо-состояние создаётся автоматически при старте контейнера
(`scripts/seed_demo.py`, идемпотентно — повторный запуск ничего не дублирует):

- 2 управляющие компании, 6 ресурсоснабжающих организаций;
- 3 дома в Казани со связями «дом → ресурс → организация → контакт»;
- 2 deep-link токена на каждый дом (стенд в подъезде и квитанция);
- 2 уведомления об отключениях для проверки рассылки;
- смоделированный договор управления одной из УК в базе знаний
  (`data/kb/sources/uk_vahitovskaya.md`) — в ответе жителю он подписан как
  «тестовый документ».

Токены deep-link печатаются в лог при старте:

```bash
docker compose logs app | grep "start="
```

Если `MAX_BOT_USERNAME` заполнен, в логе будет сразу готовая ссылка вида
`https://max.ru/<ник_бота>?start=<токен>`; без него — только токен, потому что
собрать ссылку не из чего.

Наборы для замеров лежат в `data/test_cases/`: 50 описаний проблем с эталонной
разметкой (`scripts/run_accuracy_check.py`) и группы описаний одной аварии для
проверки склейки (`scripts/run_dedup_check.py`).

## Пошаговый сценарий проверки

### Вариант A — основной сценарий в MAX (2–3 минуты)

1. Открыть в MAX бота `t449_hakaton_max_bot`.
2. Перейти по deep-link тестового дома (ул. Декабристов, 10):
   <https://max.ru/t449_hakaton_max_bot?start=9d7984baecef5909> — или
   отсканировать QR со служебного слайда презентации. Бот покажет
   распознанный адрес и попросит согласие на обработку ПДн.
3. Нажать «Согласен».
4. Написать жалобу своими словами: `в подъезде на лестничной площадке не горит
   свет второй день`.
5. Получить подтверждение и заявку с номером, адресатом, сроком и основанием.
6. Написать `статус` (без номера) — увидеть список своих заявок.
7. Написать `что в доме` — увидеть обращения дома.
8. Написать `за сколько часов приедет мастер после заявки об аварии` —
   получить ответ со ссылкой на норму или документ УК. Команда `/права`
   делает то же самое и работает даже при недоступности внешней модели.
9. Написать `где купить танк` — получить отказ, **без** создания заявки.




`check.sh` прогоняет линтер, строгий mypy, все тесты (включая сквозной тест
сценария на реальном Postgres), валидирует `compose.yaml` и проверяет, что в
отслеживаемых файлах нет секретов.

Тесты используют **те же** Postgres и Qdrant, что и контейнер `app` (адреса
из `.env`). Поэтому прогонять их на работающем боте не следует: тесты
пересоздают коллекцию базы знаний и пишут в те же таблицы. Перед проверкой
достаточно остановить приложение, хранилища оставить:

```bash
docker compose stop app
```

```bash
docker compose start app
```

Отдельно — сквозной тест основного сценария на продакшн-маршрутизации:

```bash
uv run pytest tests/integration/test_e2e_scenario.py -v
```

Действия диспетчера (смена статуса — жителю уходит уведомление). `<номер>` —
номер из ответа бота; на пустой базе команда честно ответит «заявка № N не
найдена»:

```bash
docker compose exec app python scripts/ticket_status.py <номер> in_progress
```

Уведомления об отключениях, которые созданы демо-данными:

```bash
docker compose exec app python scripts/notify.py list
```

Вывод — строки вида
`75f8e250…  действует  planned_outage  холодное водоснабжение  30.09 00:10 — 30.09 08:10  sent=0 pending=0 failed=0`.

## Примеры ожидаемого поведения системы

Ответы ниже — дословно из живого прогона в MAX на развёрнутом стенде
29.09.2026; пример склейки с соседом — из прогона 27.09.2026.

**Жалоба → заявка:**

> **Житель:** в подъезде на лестничной клетке не горит свет второй день
> **Бот:** Принял, обрабатываю…
> **Бот:** Заявка № 1 принята. Отвечает: ООО «УК Вахитовская» (тест).
> Аварийная служба: +7 (843) 000-00-01.
> Нормативный срок для этого типа не установлен (ПП РФ №491).
> Основание: ПП РФ №491, п. 7 — В состав общего имущества включается
> внутридомовая система электроснабжения, состоящая из вводных шкафов,
> вводно-распределительных устройств, аппаратуры защиты…
> *(кнопки «Статус заявки», «Показать норму» — полный текст пункта)*

**Модель не уверена — заявка уходит диспетчеру, а не угадывается:**

> **Житель:** с крыши течёт на пятый этаж после дождя
> **Бот:** Принял, обрабатываю…
> **Бот:** Не берусь точно определить ответственного — передал заявку № 2
> диспетчеру вашей УК. АДС: +7 (843) 000-00-01.

**Что происходит в доме:**

> **Житель:** какие заявки есть в доме
> **Бот:** Обращения по дому г. Казань, ул. Декабристов, д. 10:
> • № 3 — Проблема в местах общего пользования (подъезд, МОП), принята (29.09 15:53)
> • № 2 — Протечка кровли, передана диспетчеру для уточнения ответственного (29.09 15:52)
> • № 1 — Проблема в местах общего пользования (подъезд, МОП), принята (29.09 15:50)
> Показываю тип, статус и дату — без текстов обращений соседей.

**Вопрос о правах своими словами, без команды — ответ по документу своей УК:**

> **Житель:** за сколько приедет мастер после заявки об аварии
> **Бот:** Принял, обрабатываю…
> **Бот:** Ищу в нормативах…
> **Бот:** Мастер приедет в течение двух часов после регистрации заявки, а в
> нерабочее время — в течение трёх часов.
> Основание:
> • Договор управления ООО «УК Вахитовская» (тестовый документ), п. 4.2
> Это справка по нормативам, а не юридическая консультация.

**Вопрос, на который в нормативах ответа нет, — честный отказ:**

> **Житель:** /права а если кот мяукает что делать
> **Бот:** Ищу в нормативах…
> **Бот:** В нормативах, которые я знаю, прямого ответа на этот вопрос нет. Вы
> можете уточнить в своей управляющей компании (АДС: +7 (843) 000-00-01) или
> в жилищной инспекции вашего региона.

**Повтор той же жалобы — не вторая заявка:**

> **Житель:** в подъезде на лестничной площадке не горит свет второй день
> **Бот:** Об этой проблеме у вас уже есть заявка № 1, статус — принята.
> Нормативный срок для этого типа не установлен (ПП РФ №491).
> *(кнопки «Это другая проблема», «Статус заявки»)*

**Сосед сообщает о той же аварии — одна заявка, а не две:**

> **Бот:** Об этой проблеме в вашем доме уже сообщили — присоединил вас к
> заявке № 7, статус — принята. *(кнопки «Это другая проблема», «Статус заявки»)*

**Вопрос не про дом — отказ без заявки:**

> **Житель:** где купить танк
> **Бот:** Я занимаюсь только домом и коммунальными услугами: авариями,
> заявками, отключениями и вопросами о том, кто за что отвечает. С этим —
> обращайтесь.

**Ошибочные действия не создают тупиков:** «статус» без номера показывает
список заявок, нетекстовое сообщение (фото, голосовое) получает подсказку
написать текстом, «спасибо» и «привет» не доходят до модели и не создают
заявок.

## Порядок остановки и повторного запуска

Остановка без потери данных (тома `postgres_data` и `qdrant_data`
сохраняются):

```bash
docker compose down
```

Повторный запуск — заявки, согласия и статусы на месте:

```bash
docker compose up -d
```

Полный сброс состояния, включая базу и векторы (демо-данные будут созданы
заново при следующем старте):

```bash
docker compose down -v
```

Перезапуск только приложения после правки кода:

```bash
docker compose up -d --build app
```

## Известные ограничения

- **Точность классификации нестабильна между вызовами.** Бесплатная модель на
  одном и том же описании может дать разную зону и уверенность; на тестовом
  наборе одинаковую зону во всех трёх прогонах дали 38 обращений из 50. По
  этой же причине около 18% обращений уходят в ветку «не берусь определить» —
  это осознанный выбор в пользу честного отказа против уверенной ошибки.
- **Бесплатные модели бывают недоступны.** Когда основная не отвечает,
  ответ даёт одна из пяти резервных — они слабее на трудных случаях, а если
  лежит вся цепочка, ответ задерживается до 100 с. Обращение при этом не
  теряется.
- **Консультант отвечает своими словами.** Номера актов, телефоны и сайты,
  которых он не видел, код отсекает, но неверный по сути совет исключить
  нельзя; опорой служит справка «кто чем занимается» в промпте.
- **Нет реальных интеграций** с ГИС ЖКХ и системами УК: организации, дома,
  контакты и договор управления — смоделированные данные.
- **Нет рабочего места диспетчера УК** — заявка создаётся и маршрутизируется,
  но интерфейса получателя в MVP нет.
- **Нет админки онбординга УК** — подключение новой управляющей компании
  сейчас ручное (чек-лист из 8 шагов в `idea_and_scope.md`).
- **Обработка ПДн закрыта частично:** согласие и его версии есть, сроков
  хранения и удаления по запросу субъекта нет.
- **Заявка без фото** — вложения не принимаются, формат загрузки файлов в MAX
  не проверялся.
- **Мини-приложение не делалось** — история обращений по дому доступна текстом
  в чате.
- **Порог уверенности откалиброван на том же наборе, на котором меряется
  точность** — это завышает результат, факт зафиксирован в
  `architecture.md` §4.

Полный перечень — [architecture.md §15](./documentation/architecture.md).
