# Памятка для разработчика: ветка `dev-ilya`

Этот файл — всё, что нужно прочитать и знать до начала работы над
четырьмя задачами: **STATUS-001, DEDUP-001, NOTIFY-001, RIGHTS-001**.
Файл `.env` тебе передадут отдельно — настраивать окружение не нужно.

## 1. Главные правила (прочитать первыми)

1. **Работаешь только в ветке `dev-ilya`.** Ветку создаёшь от свежего
   `main` (раздел 3) и пушишь только её.
2. **Ничего не мерджить.** Ни в `main`, ни куда-либо ещё: не нажимать
   «Merge» в GitHub, не делать `git merge`/`git rebase` в `main`, не пушить
   в `main`, никаких `--force` в чужие ветки. Pull Request открывать
   **не нужно** — если откроешь для удобства просмотра, не мерджи его.
3. **Ничего не деплоить.** Не подключаться к серверу, не запускать
   `deploy/compose.vm.yaml`, не менять файлы в `deploy/`. Бот в MAX уже
   работает на сервере — любой твой запуск туда сломает живую демонстрацию.
4. **Не трогать подписку вебхука MAX.** Никаких вызовов
   `POST /subscriptions`, `DELETE /subscriptions`, `GET /updates` с токеном
   бота: вебхук зарегистрирован на рабочий сервер, перерегистрация уведёт
   сообщения жителей с него.
5. **Не коммитить секреты и большие файлы.** `.env`, `credentials/`,
   `data/model/` в `.gitignore` — не добавлять их принудительно
   (`git add -f`). Перед каждым коммитом смотри `git status`.
6. **Не выдумывать нормы.** Любой текст, который бот показывает жителю как
   норму, берётся только из базы знаний (`data/kb/sources/` — дословные
   официальные тексты). Никаких «ПП №… п. …» из головы или от модели.
7. **Перед каждым пушем** — `bash scripts/check.sh` зелёный.

## 3. Git: как начать и как сдавать

```bash
git clone https://github.com/glev23/digital-upravdom.git
cd digital-upravdom
git checkout main
git pull
git checkout -b dev-ilya
```

Дальше вся работа — в `dev-ilya`:

```bash
git status
git add <конкретные файлы>
git commit -m "STATUS-001: уведомления подписчиков о смене статуса"
git push -u origin dev-ilya
```

- Коммиты — с префиксом задачи (`STATUS-001: …`, `DEDUP-001: …`); можно
  несколько коммитов на задачу.
- Пушить можно и нужно по мере работы (хотя бы после каждой закрытой
  задачи), чтобы работа не лежала только у тебя.
- Если в `main` появятся новые коммиты — **не** подтягивай их сам в свою
  ветку без договорённости: сведение веток сделает основной разработчик.

## 4. Локальный запуск

Postgres и Qdrant — в Docker, приложение и тесты — через `uv` (venv):

```bash
uv sync
docker compose up -d postgres qdrant
uv run alembic -c db/alembic.ini upgrade head
uv run python scripts/seed_problem_types.py
uv run python scripts/seed_demo.py
```

Модель эмбеддингов (~490 МБ) в репозитории нет — один раз экспортировать
локально (нужна для KB, дедупликации, тестов с эмбеддингами):

```bash
uv sync --group embedding-export
uv run python scripts/export_onnx.py
uv sync
uv run python scripts/load_kb.py
```

Приложение целиком (как у проверяющих) — `docker compose up --build`.
Все команды запускать **из корня репозитория**: скрипты читают `.env` из
текущей папки.

Проверка перед пушем:

```bash
bash scripts/check.sh
```

Это `ruff`, `ruff format --check`, `mypy --strict`, `pytest`,
`docker compose config` и поиск секретов. Интеграционные тесты сами
создают отдельную базу `<имя>_test` и накатывают миграции — базу
разработки они не трогают.

## 6. Как устроен код и на чём здесь уже спотыкались

**Поток сообщения.** `POST /webhook/max` пишет событие в `inbound_events`
→ воркер (`scheduler.py`) забирает его → `bot_gateway/dispatcher.py`
выбирает обработчик → онбординг (`onboarding/handlers.py:gated`) → основной
сценарий (`flow/handlers.py`). Кнопки маршрутизируются по префиксу
payload в `dispatcher.py:route_callback` (`onb:`, `clf:`; новые префиксы —
`ddp:` для DEDUP-001 и т. п.).

**Транзакции.**

- Обработчики **не коммитят**: воркер фиксирует всё, что сделал
  обработчик, одним commit вместе с отметкой события `done`, а при
  исключении — откатывает (частичный результат не должен пережить сбой).
  Единственное исключение — мгновенное подтверждение в
  `flow/handlers.py:on_message` (коммитится до вызова LLM, см. FLOW-001).
- `outbox.enqueue_message` тоже не коммитит — сообщение уходит вместе с
  транзакцией вызывающего.
- Отправка в MAX — **только** через `outbox` (повторы с задержкой).
  Прямой вызов `MaxClient` из обработчика запрещён.

**Кнопки.** Состояние живёт в payload кнопки, а не в таблице сессий.
Лимит payload — 1024 символа; **не класть туда кириллицу и свободный
текст** (base64 кириллицы раздувается почти втрое — на этом уже ломалась
кнопка «Оставить адрес»). Кладём идентификаторы и номера, а при нажатии
**перепроверяем права** (кнопку можно подделать: чужой номер заявки,
чужой `log_id`).

**Персональные данные.**

- В LLM и в журналы — только маскированный текст (`masking.mask()` →
  `MaskedText`; `mypy` не даст передать сырой `str` в промпт).
- В логи приложения не пишем текст жителя и тексты ответов модели; в
  `last_error` — только тип исключения.
- Жителю без действующего согласия бот ничего не отправляет
  (`onboarding.service.has_valid_consent`).

**LLM и эмбеддинги.**

- LLM-клиент — один на процесс: `classifier.llm.get_llm_client()`. **Не
  создавать `OpenRouterClient()` на каждый вызов** — лимит частоты и
  размыкатель живут в экземпляре и иначе не работают.
- `embeddings.embed()` синхронный и тяжёлый — из async-кода вызывать через
  `asyncio.to_thread`, иначе встаёт весь event loop (вебхук, воркеры).
- Основание для жителя — только подтверждённые фрагменты базы знаний
  (`classifier.service.confirm_citations` по номерам фрагментов); полная
  ссылка — `RetrievedChunk.label` («ПП РФ №491, п. 5 абз. 1»), а не
  короткий `ref`.
- Из `problem_types.norm_reference` жителю показывается только ссылка на
  акт (`flow/handlers.py:_norm_label`) — остальное там служебные пояснения.
- `problem_types.resolution_hours` — это **допустимый перерыв** по прил. 1
  ПП №354, а не срок устранения; жителю так и пишем.

**Миграции и перечисления.**

- Перечисления — `VARCHAR + CHECK` через `models/enums.py:pg_enum` с явным
  уникальным именем ограничения.
- Длина `VARCHAR` у enum-колонки = длине самого длинного значения. Новое
  значение длиннее старых — в миграции нужен `alter_column` на длину
  (уже наступали: `awaiting_consent` не влез в `VARCHAR(10)`).
- Изменение CHECK — `drop_constraint` + `create_check_constraint` с тем же
  именем, в `downgrade` — обратно.

**Docker.** Новый файл в `scripts/`, который должен работать внутри
контейнера, надо добавить в `COPY` в `docker/app.Dockerfile`, а новую
папку `data/…` — ещё и в allowlist `.dockerignore`. Уже было: скрипт не
попал в образ, контейнер падал на старте, а тесты при этом были зелёными.

**Настройки.** Новая переменная окружения добавляется одновременно в
`src/upravdom/config.py`, `.env.example` и architecture.md §12 — их
синхронность проверяется при сдаче. Свой `.env` правь сам под новые
переменные (значения по умолчанию в `config.py` должны позволять
работать и без них).

**Тесты.**

- Интеграционные — на настоящем Postgres (`tests/integration/conftest.py`:
  фикстура `session` в откатываемой транзакции, `onboard_user`).
- LLM в тестах — `FakeLlmClient`, MAX — `FakeMaxClient`. **Тесты не ходят
  в сеть.**
- Тексты — в `texts.py` модулей, в тестах сравнивать с константами, а не
  с копией строки.

**Тексты и стиль.** Все сообщения жителю — в `texts.py` соответствующего
модуля. Комментарии в коде — только «почему», коротко.

## 7. Известная дыра: классификация на бесплатной модели

Подробно — [`tasks/classify-003.md`](./tasks/classify-003.md). Коротко:
бесплатная модель `nex-agi/nex-n2.5-mini:free` нестабильна — на одних и
тех же фразах то ссылается на фрагменты нормативов, то нет, и
уверенность у неё скачет. Поэтому живой прогон сейчас даёт в основном
«не берусь определить». Это задача **основного разработчика**, не твоя:

- не меняй `classifier/prompt.py`, `classifier/schema.py`, пороги и
  правило «без подтверждённой ссылки нет автоматической маршрутизации»;
- в RIGHTS-001 эта же нестабильность даст частые отказы — это ожидаемо,
  **не ослабляй проверку основания**, чтобы поднять долю ответов;
- живые прогоны (`scripts/classify_demo.py`, `scripts/rights_demo.py`)
  тратят суточный лимит бесплатной модели — несколько запусков, не циклы.

## 8. Когда задача считается сделанной

1. Все критерии приёмки в task-файле выполнены и отмечены `[x]`;
   невыполненные — с объяснением.
2. `bash scripts/check.sh` зелёный.
3. Заполнен раздел «Результат закрытия»: что изменено, какие проверки
   реально запускались (с цифрами), отклонения от постановки, follow-up.
4. Статус `done` — одновременно в task-файле и в `progress_dev.md` (в
   твоей ветке).
5. Коммит запушен в `dev-ilya`.

Если в постановке что-то противоречит коду или непонятно — прими
разумное решение, опиши его в «Отклонениях от постановки» и продолжай;
если решение ломает чужой модуль или меняет контракт — лучше спроси.
