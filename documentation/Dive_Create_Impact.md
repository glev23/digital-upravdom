# DIVE — разобраться в задаче

## 1. PSW: шесть вопросов о задаче

**Задача проекта одной фразой:** сделать чат-бота в MAX, через который житель
дома под управлением УК сообщает об аварии своими словами и сразу получает
корректно направленную заявку — без поиска контактов, дозвона и выяснения,
кто за что отвечает.

### 1.1 Контекст

**Зачем необходимо решение?**

- Житель при аварии должен сам определить, кто отвечает: УК, РСО, он сам
  как собственник или муниципалитет. Граница ответственности неочевидна
  даже юристам — по воде и отоплению она проходит по первому запорному
  устройству и регулярно становится предметом судебных споров.
- Контакт аварийной службы часто не работает: роботизированный обзвон
  Минстроя нашёл 555 недействующих номеров АДС только в Казани (публикация
  26.08.2026).
- Заявка, поданная голосом, остаётся строкой в журнале АДС без цифрового
  статуса; при передаче подрядчику или РСО житель теряет её из виду.
- Сантехника — 34% всех обращений в УК, аварийные обращения — 17%
  (1,8 млн обращений в 300+ УК, I полугодие 2026). Это массовый,
  повторяющийся сценарий, а не редкий случай.

**Какие решения уже существуют?**

| Решение | Что закрывает | Чего не закрывает |
|---|---|---|
| Звонок в АДС | Живой диспетчер | Дозвон, мёртвые номера, нет цифрового следа |
| ГИС ЖКХ | Подача обращения, статус | Житель сам выбирает адресата и категорию |
| Госуслуги.Дом (20+ млн) | Заявка в УК, статус, коллективные заявки | Та же форма с категориями; формальные ответы |
| Приложения УК («Диспетчер 24» и др.) | Заявки в свою УК | Только своя УК, адресат не определяется |
| Порталы регионов | Жалобы на благоустройство | Рубрикатор, не аварийный сценарий |
| Официальный канал УК в MAX (ПП №40 с 01.09.2026) | Факт присутствия УК в MAX | Норматив требует канал, а не удобный интерфейс |

Общий пробел: **все отвечают на вопрос «как подать заявку», ни один — на
вопрос «кому»**. Подробное сравнение — [idea_and_scope.md, шаг 3.5](./idea_and_scope.md).

### 1.2 Критерии успеха

**Что важно в решении?**

1. Житель получает правильного адресата по свободному описанию проблемы.
2. Ответ объясним: бот показывает норму, по которой граница ответственности
   проходит именно так, и честно говорит «не уверен», когда оснований мало.
3. Основной путь без лишних шагов: вход по QR без ввода адреса, одно
   сообщение, заявка с номером и сроком.
4. Обращение не теряется и не дублируется ни при каких сбоях.

**По каким критериям будут оценивать жюри?**

| Этап | Критерий | Вес | Наш главный аргумент |
|---|---|---|---|
| Онлайн, продукт (40%) | Потенциал масштабирования | **35%** | Единица тиража — одна УК; чек-лист подключения из 8 шагов |
| | Пользовательская ценность | 25% | Единственное отличие от существующих сервисов — определение адресата |
| | UX/UI | 20% | Вход по QR без ввода адреса, одно сообщение до заявки |
| | Обоснованность и целостность | 15% | Проблема → механика → метрика связаны; MoSCoW с честным Won't Have |
| | Презентация | 5% | — |
| Онлайн, техника (60%) | Работоспособность | **30%** | Сквозной сценарий в MAX |
| | Интеграция и обмен данными | 20% | Идемпотентный inbox, outbox с повторами |
| | Архитектура | 20% | Монолит с явными границами модулей |
| | Стабильность и ошибки | 10% | Матрица отказов, деградация без LLM |
| | Безопасность и данные | 10% | Маскирование, согласие на ПДн, секреты вне репозитория |
| | Документация | 10% | README по формату сдачи |
| Бонус | Возможность MAX сверх минимума | +0,15 | Deep-link со стартовым параметром |
| Финал | Ценность / масштабирование / MVP / пилот / защита / команда | 25 / 25 / 20 / 15 / 10 / 5% | — |

Допуск: решение в теме трека, бот в MAX запускается и проходит основной
сценарий, есть презентация. Нарушение любого пункта — 0 баллов.

### 1.3 Пространство решений

**Что минимально необходимо для MVP?**

- привязка жителя к дому (deep-link + запасной путь вводом адреса);
- согласие на обработку ПДн;
- приём свободного текста в MAX;
- определение типа проблемы и зоны ответственности по нормативам;
- заявка с номером, нормативным сроком и адресатом по дому;
- статус заявки в боте;
- тестовый набор и измерение точности против baseline.

**Что избыточно для MVP?**

- микросервисы, балансировщики, service mesh — нагрузка пилота это единицы
  обращений в сутки;
- реальная интеграция с ГИС ЖКХ и системами УК — недоступна на хакатоне,
  заменяется помеченными тестовыми данными;
- рабочее место диспетчера УК;
- несколько регионов в демо;
- мини-приложение — не нужно для основного сценария, только Could Have;
- собственный публичный API — по условиям кейса баллов не даёт, но создаёт
  обязательные проверки.

Полная приоритизация — MoSCoW в [idea_and_scope.md, шаг 6](./idea_and_scope.md).

### 1.4 Ограничения и барьеры

**Ограничения кейса:**

- MAX — среда реализации; основной сценарий проверяется в MAX и должен
  работать в мобильной и веб-версии;
- чат-бот или чат-бот с мини-приложением; мини-приложение не может быть
  изолированным от бота сервисом и требует HTTPS;
- **ник бота нельзя изменить после создания**;
- только открытые библиотеки; никаких частных API и чужого кода без
  свободной лицензии;
- секреты в репозитории запрещены;
- смоделированные данные обязательно помечаются в материалах;
- сборка в Docker — не дольше 5 минут, запуск всех компонентов одной командой;
- после дедлайна код не меняется.

**Барьеры, которые видим мы:**

| Барьер | Чем закрываем |
|---|---|
| Контракт MAX Bot API не проверен | Задача MAX-001 — подтверждённый контракт до кода |
| Бот должен быть доступен жюри — нужен публичный HTTPS | Задача DEPLOY-001 |
| `torch` может сломать бюджет сборки 5 минут | Задача SPIKE-001 — замер и выбор torch / ONNX до кода |
| Зависимость от внешнего LLM | Деградация на similarity search, резервная модель, кэш |
| Персональные данные жителей во внешнем сервисе | Маскирование, согласие, раскрытие в README |

### 1.5 Заинтересованные стороны

**Кто будет оценивать работу?**

- экспертное жюри трека «Умный город» (Минобрнауки России × MAX);
- технические проверяющие: запуск по README, прохождение сценария в MAX,

**Кто будет пользоваться решением?**

| Роль | Место в продукте | Что получает |
|---|---|---|
| **Житель / собственник в доме под УК, старый фонд** | Основной пользователь | Правильный адресат без поиска и дозвона, статус, предупреждения |
| Диспетчер УК | Получатель заявки, без своего интерфейса в MVP | Структурированные заявки; одна заявка вместо десятков при массовой аварии |

## 2. Не начинайте с технологии

| Шаг | Ответ |
|---|---|
| **1. Ситуация пользователя** | У жителя старого дома под УК течёт с потолка или из стены. Он не знает, кто отвечает — УК, РСО или он сам, — и где взять рабочий номер аварийной службы. |
| **2. Барьер** | Приходится искать контакт (стенд, квитанция, соседский чат), дозваниваться на номер, который может не работать, объяснять проблему устно и потом перезванивать, чтобы узнать, жива ли заявка. В цифровых сервисах — форма, где адресата надо выбрать самому. |
| **3. Изменение** | Одно сообщение своими словами вместо поиска контакта и дозвона; правильный адресат с объяснением по норме вместо догадки; номер заявки и статус вместо тишины. |
| **4. Механика** | Бот в MAX определяет тип проблемы и зону ответственности по свободному описанию, опираясь на нормативы, и сразу создаёт заявку с нормативным сроком. **Только после этого** возник вопрос о технологии: свободный текст не раскладывается в меню кнопок, поэтому нужны поиск по нормативам (RAG) и LLM. |

## 3. Custdev: разбор реального опыта

### 3.1 Что уже известно о реальном опыте жителей

Разбор по открытым источникам: отраслевая выборка обращений, результаты
проверок, опубликованные отзывы пользователей. Структура — по четырём вопросам
из методологии.

| Вопрос | Что показывают источники |
|---|---|
| **1. Контекст** — что произошло, какой результат нужен | Самая частая причина обращения в УК — сантехника: 34% всех заявок, аварийных обращений — 17% (1,8 млн обращений, 300+ УК, I полугодие 2026). Нужный результат — чтобы протечку остановили, а не чтобы заявку «зарегистрировали». |
| **2. Действия** — что делал сначала, чем пользовался | Телефон остаётся главным каналом: 49% обращений в 2025 году против 71% в 2020; доля мобильных приложений выросла с 16% до 36% (~9 млн обращений, 300 УК, 2020–2025). То есть половина жителей по-прежнему начинает со звонка. |
| **3. Барьеры** — где было сложнее всего | **Дозвон:** 555 недействующих номеров АДС в Казани, ещё 94 — в пяти районах Татарстана, у 18 УК контакты недостоверны (проверка Минстроя, август 2026). **Адресат:** пользовательница Госуслуги.Дом подала больше десяти заявок, все закрыты формальными ответами, УК отвечала «это потом, это не мы» (отзыв на irecommend.ru, 16.10.2024). Перекладывание ответственности — ровно та неопределённость, которую мы закрываем. |
| **4. Потери** — время, повторы, что если не решено | Заявки переоткрываются по несколько раз; следующий шаг — жалоба в ГЖИ. В Татарстане обращения в ГЖИ выросли на 41,2% за I полугодие 2026 (16 493 обращения; основные темы — содержание общего имущества и качество ЖКУ), штрафы по итогам проверок — 24,2 млн руб. против 7,4 млн годом ранее. Каждая нерешённая заявка превращается в повторное обращение, а затем в жалобу. |

**Что это подтверждает:** проблема массовая (каждое третье обращение —
сантехника), первый шаг всё ещё звонок, и именно на нём житель упирается
в мёртвые номера. Даже цифровая заявка не спасает от вопроса «кто отвечает».

**Чего открытые источники не показывают** и что должны дать интервью:
сколько времени житель тратит от обнаружения протечки до принятой заявки,
как часто первый звонок уходит не туда и как житель выясняет, чья это зона.

### 3.2 Гайд интервью

**Кого опрашиваем:** 5–7 жителей домов под управлением УК, построенных
в 1957–2000-х годах, у которых за последний год была авария или неисправность
в квартире или в подъезде. Приоритет — те, кто сталкивался с протечкой:
это самый частый сценарий.

**Чего не спрашиваем** — такие вопросы дают социально желаемые ответы
про воображаемое будущее:

- «Вам был бы полезен бот, который сам определит, кто отвечает?»
- «Пользовались бы вы таким ботом в MAX?»
- «Нравится ли вам идея?»

**Что спрашиваем — только о последнем реальном случае:**

| Блок | Вопросы |
|---|---|
| **Контекст** | Вспомните последний раз, когда в доме или квартире что-то сломалось или протекло. Что произошло? Когда это было? Чего вы хотели добиться? |
| **Действия** | Что вы сделали первым делом? Где искали, кому звонить или писать? Что делали дальше? Какими сервисами, приложениями, чатами пользовались? |
| **Барьеры** | На каком этапе было сложнее всего? Приходилось ли выяснять, чья это зона ответственности? Дозвонились ли с первого раза? Узнали ли номер заявки? Как узнавали, что происходит с заявкой? |
| **Потери** | Сколько времени прошло от обнаружения проблемы до момента, когда её приняли в работу? А до устранения? Сколько раз пришлось звонить или писать повторно? Что было бы, если бы проблему так и не решили? Как часто такое случается? |

**Что фиксируем по каждому интервью:** канал первого обращения, время до
принятой заявки, число повторных контактов, было ли непонимание зоны
ответственности, узнал ли житель статус без звонка.

### 3.3 Результаты интервью

Заполняется по мере проведения. Каждая строка — один респондент, без

| # | Тип дома / год | Что случилось | Первый канал | Время до принятой заявки | Повторные контакты | Непонятно, кто отвечает? | Главный барьер |
|---:|---|---|---|---|---|---|---|
| 1 | | | | | | | |
| 2 | | | | | | | |
| 3 | | | | | | | |
| 4 | | | | | | | |
| 5 | | | | | | | |

**Вывод по интервью:** заполняется после 5 интервью. Если барьер «кто

точку эффекта, а не подгонять выводы.

| Гипотеза | Значимость | Неопределённость | Проверяемость | Итог |
|---|---:|---:|---:|---:|
| **Бот по свободному описанию определяет адресата точнее меню категорий** | 3 | 3 | 3 | **27** |
| Вход по QR повышает долю завершивших сценарий | 2 | 2 | 1 | 4 |
| Дедупликация снижает нагрузку на АДС | 2 | 2 | 2 | 8 |
| Проактивные уведомления уменьшают число звонков об отключениях | 2 | 1 | 1 | 2 |

**Ключевая гипотеза:**

> Если мы поможем **жителю дома под управлением УК (старый фонд)** выполнить
> **сообщение об аварии своими словами** с помощью **бота в MAX, который
> определяет тип проблемы и зону ответственности по нормативам**, то **доля
> правильно направленных заявок** станет **выше, а время до зафиксированной
> заявки — короче**, потому что **житель больше не выбирает адресата сам:
> форма с категориями требует знания, которого у него нет, а бот берёт это
> решение на себя и объясняет его нормой**.

| Проверка гипотезы | Ответ |
|---|---|
| **Пользователь** | Собственник или наниматель в доме под УК, постройка 1957–2000-х |
| **Изменение** | Правильный адресат с первого раза вместо самостоятельного выбора |
| **Обоснование** | Формы требуют выбрать категорию и адресата; значительная часть жителей не знает даже свою УК; граница ответственности неочевидна и спорна |
| **Проверяемость** | Точность по двум осям на 40–60 реальных описаниях против двух baseline (меню категорий, ключевые слова) и против деградации без LLM — подробно в [architecture.md §13](./architecture.md) |

# CREATE — собрать решение

## 6. Будущая демонстрация до разработки

| Вопрос | Ответ |
|---|---|
| **1. Кто?** | Житель квартиры в панельном доме 1970-х под управлением УК |
| **2. С чем?** | У него течёт из стены за ванной, и он не знает, кому звонить |
| **3. Что делает?** | Сканирует QR на стенде в подъезде → подтверждает свой адрес и даёт согласие → пишет одно сообщение: «из стены за ванной сифонит вода» → при необходимости отвечает на один уточняющий вопрос кнопкой |
| **4. Что делает продукт?** | Привязывает дом по QR; определяет тип проблемы и зону ответственности по нормативам; находит адресата по дому; проверяет, нет ли уже открытой заявки о том же; создаёт заявку со сроком по нормативу |
| **5. Что получает?** | Номер заявки, адресата с рабочим контактом, нормативный срок устранения и ссылку на норму, объясняющую, почему отвечает именно эта организация; статус по запросу в любой момент |

**Сценарий демо на защите (≈2 минуты):**

1. QR тестового дома → бот открыт, адрес распознан, согласие — две кнопки.
2. «Второй день из стены за ванной сифонит» → мгновенное «принял» → заявка
   с номером, УК как адресат, срок и ссылка на ПП №491.
3. Сосед из того же дома пишет «течёт по стене в ванной» → присоединение
   к той же заявке, а не новая.
4. Запрос статуса по номеру; служебная смена статуса → уведомление обоим.
5. Слайд с таблицей точности: меню / ключевые слова / наш бот / без LLM.

## 7. Идеи решений и выбор

| Идея | Что даёт | Почему отклонена или принята |
|---|---|---|
| Справочник контактов АДС в боте | Номер под рукой | Не снимает главный барьер — «кому звонить»; справочник гниёт |
| Бот с меню категорий | Просто сделать | Повторяет формы ГИС ЖКХ / Госуслуги.Дом; не ложится на свободное описание |
| Агрегатор отключений | Предупреждения | Канал уже закрывает государство (приказ №856/пр); нет своего отличия |
| Модератор домового чата | Порядок в обсуждениях | Далеко от аварийного сценария, сложно измерить эффект |
| **Бот, определяющий адресата по свободному описанию** | Закрывает «кому» | **Принята**: единственный пробел, не закрытый ни одним сервисом; эффект измерим |

**Изюминки решения:**

- **«Кому», а не «как»** — бот определяет адресата и объясняет решение нормой.
- **Честное «не уверен»** — при низкой уверенности бот не выдумывает,
  а передаёт заявку диспетчеру с пометкой.
- **Одна заявка на одну аварию** — сорок сообщений соседей о прорыве стояка
  становятся одной заявкой с сорока подписчиками.
- **Вход без адреса** — QR на стенде подъезда привязывает дом сразу.

# IMPACT — показать эффект

## 9. Три уровня эффекта

| Уровень | Формулировка | Чем доказываем | Где |
|---|---|---|---|
| **1. Результат пользователя** | «Я сообщил об аварии одним сообщением и сразу узнал, кто её устранит и в какой срок» | Прохождение сценария вживую | MVP, демо |
| **2. Наблюдаемое изменение** | «Вместо поиска контакта, дозвона и угадывания адресата — одно сообщение и правильный адресат с первого раза» | Точность маршрутизации против baseline на тестовом наборе; время от первого сообщения до заявки с номером на тестовом прохождении. Время As Is — из интервью | Тестовое прохождение, EVAL-002 |
| **3. Долгосрочный эффект** | «Меньше заявок уходит не по адресу, меньше повторных звонков в АДС и жалоб в ГЖИ» | Остаётся гипотезой; проверяется в пилоте | Пилот |

Уровни не смешиваем: на защите показываем уровни 1 и 2 как проверенные,
уровень 3 — как гипотезу пилота с метриками.

## 10. Метрики

| Метрика | Уровень | Как измеряем |
|---|---|---|
| Точность определения зоны ответственности и типа проблемы | 2 | Тестовый набор, четыре режима, раздельно по осям и по сложным случаям |
| Время до зафиксированной заявки | 2 | Тестовое прохождение против времени As Is из интервью |
| Доля корректно схлопнутых дублей и доля ложных склеек | 2 | Набор групп описаний одной аварии |
| Доля обращений пилотных домов через бота | 3 | Пилот: бот / (бот + звонки) за период |
| Повторные обращения по одной проблеме | 3 | Пилот: сравнение с периодом до запуска |

## 11. Масштабирование и пилот

- **Пилот:** 1–2 дома старого фонда под управлением УК в Казани; доступ —
  QR на стендах и в квитанциях.
- **Единица тиража** — одна УК; чек-лист подключения из 8 шагов и риски —
  [idea_and_scope.md, шаг 6](./idea_and_scope.md).
- **Порядок тиража:** Казань → районы Татарстана из того же обзвона
  Минстроя → регионы с большой долей старого фонда под УК.
