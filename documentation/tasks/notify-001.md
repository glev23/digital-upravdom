## Цель

Житель узнаёт о плановом отключении заранее, а об аварийном — сразу,
сообщением в MAX, не заходя в ГИС ЖКХ или на Госуслуги. Это ответ на
As Is п. 6 («открыл кран — а воды нет, потому что уведомление лежало в
личном кабинете, куда он не заходил»). Каждая доставка учитывается в
`notification_deliveries`, повторная отправка одному жителю исключена,
неудачная — повторяется.

## Scope

### Входит

- модуль `src/upravdom/notifications/` (пакет есть, пустой): выбор
  получателей, постановка доставок, рассылка;
- задача планировщика APScheduler, которая периодически рассылает
  неотправленные уведомления;
- учёт доставки (`notification_deliveries`) и связь с результатом
  реальной отправки в MAX;
- текст уведомления из структурированных полей;
- служебный CLI для создания уведомления и завершения аварии.

### Не входит

- реальная интеграция с РСО/ГИС ЖКХ — источник данных в MVP только
  смоделированные записи (§5.3, ограничение №10);
- подписка/отписка жителя от уведомлений — follow-up;
- ответ «об аварии уже известно» на жалобу по тому же ресурсу во время
  действующего аварийного отключения — follow-up (хорошее продолжение
  DEDUP-001);
- HTTP API для УК — по architecture.md §8 не объявляется.

## Технические требования

**Кому.** Жителям, у которых дом уведомления есть среди привязанных
(`user_houses`, любой — основной и дополнительные), **и** есть действующее
согласие на ПДн актуальной версии (`onboarding.service.has_valid_consent`).
Без согласия бот жителю не пишет ничего (§11.1).

**Когда.**

| Тип | Условие отправки |
|---|---|
| `emergency_outage` | сразу, пока отключение действует (`ends_at IS NULL` или `ends_at > now`) |
| `planned_outage` | начиная с момента появления записи и до `starts_at` (заранее — смысл уведомления); после начала отключения — не отправляется новым получателям |

Уведомления, у которых `ends_at` в прошлом, не рассылаются никогда.
Житель, привязавший дом во время действующего аварийного отключения,
получает уведомление при следующем проходе задачи — это нормально.

**Идемпотентность.** Уникальность `(notification_id, user_id)` в
`notification_deliveries` — миграция `0008` (сейчас ограничения нет). Вставка
доставки через `INSERT … ON CONFLICT DO NOTHING`: повторный проход задачи,
рестарт приложения или ретрай воркера не шлют жителю второе сообщение.
**Не полагаться на проверку «есть ли уже запись» перед вставкой** — гонка
между проверкой и вставкой (приём, уже используемый в inbox, BOT-001).

**Статус доставки должен отражать реальную отправку**, а не постановку в
очередь. Доставка создаётся в `pending`, в payload исходящего сообщения
кладётся `notification_delivery_id`; `outbox.send_claimed` после успешной
отправки переводит доставку в `sent` (`sent_at`), после исчерпания
попыток — в `failed` (`error` — тип ошибки, без текста). Повторы
неудачных отправок уже делает `outbox` (экспоненциальная задержка,
BOT-001) — свой второй механизм повторов не нужен.

**Адресация.** В `users` нет `chat_id` диалога — только `max_user_id`, а
для диалога с ботом `chat_id` ≠ `user_id`. Отправка — по `user_id`
(`POST /messages?user_id=…`, max_api.md §7); механизм делается в
STATUS-001 — переиспользовать, не дублировать.

**Задача планировщика.** В `scheduler.py:create_scheduler` — новая
задача `notify_worker` с интервалом `NOTIFY_POLL_INTERVAL_SECONDS`
(стартово 60), `max_instances=1`, `coalesce=True` — как у существующих.
Проход: выбрать действующие уведомления → для каждого получателя без
доставки вставить доставку и поставить сообщение в `outbox` → commit.
Одна транзакция на уведомление: сбой на одном не блокирует остальные.
Размер прохода ограничен (`NOTIFY_BATCH_SIZE`, стартово 200 доставок),
чтобы большой дом не держал воркер. Новые переменные — в `config.py`,
`.env.example` и architecture.md §12 одновременно.

**Текст уведомления** — из полей, а не только из свободного `message`:
«Аварийное отключение: электроснабжение, ваш дом <адрес>. Начало —
22.09 14:30. <message>» / «Плановое отключение: холодная вода, <адрес>,
24.09 09:00 — 24.09 17:00. <message>». Время — в `DISPLAY_TIMEZONE`.
Если уведомление пришло от смоделированных данных (`source = test_data`)
— в конце пометка «(тестовые данные)»: ограничение №10 кейса требует
явно обозначать смоделированное. Тексты — `notifications/texts.py`.

**Наблюдение по демо-данным.** `scripts/seed_demo.py` пересоздаёт два
тестовых уведомления **на каждом старте контейнера** со временем
относительно «сейчас» и `ON CONFLICT DO UPDATE`: завершённая через CLI
авария (`ends_at`) при рестарте снова станет действующей, а текст
планового («2 дня с 09:00 до 17:00») не совпадает с реальными
`starts_at`/`ends_at`. Исправить: сид не перезаписывает `ends_at` и
`starts_at` существующих записей (`ON CONFLICT DO NOTHING` для
уведомлений), текст планового — без конкретного времени (время теперь
берётся из полей). Идемпотентность `seed_demo` при этом должна остаться
(тест DATA-001).

**Служебный CLI** — `scripts/notify.py`:

- `create --house <house_id|токен deep-link> --type planned|emergency
  --resource hot_water --starts "2026-09-24 09:00" [--ends …] --message "…"`
  — `source = manual`;
- `close <notification_id>` — проставить `ends_at = now` у аварийного;
- `list` — действующие уведомления и число доставок `sent/pending/failed`.

Не HTTP (architecture.md §8). Если скрипт нужен внутри контейнера
(`docker compose exec app`) — добавить в `COPY` `docker/app.Dockerfile`.

## Сценарии

| # | Ситуация | Ожидаемое |
|---|---|---|
| 1 | Аварийное отключение по дому, 2 жителя с согласием | Каждый получает одно сообщение, 2 доставки `sent` |
| 2 | Повторный проход задачи / рестарт | Повторных сообщений нет |
| 3 | Житель без согласия (или отозвал) | Сообщения нет, доставки нет |
| 4 | Житель привязал дом во время аварии | Получает при следующем проходе |
| 5 | Плановое, `starts_at` через 2 дня | Сообщение уходит сейчас |
| 6 | Плановое уже началось | Новым получателям не отправляется |
| 7 | `ends_at` в прошлом | Не отправляется |
| 8 | MAX временно недоступен | Доставка `pending` → после повтора `sent`; после исчерпания попыток — `failed` |
| 9 | Уведомление по второму (не основному) дому жителя | Приходит |
| 10 | `notify.py close` + рестарт контейнера | Авария остаётся завершённой |

- **Отклонения от постановки:**
  1. **Получатели и доставки создаются одним SQL-запросом**
     (`INSERT … SELECT … ON CONFLICT DO NOTHING RETURNING`), а не «выбрать
     получателей → вставить доставки». Так между выбором и вставкой нечему
     вклиниться, и в постановке требовалось именно это поведение; `NOT EXISTS`
     внутри — только чтобы batch не выбирался уже разосланными.
  2. **`list_active` возвращает уведомления, а рассылку по каждому делает
     `dispatch`** — разделение нужно, чтобы воркер мог открыть свою
     транзакцию на каждое уведомление (требование «сбой на одном не
     блокирует остальные»).
  3. **`error` доставки — тип исключения** (`MaxPermanentError`), а не текст:
     в сообщении внешнего сервиса может оказаться что угодно
     (architecture.md §11). В `outbound_messages.last_error` текст остаётся,
     как было.
  4. **CLI `create` принимает и UUID дома, и токен deep-link.** С демо-стенда
     под рукой именно токен, а не UUID.
  5. **Время в `--starts`/`--ends` — местное** (`DISPLAY_TIMEZONE`), не UTC:
     диспетчер вводит то время, которое называет жителю.
  6. **Текст планового уведомления в сиде изменён** («Профилактические работы
     на сетях» вместо «2 дня с 09:00 до 17:00»): конкретное время теперь
     берётся из полей и с прошитой строкой расходилось.
  7. **В тестах `_deliveries` читает с `populate_existing=True`**: статус
     доставки меняет `send_claimed` сырым SQL, и объекты в identity map
     остались бы со старым значением — тест проходил бы по стале́й копии.
