# ONBOARD-002 — Запасной путь: поиск дома по адресу

| Поле | Значение |
|---|---|
| ID | `ONBOARD-002` |
| Статус | `done` |
| Требования | architecture.md §7.1 («Запасной путь», «Если дом не найден»), §10 (строки «deep-link неизвестен», «дом не найден»); кейс — критерий UX («без тупиков») |
| Зависимости | ONBOARD-001 |
| Блокирует | FLOW-001 (полнота онбординга), QA-001 |

## Цель

Житель, пришедший без ссылки дома (по нику бота, из поиска, по
пересланной ссылке, с отозванным токеном или нажавший «Это не мой дом»),
находит свой дом, написав адрес текстом и выбрав вариант кнопкой. Если дом
не подключён — получает честный ответ, общий контакт и возможность
оставить адрес, а не тупик. Кейс оценивает UX именно по отсутствию
тупиков; основной путь (deep-link) закрывает большинство, но не всех.

## Scope

### Входит

- точки входа — все места, где ONBOARD-001 сейчас отвечает «перейдите по
  ссылке своего дома»: `bot_started` без `payload` / с неизвестным или
  отозванным токеном, кнопка «Это не мой дом», сообщение жителя без
  привязанного дома;
- поиск дома по свободному вводу адреса среди `houses`, до 5 вариантов
  кнопками + кнопка «Моего дома нет в списке»;
- выбор варианта → **тот же** шаг согласия, что в ONBOARD-001 (адрес +
  текст + кнопки), `consents.source = "address_search"`;
- ветка «дом не найден»: честное сообщение, общий контакт, кнопка
  «Оставить адрес» → запись в новую таблицу заявок на подключение;
- повторная попытка ввода без перезапуска диалога.

### Не входит

- интеграция с ФИАС/ГАР или DaData — `fias_id` в демо-данных пуст, а
  внешняя зависимость в онбординге — лишняя точка отказа для MVP; путь
  масштабирования (architecture.md §16) — сопоставление с ФИАС при
  онбординге УК, а не у жителя;
- геолокация (`request_geo_location`) — Could Have, отдельная задача при
  необходимости;
- рабочее место для разбора заявок на подключение — только запись в БД и
  выборка скриптом.

## Технические требования

**Режим «жду адрес» — без таблицы состояний.** Житель без привязанного
дома не может сделать в боте ничего, кроме как найти дом, поэтому любой
текст от него трактуется как ввод адреса. Это снимает необходимость
хранить диалоговое состояние. Исключение — служебные команды (`/revoke`,
`/start`), они обрабатываются как обычно.

**Согласие и ввод адреса.** Адрес дома (без номера квартиры) до согласия
используется только для поиска и нигде не сохраняется — поиск не является
обработкой содержательного обращения (§11.1). Сохранение адреса в ветке
«не найден» — только по явной кнопке «Оставить адрес» с короткой
пометкой, что и зачем сохраняется.

**Нормализация адреса** (`onboarding/address.py`, чистая функция):
нижний регистр, `ё → е`, удаление города/региона («г.», «Казань»),
раскрытие и удаление типов («ул.», «улица», «пр-т», «проспект», «д.»,
«дом», «к.», «корп.»), пунктуация → пробел, схлопывание пробелов.
Выделяется **номер дома с литерой/корпусом** (`10`, `10а`, `10 к2`) и
**остаток — название улицы**.

**Сопоставление.**

- номер дома должен совпасть **точно** (после нормализации). Ул.
  Декабристов, 10 и 12 — разные дома с разными адресатами; нечёткое
  совпадение номера отправило бы заявку в чужую УК — ровно то, от чего
  защищает обязательный показ распознанного адреса;
- улица — нечётко: `difflib.SequenceMatcher` (stdlib, без новой
  зависимости) по нормализованному названию, порог стартово `0.75`,
  проверяется тестами на опечатках («Декабрисов», «лумумба» vs «Патриса
  Лумумбы» — частичное совпадение по токенам тоже должно находить);
- поиск в пределах `houses` целиком: на демо-объёме (единицы–сотни домов
  на УК) это миллисекунды. Порог масштабирования и замена на `pg_trgm`
  с индексом по нормализованному адресу — фиксируется в закрытии как
  шаг лестницы, не делается сейчас.

**Кнопки выбора.** `payload` — `onb:pick:<house_id>`. Выбор снова
разрешается через БД (дом мог быть удалён); дальше — общий с ONBOARD-001
путь показа адреса и согласия, без дублирования кода.

**Дом не найден.** Сообщение: «Этот дом пока не подключён к боту» + общий
контакт + кнопки «Ввести адрес ещё раз» и «Оставить адрес». Общий контакт
— параметр окружения `FALLBACK_CONTACT_TEXT` (по умолчанию — единый номер
экстренных служб 112 для аварий, опасных для жизни, и совет обратиться в
свою УК по квитанции); добавляется в `.env.example` и architecture.md §12
одновременно (правило синхронизации §12).

**Заявки на подключение дома** — новая таблица `house_requests`: `id`,
`user_id` (FK), `address_text`, `created_at`, `status` (`new` /
`connected` / `rejected`). Обращение не теряется (architecture.md §7.1:
«обращение сохраняется»), а для питча масштабирования это ещё и сигнал
спроса — какие дома хотят подключения. Миграция `0004`; в перечень таблиц
architecture.md §5.7 — одновременно.

**Защита от перебора.** Поиск доступен и без согласия, поэтому через него
можно выяснять, какие дома подключены. Ответ показывает только адреса
домов (публичная информация, её и так печатают на стендах) и подпадает
под общий лимит частоты сообщений (BOT-001) — дополнительных мер не
требуется, решение фиксируется явно.

## Сценарии

| # | Ввод | Ожидаемое поведение |
|---|---|---|
| 1 | «Декабристов 10» | 1 вариант кнопкой → выбор → шаг согласия с этим адресом |
| 2 | «г. Казань, ул. Декабристов, д. 10» | То же, что п.1 |
| 3 | «декабрисов 10» (опечатка) | Находит |
| 4 | «Лумумбы 5» | Находит «ул. Патриса Лумумбы, д. 5» |
| 5 | «Декабристов 12» | Не находит (номер не совпал) → ветка «не найден» |
| 6 | «Пушкина 1» | Ветка «не найден», кнопки повтора и «Оставить адрес» |
| 7 | «Оставить адрес» | Запись в `house_requests`, подтверждение жителю |
| 8 | Мусор («привет», пустая строка, эмодзи) | Просьба указать улицу и номер дома, пример формата |
| 9 | Приход без `payload` | Приглашение ввести адрес вместо ошибки |
| 10 | «Это не мой дом» из ONBOARD-001 | Приглашение ввести адрес |
| 11 | Несколько совпадений | До 5 кнопок + «Моего дома нет в списке» |
