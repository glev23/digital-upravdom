# SPIKE-001 — Рантайм эмбеддингов и бюджет сборки ≤5 минут

| Поле | Значение |
|---|---|
| ID | `SPIKE-001` |
| Статус | `done` |
| Требования | architecture.md §2, §12, §15 (риск «Бюджет сборки ≤5 минут»); кейс — «Формат сдачи», п. 5 |
| Зависимости | INIT-001 |
| Блокирует | KB-001, CLASSIFY-001 |

## Цель

До написания кода, зависящего от эмбеддингов, измерить, укладывается ли
холодная сборка образа с моделью `sergeyzh/BERTA` в 5 минут, и выбрать рантайм
инференса. Результат — решение, записанное в architecture.md, и готовый слой
Dockerfile, а не только цифра.

Это задача-исследование: выбор между `torch` и ONNX Runtime меняет состав
зависимостей и код модуля эмбеддингов, поэтому его нельзя откладывать до
сборки перед сдачей.

## Scope

### Входит

- замер холодной сборки для двух вариантов:
  - **A:** `sentence-transformers` + CPU-сборка `torch` (текущий вариант
    architecture.md §2);
  - **B:** ONNX Runtime + экспортированная в ONNX модель BERTA + токенизатор
    без `torch`;
- для каждого варианта: время сборки, размер образа, время загрузки модели при
  старте, задержка эмбеддинга короткого сообщения на CPU;
- для варианта B: проверка, что векторы совпадают с вариантом A (косинусная
  близость на наборе фраз);
- проверка лицензий зависимостей выбранного варианта;
- решение и его запись в architecture.md (§2, §12, «История решений»);
- слой Dockerfile для выбранного варианта с кэшированием весов модели
  отдельным слоем.

### Не входит

- база знаний, чанкинг, загрузка в Qdrant (KB-001);
- классификация и семантический кэш (CLASSIFY-001, CLASSIFY-002);
- смена модели эмбеддингов — только если оба варианта не укладываются
  в бюджет (тогда это отдельное решение с пересчётом, а не молчаливая замена);
- GPU-сборки в любом виде.

## Технические требования

- **Условия замера — как у проверяющего.** Базовый образ `python:3.12-slim`
  скачан заранее (кейс исключает его из бюджета), кэш сборки очищен,
  `--no-cache`. Всё, что скачивается во время сборки (колёса, веса модели),
  в бюджет **входит**.
- **Запас.** Целевое время — не больше 3,5 минуты на машине команды: машина
  и сеть проверяющего могут быть медленнее. Вариант, который проходит
  «впритык» к 5 минутам, считается не прошедшим.
- **Замер повторяется трижды**, фиксируется худший результат.
- **Совпадение векторов (вариант B).** На 50 фразах из тематики проекта
  средняя косинусная близость с вариантом A — не ниже 0.99. Если ниже —
  вариант B меняет поведение классификатора и требует отдельного решения.
- **Задержка эмбеддинга** короткого сообщения (до 50 слов) на CPU — не выше
  200 мс в среднем; иначе эмбеддинг становится узким местом вопреки
  architecture.md §14.
- Готовая ONNX-версия BERTA может отсутствовать в открытом доступе — тогда
  экспорт выполняется командой самостоятельно, а скрипт экспорта кладётся
  в репозиторий, чтобы результат был воспроизводим. Скачивать сторонние
  неофициальные ONNX-сборки модели нельзя (ограничение №7 кейса о чужом коде).
- Результаты сравнения — таблицей в результате закрытия и в architecture.md.


совпадение векторов» и однозначный выбор.

## Результат закрытия

Закрыто 21.09.2026; multi-stage замер дозаписан **22.09.2026**.

| Вариант | Холодная сборка | Сеть на веса модели | Задержка/фраза | Cosine vs эталон |
|---|---|---|---|---|
| A — torch CPU + sentence-transformers, всё в одном стейдже | 194 с | ~1 ГБ (torch + веса) | 5.4 мс | — (эталон) |
| B′ — ONNX из git (модель закоммичена) | 55 с | нет (COPY из контекста) | 3.7–13 мс | ~1.0 |
| **B — ONNX multi-stage (актуальный)** | **187 с** (`real 3m7.5s`) | HF BERTA + torch CPU только в exporter | 3.7–13 мс | ~1.0 |

**Решение: вариант B (multi-stage).** Изначально ONNX-модель (490 МБ)
планировалось коммитить в `data/model/berta-onnx/` — единичный прогон дал
55 с. **Это было ошибкой**: 490 МБ > лимита GitHub 100 МБ/файл без LFS.
Переделано на **multi-stage Docker**: стейдж `exporter` ставит torch/optimum,
экспортирует модель (`scripts/export_onnx.py`) и отбрасывается; в финальный
образ копируется только результат — рантайм torch не видит. Модель не
коммитится. `data/model/` — в `.gitignore`, для локального venv — тот же
скрипт экспорта.

**Холодный замер multi-stage (22.09.2026), машина команды:**

```text
docker pull python:3.12-slim   # вне бюджета
docker builder prune -af
time docker compose build --no-cache app
→ real 3m7.517s  (compose: 187.3s)
```

Разбивка ключевых шагов exporter:
- `uv sync --group embedding-export` — ~74 с (`torch==2.14.0+cpu`, без CUDA);
- `python scripts/export_onnx.py` (скачивание BERTA + экспорт ONNX) — ~88 с;
- base + export image — остаток.

Укладывается в запас SPIKE ≤3,5 мин (210 с) и в лимит кейса ≤5 мин. Запас
до 3,5 мин тонкий (~23 с) — на медленной сети проверяющего риск выше;
квантизация / кэш HF в образе не делались.

**Исправление локера (22.09.2026):** `torch` сделан прямой зависимостью
группы `embedding-export` + `[tool.uv.sources]` → индекс
`https://download.pytorch.org/whl/cpu`. До этого транзитивный torch из
PyPI тянул CUDA (`nvidia-*`, `triton`, ~2+ ГБ) и ломал бюджет/RAM.

Важный найденный факт: BERTA — инструктивная модель, нужен префикс-промпт
перед текстом (без него cosine падал до ~0.73). Для SPIKE-001 использован
дефолтный промпт модели; какой промпт брать для retrieval в CLASSIFY-001
(`search_query:`/`search_document:` — асимметричная пара) — открытый вопрос
для той задачи, не для этой.

Изменённые артефакты: `src/upravdom/embeddings.py`,
`scripts/export_onnx.py`, `scripts/spike_embeddings.py`,
`docker/app.Dockerfile`, `pyproject.toml` / `uv.lock` (onnxruntime в
рантайме; torch CPU только в `embedding-export`), `.dockerignore`,
`tests/unit/test_embeddings.py`, `documentation/architecture.md` §2.

Follow-up: KB-001 выбирает промпт для retrieval; при провале бюджета у
проверяющего — квантизация ONNX или предварительный кэш весов HF в слое.
