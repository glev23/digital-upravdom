| Поле | Значение |

| Статус | `done` |

## Цель

Житель после онбординга пишет о проблеме своими словами и в том же
диалоге получает: мгновенное «принял», затем — кто отвечает и по какой
норме, номер заявки, срок и телефон аварийной службы; при сомнении — один
уточняющий вопрос кнопками; в любой момент — статус своих заявок. Это
пункт «Допуска» кейса: без полностью проходимого в MAX основного
сценария решение не оценивается. Заглушка `acknowledge_receipt` из
BOT-001 уходит.

## Scope

### Входит

- модуль `src/upravdom/flow/`: обработчик содержательного сообщения за
  шлюзом онбординга, обработчик кнопок уточнения и статуса, тексты;
- мгновенное подтверждение приёма до классификации;
- ответы по трём веткам и по зонам ответственности;
- уточняющий вопрос кнопками и повторная классификация;
- запрос статуса: команда, текст, кнопка, номер;
- проверка сценария вживую в MAX на VM.

### Не входит

- кэш и деградация без LLM — CLASSIFY-002 (FLOW-001 работает с тем, что
  возвращает `classify()`, включая `fallback_used`);
- присоединение к существующей заявке — DEDUP-001;
- уведомления подписчиков о смене статуса — STATUS-001;
- ответы на вопросы о правах — RIGHTS-001;
- фото к заявке — PHOTO-001.

## Технические требования

**Мгновенное подтверждение (§3, п. 4).** Классификация занимает секунды
(LLM ~2–8 с), и отправленное в той же транзакции подтверждение пришло бы
одновременно с ответом — то есть не было бы «мгновенным». Поэтому
обработчик ставит в очередь подтверждение и **коммитит его отдельно**, до
классификации. Повторная попытка того же события (ретрай воркера) второе
подтверждение не шлёт — условие `event.attempts == 1`. Текст не обещает
лишнего: «Принял, определяю, кто отвечает» — без слова «заявка», её ещё
нет. Команда статуса распознаётся **до** подтверждения (исправлено после
ревью: на «статус» подтверждение про определение ответственного неверно).

**Ответ по веткам и зонам.**

| Решение | Заявка | Ответ жителю |
|---|---|---|
| `auto`, зона `uk` / `rso` | Создаётся (TICKET-001) | «Заявка № N принята. Отвечает: <организация>. Аварийная служба: <телефон>». Допустимый перерыв по нормативу — до <дата, время> (<норма>). Для аварий внутридомовых систем УК — сроки АДС по ПП №416 п. 13. «Основание: <полная ссылка на пункт> — <начало текста пункта>». Кнопка «Статус заявки» |
| `auto`, зона `owner` | Не создаётся | Почему это зона собственника — с пунктом нормы (граница «первое отключающее устройство»); контакт АДС УК, если нужен платный вызов или авария затрагивает соседей |
| `auto`, зона `municipality` | Не создаётся | Почему это не УК — с нормой; общий контакт (`FALLBACK_CONTACT_TEXT`) |
| `clarify` | Не создаётся до ответа | Вопрос + 2–4 кнопки вариантов + кнопка «Не знаю» |
| `unknown` (в т. ч. `fallback_used`) | Создаётся, зона `unknown`, статус `needs_dispatcher` | Честно: «Не берусь точно определить ответственного — передал заявку № N диспетчеру вашей УК» + телефон АДС. Предположение модели не выдаётся за факт (требование кейса) |

Срок показывается в часовом поясе дома — `DISPLAY_TIMEZONE`
(по умолчанию `Europe/Moscow`, Казань), переменная в `config.py`,
`.env.example` и architecture.md §12. Если `due_at IS NULL` —
«нормативный срок для этого типа не установлен» + норма. Дом без УК
(адресат `None`) — ветка `unknown` с общим контактом.

**Срок называется честно** (исправлено после ревью). В
`problem_types.resolution_hours` — допустимая продолжительность перерыва
(прил. 1 ПП №354), а не срок устранения. Жителю — «Допустимый перерыв по
нормативу — до …»; для аварий внутридомовых систем ХВС, ГВС,
водоотведения, отопления и электроснабжения в зоне УК дополнительно
строка про сроки АДС из ПП №416, п. 13 (локализация — полчаса, устранение
— до 3 суток; официальный текст, KB-001). Из `norm_reference` жителю
показывается только ссылка на акт: остальное там — служебные пояснения
справочника.

**Основание в ответе** — полная ссылка подтверждённого фрагмента
(«ПП РФ №491, п. 5 абз. 1», первая строка фрагмента KB) и начало текста
пункта, **не** генерация LLM. Бот показывает жителю норму, а не пересказ
модели.

**Уточнение — без отдельной таблицы состояний.** Вопрос и варианты
сохраняются в строке журнала первого прохода — nullable колонка
`classification_logs.clarification` (JSON: `question`, `options`),
миграция `0006`. Кнопки несут только `clf:ans:<log_id>:<номер варианта>`
(и `clf:none:<log_id>` для «Не знаю»): текст вопроса в payload не
кладётся — кириллица в payload кнопки быстро упирается в лимит (урок
ONBOARD-002 с длинным адресом). По нажатию: вопрос и выбранный вариант —
из журнала, исходный текст — из `inbound_events.payload` по
`classification_logs.inbound_event_id` (внутреннее хранение, как
`tickets.raw_text`), второй проход `classify(..., clarification=…)`.
Нажатие проверяет, что запись журнала относится к событию этого же жителя
(`inbound_events.max_user_id`) — чужую кнопку не подделать подстановкой
`log_id`. После уточнения ветка `clarify` невозможна (CLASSIFY-001) —
только `auto` или `unknown`. «Не знаю» → сразу `unknown`. Повторное
нажатие не создаёт вторую заявку — идемпотентность по `source_event_id`
(TICKET-001).

**Статус.** Команды `/status`, «статус», «моя заявка», кнопка «Статус
заявки» → список до 5 заявок жителя (открытые первыми): номер, статус,
адресат. «статус 1024» / «/status 1024» → одна заявка по номеру с
проверкой доступа (TICKET-001); чужой и несуществующий номер — одно и то
же «заявка не найдена среди ваших». Команды распознаются **до**
классификации: «статус» — не жалоба, в LLM не уходит.

**Кнопки и ответы на нажатия** — через `outbox` (`inline_keyboard`,
`POST /answers`, ONBOARD-001). Прямая отправка из обработчика запрещена
(§7).

**Нагрузка.** Воркер обрабатывает события последовательно
(`max_instances=1`), и сообщение с вызовом LLM занимает его на секунды.
Для MVP это допустимо (architecture.md §14) — фиксируется замером;
параллельная обработка — не в этой задаче.

**Тексты** — `flow/texts.py`, как в онбординге.

| # | Действие | Ожидаемое |
