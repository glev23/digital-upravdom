## Цель

README, по которому проверяющий поднимает решение с нуля, проходит основной
сценарий и понимает границы: все обязательные разделы формата сдачи на месте,
каждая команда реально выполнена, каждое число — измерено, а не оценено.

## Scope

### Входит

- все разделы формата сдачи: назначение, сценарий, состав и архитектура, одна
  команда запуска через Docker, необходимые параметры окружения, переменные
  окружения, порты, зависимости, внешние сервисы, работа с данными, порядок
  работы с тестовыми данными, пошаговый сценарий проверки, примеры ожидаемого
  поведения, известные ограничения, порядок остановки и повторного запуска;
- замер холодной сборки образа;
- актуализация `scripts/README.md` (он описывал состояние до половины задач).

### Не входит

- презентация (PRES-001) и чек-лист сдачи (SUBMIT-001);
- перепроверка фактов о проблеме по первоисточникам (RESEARCH-001) — в README
  вынесена одна цифра ВЦИОМ, уже проверенная лично.

## Критерии приёмки

- [x] Присутствуют все обязательные разделы формата сдачи.
- [x] Каждая команда из README выполнена, вывод сверен.
- [x] Время холодной сборки измерено и укладывается в бюджет ≤5 минут.
- [x] Примеры ожидаемого поведения — дословные ответы бота, а не пересказ.
- [x] Ограничения названы честно, включая неустойчивость модели.
- [x] `bash scripts/check.sh` проходит.

## Проверка

```bash
docker compose build --no-cache app     # замер холодной сборки
docker compose down -v                  # чистое состояние
docker compose up --build -d
curl http://localhost:8000/health
curl http://localhost:8000/ready
docker compose logs app | grep "start="
docker compose stop app && bash scripts/check.sh && docker compose start app
uv run pytest tests/integration/test_e2e_scenario.py -v
docker compose exec app python scripts/notify.py list
docker compose down && docker compose up -d
```

## Результат закрытия

**Закрыта 28.09.2026.** Все команды выполнены на чистом состоянии
(`docker compose down -v`), фактические результаты:

| Что | Результат |
|---|---|
| Холодная сборка `--no-cache` | **2 мин 46 с** (бюджет кейса ≤ 5 мин) |
| Старт с нуля до `/ready` | около 25 с, `load_kb OK count=44 docs=7` |
| `/health`, `/ready` | `{"status":"ok"}`, `{"status":"ok","postgres":true,"qdrant":true}` |
| `scripts/check.sh` | 573 теста, OK |
| Сквозной тест сценария | `test_full_scenario_twice_on_same_state` PASSED |
| `down` → `up -d` | данные на месте: 3 дома, 6 deep-link, 2 уведомления |

Что вскрылось по ходу и исправлено **в README, а не задним числом**:

- команда «показать deep-link» в первой редакции искала в логе
  `https://max.ru`, но при пустом `MAX_BOT_USERNAME` (а он пуст в
  `.env.example`) сид печатает только `start=<токен>` — собрать ссылку не из
  чего. Команда исправлена на `grep "start="` с объяснением;
- `ticket_status.py 1 in_progress` на чистой базе отвечает «заявка № 1 не
  найдена» — номер берётся из ответа бота, в README стоит `<номер>` и назван
  этот ответ;
- тесты ходят в **те же** Postgres и Qdrant, что и контейнер `app`, и
  пересоздают коллекцию базы знаний. Один из прогонов `check.sh` на
  работающем приложении завершился с нарушениями, тот же прогон при
  остановленном `app` — зелёный. В README добавлен порядок: `docker compose
  stop app` → проверка → `start app`. Конкретная упавшая проверка не
  зафиксирована — вывод не сохранился, поэтому в документации описан порядок
  запуска, а не механизм гонки.

**Follow-up:** причину гонки тестов с работающим приложением стоит найти и
либо изолировать тестовую БД, либо назвать явно (отдельная задача, на сдачу
не влияет — порядок запуска описан).
