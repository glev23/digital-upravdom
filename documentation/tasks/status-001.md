# STATUS-001 — Сквозной статус заявки и уведомление подписчиков

| Поле | Значение |
|---|---|
| ID | `STATUS-001` |
| Статус | `ready` |
| Исполнитель | dev-ilya (ветка `dev-ilya`) |
| Требования | architecture.md §5.2 (`ticket_events` append-only, `ticket_subscribers`), §7 (исходящие только через очередь), §6.5 (подписчики после склейки); idea_and_scope.md As Is п. 4 («заявка передана дальше — для жителя теряется»), To Be п. 3, MoSCoW (Should Have) |
| Зависимости | TICKET-001, FLOW-001 |
| Блокирует | PRES-001 (сценарий «статус не теряется при передаче») |

## Цель

Житель не звонит, чтобы узнать, что с заявкой: каждый переход статуса и
каждая передача между организациями («передано в РСО», «передано
подрядчику») приходят ему сообщением сами, а по номеру заявки видна
история переходов с датами. Это закрывает боль из As Is — «после передачи
в РСО заявка для жителя теряется» — и должно работать для **всех**
подписчиков заявки, включая присоединённых дедупликацией.

## Scope

### Входит

- уведомление всех подписчиков о смене статуса (`change_status`);
- переадресация заявки между организациями (`reroute`) с событием
  `routed` и уведомлением;
- история заявки по номеру: последние события с датами;
- расширение служебного CLI для демонстрации переходов и переадресации;
- тексты уведомлений.

### Не входит

- рабочее место диспетчера / HTTP API для смены статуса — нет по
  architecture.md §8 (объявленный API порождает обязательства сдачи);
- эскалация при просрочке срока (ГЖИ и т. п.) — follow-up;
- уведомления об отключениях — NOTIFY-001;
- отписка жителя от уведомлений по заявке — follow-up.

## Технические требования

**Уведомление о смене статуса.** В `tickets/service.py:change_status` —
после записи события `status_changed`, **в той же транзакции**, в очередь
`outbox` ставится сообщение каждому подписчику заявки
(`ticket_subscribers`). Почему в той же транзакции: статус без
уведомления или уведомление без статуса — рассинхрон, который житель
увидит («сказали, что выполнено, а в статусе — в работе»). Исходящие —
только через `outbox.enqueue_message` (§7), прямая отправка запрещена.

Кому отправлять:

- всем подписчикам заявки, у которых **действующее согласие** на ПДн
  актуальной версии (`onboarding.service.has_valid_consent`) — после
  отзыва согласия бот жителю больше не пишет;
- адрес отправки — `chat_id` диалога с жителем. В `users` хранится только
  `max_user_id`; для диалога с ботом `chat_id` ≠ `user_id`
  (подтверждено живым событием, фикстура `tests/fixtures/max/`). Отправка
  по `user_id` в MAX поддерживается (`POST /messages?user_id=…`,
  max_api.md §7), но в `outbox`/`HttpxMaxClient` сейчас только
  `chat_id` — **добавить адресацию по `user_id`** (payload `outbox`
  `{"user_id": …}` + параметр в `MaxClient.send_message`), а не угадывать
  `chat_id`. Альтернатива — сохранять `chat_id` у пользователя при каждом
  входящем событии; выбрать одно и записать решение в закрытие.

Текст: «Заявка № N: статус изменён — <новый статус>. <адресат, если
изменился>». Для `completed` — «Заявка № N выполнена. Если проблема не
решена — напишите, создам новую заявку.» Кнопка «Статус заявки».

**Переадресация** — `tickets/service.py:reroute(ticket, *, zone, org_id,
actor)`: меняет `routed_to_org_type`/`routed_to_org_id` (и
`responsibility_zone`, если зона другая), пересчитывает адресата через
`resolve_addressee` при переходе на РСО по ресурсу, пишет событие
`routed` с `payload = {"from": …, "to": …, "reason": …}` и уведомляет
подписчиков: «Заявка № N передана: <организация>, телефон <контакт>».
Статус при переадресации не меняется (переадресация и статус — разные
оси; «передано подрядчику» — это статус `routed_to_contractor`, а
«передано в РСО» — смена адресата). Закрытая заявка не переадресуется.

**История по номеру.** «статус 1024» (FLOW-001) дополнительно показывает
последние 5 событий заявки из `ticket_events` в хронологическом порядке:
«22.09 14:05 — принята (УК «…»)», «22.09 15:10 — передана в АО
«Водоканал»», «22.09 18:00 — выполнена». Время — в `DISPLAY_TIMEZONE`.
События `subscriber_joined`/`subscriber_left` жителю показываются
агрегированно («к заявке присоединились ещё 3 жителя»), без имён и
идентификаторов других людей.

**Служебный CLI.** `scripts/ticket_status.py` уже меняет статус — теперь
это приводит к уведомлениям. Добавить `scripts/ticket_reroute.py <номер>
--zone rso|uk [--org-id …]` для демонстрации переадресации. Новый скрипт
**не нужно** копировать в Docker-образ, если он запускается только
локально; если через `docker compose exec app` — добавить в `COPY`
`docker/app.Dockerfile` (урок DATA-001: скрипт не попал в образ, контейнер
падал).

**Тексты** — `tickets/texts.py`.

## Сценарии

| # | Действие | Ожидаемое |
|---|---|---|
| 1 | `ticket_status.py N in_progress` | Автор получает «статус — в работе» |
| 2 | У заявки 3 подписчика (после DEDUP-001) | Уведомление получают все трое |
| 3 | Один подписчик отозвал согласие | Ему уведомление не уходит, остальным — уходит |
| 4 | `ticket_reroute.py N --zone rso` | Событие `routed`, адресат — РСО по ресурсу дома, уведомление с контактом РСО |
| 5 | «статус N» | Статус + история последних 5 событий с датами |
| 6 | Запрещённый переход | Исключение, ни события, ни уведомления |
| 7 | Сбой посреди `change_status` | Откат: ни статуса, ни уведомления |
| 8 | `completed` | Текст с предложением написать снова |

- [ ] Сценарии 1–8 покрыты тестами и проходят.
