# DEPLOY-001 — Публичный HTTPS и живая проверка в MAX

| Поле | Значение |
|---|---|
| ID | `DEPLOY-001` |
| Статус | `done` |
| Требования | architecture.md §7, §12.1; кейс — «Допуск» п.2, «Ограничения» п.2 |
| Зависимости | INIT-001, MAX-001 |
| Блокирует | QA-001, SUBMIT-001, WEB-001 |

## Цель

Поднять решение на публичном HTTPS-адресе с доверенным сертификатом —
без этого MAX не примет вебхук (самоподписанные сертификаты отклоняются,
подтверждено MAX-001) и бот недоступен жюри (пункт 2 «Допуска» кейса — без
этого 0 баллов без оценки).

## Scope

### Входит

- отдельная конфигурация деплоя (не трогает корневой `compose.yaml` —
  он должен остаться чистым артефактом сдачи: `docker compose up` в
  корне репозитория, без флагов и посторонних сервисов);
- reverse proxy с автоматическим TLS (Let's Encrypt);
- публичный домен, указывающий на сервер;
- сборка и запуск полного стека на сервере;
- регистрация вебхука в MAX (`POST /subscriptions` на подтверждённый
  адрес, `max_api.md` §3);
- живая проверка: сообщение боту в MAX получает ответ в мобильной и
  веб-версии (перенесённый пункт из BOT-001 и MAX-001).

### Не входит

- сам сервер — используется существующая VM пользователя (общая с другими
  проектами, не создаётся заново);
- изменение корневого `compose.yaml`, `Dockerfile`, `.env.example`;
- домен на платной основе — используется бесплатный DuckDNS.

## Технические требования

- **Сервер общий с другими проектами.** Никаких изменений системных
  настроек хоста (`sudo`, `ufw`) — пароль от `sudo` недоступен и не
  запрашивался. Все порты, кроме 80/443 (заняты только под этот деплой),
  остаются нетронутыми.
- **Внутренние сервисы не публикуются на хост вообще** — строже, чем в
  дев-воркфлоу (architecture.md §12.1): на этой машине нет локальной
  разработки через venv, публиковать `postgres`/`qdrant` незачем даже на
  нестандартные порты. Единственная точка входа снаружи — reverse proxy.
- **Имя каталога на сервере — нейтральное** (`~/svc-app`, не
  «hakaton»/«upravdom») — по решению пользователя: машина используется
  для многих проектов, нейтральное имя не создаёт путаницы в списке.
  Публичный домен при этом — осмысленный, привязанный к продукту: это
  видно в презентации и коде проверки, а не только в списке папок на
  чужом сервере.
- **Домен — бесплатный DuckDNS**, не сервис вида `sslip.io`/`nip.io`
  (эти показывают IP прямо в имени — не подходит, если IP не должен быть
  виден напрямую). A-запись заводится пользователем в веб-интерфейсе
  DuckDNS вручную (создание аккаунта — действие пользователя, не
  агента, см. общие правила).
- **TLS** — Caddy 2, автоматический выпуск и продление сертификата,
  challenge — `tls-alpn-01` (порт 443, без необходимости в порту 80 для
  проверки, хотя оба свободны).
- **Секреты** — только через `.env` на сервере (передан по SSH, тому же
  каналу, что и код), не в командной строке, не в логах, не в git.

## Артефакты

| Артефакт | Назначение |
|---|---|
| `deploy/compose.vm.yaml` | Отдельный compose для VM-деплоя: без хостовых портов у postgres/qdrant/app, добавлен `caddy` |
| `deploy/Caddyfile` | Домен + `reverse_proxy app:8000`, автоматический TLS |
| `docker/certs/russian_trusted_root_ca.pem`, `russian_trusted_sub_ca.pem` | Публичные сертификаты Минцифры (не секреты) — без них `HttpxMaxClient` не проходит TLS к `platform-api2.max.ru` |

- [x] Стек собран и поднят на сервере (`docker compose -f deploy/compose.vm.yaml up -d --build`).

- [x] Публичный HTTPS-адрес отвечает `200` на `/health` и `/ready` без `--insecure` (сертификат проходит проверку доверия по умолчанию).
- [x] Секреты не встречались в командах и выводе.
- [x] Системные настройки хоста (`sudo`, firewall) не изменялись.
- [x] Вебхук зарегистрирован в MAX (`POST /subscriptions`, с подтверждения пользователя) — `update_types`: `message_created`, `bot_started`, `message_callback`; проверено `GET /subscriptions`.
- [x] Сообщение боту в MAX получает ответ — проверено 22.09.2026 пользователем: 2 сообщения, оба обработаны и получили ответ с первой попытки, 0 ошибок. Проверка именно в обеих версиях (мобильная/веб) осталась на усмотрение пользователя при следующем заходе — сам факт «бот отвечает в реальном MAX» подтверждён.

## Проверка

```bash
curl -s -w "\nHTTP %{http_code}\n" https://digital-upravdom.duckdns.org/health
curl -s -w "\nHTTP %{http_code}\n" https://digital-upravdom.duckdns.org/ready
```

Ожидаемо: `{"status":"ok"}` / `200`, затем `{"status":"ok","postgres":true,"qdrant":true}` / `200`.
