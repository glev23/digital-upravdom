# FLOW-005 — Роутинг намерения моделью, а не только шаблонами

| Поле | Значение |
|---|---|
| ID | `FLOW-005` |
| Статус | `done` |
| Требования | architecture.md §4, §6.2; критерий UX «нет тупиков и противоречивых переходов»; idea_and_scope.md шаг 4 |
| Зависимости | FLOW-002, FLOW-003, FLOW-004, CLASSIFY-001 |
| Блокирует | нет |

## Проблема

Слой интентов — закрытый список регулярных выражений, срабатывающих на
сообщении целиком. Формулировка, которой нет в списке, проваливается в
классификацию, не находит жилищного типа и **создаёт заявку диспетчеру**.

Живой прогон 28.09.2026, два случая подряд:

| Что написал житель | Что ожидал | Что получил |
|---|---|---|
| `какие заявки ещё есть в доме` | список обращений дома | заявка № 15 диспетчеру |
| `права за сколько часов приедет мастер` | справку по нормативу | заявка № 13 диспетчеру |

Второй случай закрыт правкой детектора прав (голое слово-команда и
необязательный знак вопроса). Первый шаблонами не лечится: «какие заявки в
доме» совпадает, «какие заявки **ещё есть** в доме» — нет, и таких вариантов
бесконечно много.

**Важно:** оба случая не теряют обращение — житель получает заявку, а не
тишину. Но это тупик по смыслу: он спросил, а ему завели заявку.

## Цель

Сообщение, которое не поймал быстрый шаблонный слой, разбирается моделью,
которую мы и так вызываем на этом шаге, — и попадает в нужную ветку вместо
заявки. Дополнительного вызова модели нет: расширяется схема существующего.

## Scope

### Входит

- поле `intent` в схеме ответа модели: `complaint` / `house_tickets` /
  `my_tickets` / `rights` / `other`;
- `PROMPT_VERSION` 4 → 5 и правила в промпте с примерами;
- ветка в `flow/handlers.py`: при `intent` ≠ `complaint` — соответствующий
  обработчик вместо создания заявки;
- для `rights` — вызов справки (второй вызов модели, только для этой ветки);
- тесты: формулировки, которые шаблоны не ловят, и контрольный список жалоб.

### Не входит

- замена шаблонного слоя: он остаётся впереди как быстрый и бесплатный путь;
- отказ от команды `/права`: она работает без внешней модели и остаётся
  страховкой на случай её недоступности (architecture.md §10);
- роутинг при недоступности модели: тогда поведение прежнее — шаблоны и
  заявка диспетчеру.

## Технические требования

**Условие несимметричное, как в FLOW-003.** Интент принимается, только если
модель одновременно не нашла конкретного жилищного типа
(`problem_type == "other"`). Иначе «какие заявки в доме, у меня опять течёт»
осталось бы без заявки. Потерять жалобу дороже, чем не распознать вопрос.

**Порядок остаётся прежним:** шаблоны → команда статуса → детектор прав →
подтверждение приёма → классификация → роутинг по `intent` → заявка.

**Журнал:** `intent` пишется в `classification_logs.reasoning`? Нет —
отдельного поля не заводим, миграции в этой задаче нет; факт срабатывания
виден по отсутствию заявки при `problem_type = other`.

## Критерии приёмки

- [x] «какие заявки ещё есть в доме», «а что там по дому», «о чём соседи
      писали» — список обращений, заявка не создаётся.
- [x] «за сколько часов приедет мастер» без команды — справка по нормативу.
- [x] «какие заявки в доме, у меня опять течёт» — заявка создаётся.
- [x] Контрольный список жалоб из FLOW-002 не перехватывается.
- [x] При недоступности модели поведение прежнее, без исключений.
- [x] `bash scripts/check.sh` проходит.

## Результат закрытия

**Закрыта 28.09.2026.**

Поле `intent` добавлено в схему ответа модели (`complaint` / `house_tickets` /
`my_tickets` / `rights` / `other`), `PROMPT_VERSION` 4 → 5, роутинг —
`_route_by_intent` в `flow/handlers.py` сразу после классификации.
Дополнительного вызова модели нет ни для одной ветки, кроме `rights`: справка
ищет ответ по нормативам, а классификация этого не делает.

**Живой прогон на текущей бесплатной модели** (реальный промпт, реальный
поиск по базе знаний):

| Фраза | intent | Тип | Уверенность |
|---|---|---|---|
| какие заявки ещё есть в доме | `house_tickets` | other | 0.90 |
| а что там по дому происходит | `house_tickets` | other | 0.60 |
| о чём соседи писали | `house_tickets` | other | 0.50 |
| что с моей заявкой | `my_tickets` | other | 0.85 |
| за сколько часов приедет мастер после заявки об аварии | `rights` | other | 0.30 |
| **какие заявки в доме, у меня опять течёт** | **`complaint`** | other | 0.50 |
| в подъезде не горит свет второй день | `complaint` | common_area | 0.90 |
| с потолка капает после дождя | `complaint` | roof_leak | 0.88 |

Шестая строка — та самая защита: вопрос и жалоба в одном сообщении остаются
жалобой, заявка создаётся.

**Ограничение, замеченное на том же прогоне:** из 11 вызовов три вернулись
`LlmUnavailable` — бесплатный провайдер отказывает эпизодически. Деградация
при этом безопасная: роутинга нет, поведение прежнее (заявка диспетчеру), то
есть обращение не теряется. Это та же неустойчивость, что зафиксирована в
CLASSIFY-003 и EVAL-002, а не новый дефект.

**Заодно исправлен детектор прав** (`rights/detect.py`): голое слово «права»,
«право», «вопрос» в начале работает как команда, а для оборотов, вопросительных
по построению («могут ли», «обязаны ли», «за сколько часов»), знак вопроса стал
необязательным. Границы узкие: «правая батарея не греет», «право собственности
на подвал у кого», «права жильцов нарушают, в подъезде темно» и «сколько часов
уже нет воды» в справку не уходят — на каждый случай есть тест.

**Что осталось:** правка не на проде. Команда `/права` сохранена намеренно —
она работает без внешней модели и остаётся страховкой на случай её
недоступности (architecture.md §10).
