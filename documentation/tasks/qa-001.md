## Цель

Основной сценарий проходится повторно на том же состоянии системы, переживает
остановку и перезапуск без потери заявок, а ошибочные действия жителя получают
понятный ответ вместо тишины или лишней заявки диспетчеру. Это прямые пункты
технической оценки кейса: «стабильно работает при повторном прохождении»,
«ошибки и некорректные действия обрабатываются предусмотренным образом»,
«в основном сценарии нет тупиков».

## Scope

### Входит

Тупики, найденные при живом прогоне 23–25.09.2026 и разборе `flow/handlers.py`:

1. **«статус» в свободной форме.** `статус N`, `статус №6`, `статус заявки 6`
   не совпадали с командой (ожидалось строго `статус 6`) и уходили в
   классификацию — диспетчер получал заявку «статус N». Любое сообщение,
   начинающееся со слова статуса, — команда; номер — первое число в хвосте,
   без числа — список заявок жителя.
2. **Сообщение без текста** (фото, голосовое, стикер) от подключённого жителя
   молча отбрасывалось. Ответ — подсказка, что пока принимается только
   текстовое описание.
3. **Справки нет.** «помощь», `/help`, «привет», «меню», «что ты умеешь»
   уходили в классификацию и создавали пустую заявку. Ответ — короткая справка
   по возможностям бота; заявка не создаётся. Только точные короткие фразы —
   жалоба, начинающаяся с «привет, …», должна дойти до классификации.
4. **Сквозной тест** на реальной маршрутизации продакшн-диспетчера
   (`default_dispatcher`): deep-link → согласие кнопкой → жалоба → заявка →
   «статус N» → второй житель с той же жалобой присоединяется → «Это другая
   проблема» → отдельная заявка → диспетчер закрывает заявку → подписчик
   уведомлён. Прогон дважды на одном состоянии (повторяемость).
5. **Остановка и перезапуск** корневого `compose.yaml` (артефакт сдачи):
   заявка, созданная до `docker compose down`, доступна по статусу после `up`.
6. **Живая проверка в MAX** того, что 23–25.09 не проверялось: запасной путь
   поиска дома по адресу (ONBOARD-002) и выход из склейки кнопкой.

### Не входит

- Нагрузочное тестирование; стабильность LLM на повторах (CLASSIFY-003).
- Оформление порядка проверки в README (DOCS-002) — здесь только факты для него.
- Распознавание фото и голоса (Could Have PHOTO-001).

## Технические требования

- LLM в сквозном тесте — `FakeLlmClient`; поиск по KB подменяется фиксированным
  фрагментом; семантический кэш отключается, чтобы тест не писал в рабочую
  коллекцию Qdrant решения под именем боевой модели.
- Справка и подсказка о нетекстовом сообщении — без подтверждения «Принял,
  определяю…» и без вызова классификации.

## Результат закрытия

Закрыто 25.09.2026.

**Три тупика исправлены** (`flow/handlers.py`, `flow/texts.py`):

- команда статуса — любое сообщение со слова статуса, номер — первое число в
  хвосте. Ограничение в 9 цифр не косметическое: «статус 99999999999999»
  переполнил бы `integer` в запросе и уронил обработку события;
- пустой текст (фото, голос, стикер) — подсказка вместо молчания;
- справка на «помощь», `/help`, «привет» — только для сообщения целиком,
  поэтому «привет, течёт кран в подвале» по-прежнему идёт в классификацию
  (закреплено тестом).

**Сквозной тест** `tests/integration/test_e2e_scenario.py` — путь двух жителей
через `default_dispatcher` (та же маршрутизация, что в рабочем воркере):
deep-link → согласие кнопкой → жалоба → заявка → статус → склейка соседа →
«Это другая проблема» → диспетчер закрывает заявку → уведомление подписчику.
Два прохода на одном состоянии дают одинаковую последовательность ответов
(номера и время нормализуются). Подменены только внешние зависимости: LLM,
поиск по KB и семантический кэш — иначе тест писал бы в рабочую коллекцию
Qdrant решения под именем боевой модели.

**Остановка и перезапуск** на корневом `compose.yaml`: заявка № 1 создана,
`docker compose down` (контейнеры удалены), `up` — «статус 1» отвечает с
историей. Тома переживают перезапуск.

**Живой прогон в MAX 25.09.2026** (веб-клиент, аккаунт пользователя):

| Проверка | Результат |
|---|---|
| «помощь» | справка без подтверждения «Принял…» и без заявки |
| «статус N» | список 5 заявок; **до исправления это же сообщение создавало заявку № 2** |
| «статус заявки 6» | карточка заявки № 6 с историей |
| жалоба про лифт | заявка № 7, зона `uk`, основание — п. 2 ПП №491 с местом про лифты |
| повтор той же жалобы | склейка: «уже есть заявка № 7» + кнопка, второй заявки нет |
| «Это другая проблема» | заявка № 8 отдельно; в истории № 7 — `subscriber_left` |

За час 6 входящих событий, все `done`, ни одного `failed`; ни одна служебная
команда заявок не создала.

**Не проверено вживую, перенесено в SUBMIT-001:**

- нетекстовое сообщение — у стикеров в MAX сначала нужно добавить пак в
  аккаунт пользователя, а загрузка файла открывает системный диалог, который
  блокирует браузер. Ветка покрыта тестом `test_non_text_message_gets_hint`;
  живьём проверяется отправкой любого фото за пару секунд;
- запасной путь поиска дома по адресу — единственный доступный аккаунт уже
  привязан к дому по deep-link, а отвязка означала бы правку данных на проде.
  Ветка покрыта `test_onboarding_address.py`; для живой проверки нужен второй
  аккаунт MAX.

**Follow-up:** в демо-базе накопились заявки от отладки (№ 1–8, часть в
`unknown` из-за прогонов на неработавшем LLM). Перед сдачей состояние стоит
пересоздать с нуля — это входит в SUBMIT-001 («замерена сборка с нуля»).
