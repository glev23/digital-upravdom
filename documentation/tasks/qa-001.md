## Цель

Основной сценарий проходится повторно на том же состоянии системы, переживает
остановку и перезапуск без потери заявок, а ошибочные действия жителя получают
понятный ответ вместо тишины или лишней заявки диспетчеру. Это прямые пункты
технической оценки кейса: «стабильно работает при повторном прохождении»,
«ошибки и некорректные действия обрабатываются предусмотренным образом»,
«в основном сценарии нет тупиков».

## Scope

### Входит

Тупики, найденные при живом прогоне 23–25.09.2026 и разборе `flow/handlers.py`:

1. **«статус» в свободной форме.** `статус N`, `статус №6`, `статус заявки 6`
   не совпадали с командой (ожидалось строго `статус 6`) и уходили в
   классификацию — диспетчер получал заявку «статус N». Любое сообщение,
   начинающееся со слова статуса, — команда; номер — первое число в хвосте,
   без числа — список заявок жителя.
2. **Сообщение без текста** (фото, голосовое, стикер) от подключённого жителя
   молча отбрасывалось. Ответ — подсказка, что пока принимается только
   текстовое описание.
3. **Справки нет.** «помощь», `/help`, «привет», «меню», «что ты умеешь»
   уходили в классификацию и создавали пустую заявку. Ответ — короткая справка
   по возможностям бота; заявка не создаётся. Только точные короткие фразы —
   жалоба, начинающаяся с «привет, …», должна дойти до классификации.
4. **Сквозной тест** на реальной маршрутизации продакшн-диспетчера
   (`default_dispatcher`): deep-link → согласие кнопкой → жалоба → заявка →
   «статус N» → второй житель с той же жалобой присоединяется → «Это другая
   проблема» → отдельная заявка → диспетчер закрывает заявку → подписчик
   уведомлён. Прогон дважды на одном состоянии (повторяемость).
5. **Остановка и перезапуск** корневого `compose.yaml` (артефакт сдачи):
   заявка, созданная до `docker compose down`, доступна по статусу после `up`.
6. **Живая проверка в MAX** того, что 23–25.09 не проверялось: запасной путь
   поиска дома по адресу (ONBOARD-002) и выход из склейки кнопкой.

### Не входит

- Нагрузочное тестирование; стабильность LLM на повторах (CLASSIFY-003).
- Оформление порядка проверки в README (DOCS-002) — здесь только факты для него.
- Распознавание фото и голоса (Could Have PHOTO-001).

## Технические требования

- LLM в сквозном тесте — `FakeLlmClient`; поиск по KB подменяется фиксированным
  фрагментом; семантический кэш отключается, чтобы тест не писал в рабочую
  коллекцию Qdrant решения под именем боевой модели.
- Справка и подсказка о нетекстовом сообщении — без подтверждения «Принял,
  определяю…» и без вызова классификации.

## Критерии приёмки

- [ ] «статус N», «статус №6», «статус заявки 6» — команда статуса, заявка не создаётся.
- [ ] Фото/голос/стикер от подключённого жителя получают подсказку, а не тишину.
- [ ] «помощь», «/help», «привет» — справка без заявки; «привет, течёт кран» — классификация.
- [ ] Сквозной тест проходит дважды подряд на одном состоянии.
- [ ] `docker compose down` → `up` (корневой compose): заявка до остановки доступна по статусу.
- [ ] Живой прогон в MAX: запасной путь по адресу и «Это другая проблема».
- [ ] `bash scripts/check.sh` проходит.
