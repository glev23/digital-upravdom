# ONBOARD-001 — Привязка дома по deep-link и согласие на ПДн

| Поле | Значение |
|---|---|
| ID | `ONBOARD-001` |
| Статус | `done` |
| Требования | architecture.md §7.1, §10 (строки «deep-link неизвестен», «согласие не выдано»), §11.1; max_api.md §5–§7; idea_and_scope.md шаг 4 (To Be), шаг 7 (платформенный бонус) |
| Зависимости | BOT-001, DATA-001 |
| Блокирует | ONBOARD-002, FLOW-001 |

## Цель

Житель открывает бота по ссылке/QR с дома, видит, **какой именно дом
распознан**, один раз даёт согласие на обработку ПДн — и только после этого
бот принимает описание проблемы. Без этого шага основной сценарий
невозможен: неизвестен дом (нет адресата, норматива, уведомлений) и нет
правового основания обрабатывать текст (152-ФЗ). Deep-link со стартовым
параметром — заявленный платформенный бонус (+0,15), поэтому сценарий
проверяется в настоящем MAX, а не только тестами.

## Scope

### Входит

- модуль `src/upravdom/onboarding/`: разрешение токена в дом, привязка
  `user_houses`, выдача/проверка/отзыв согласия с версией;
- обработчик `bot_started`: `payload` → `house_links.token` → дом →
  сообщение с распознанным адресом, текстом согласия и кнопками;
- обработчик `message_callback`: кнопки «Согласен» / «Не согласен» /
  «Это не мой дом» / «Добавить этот адрес»;
- **шлюз перед `message_created`**: пока нет дома или действующего
  согласия актуальной версии, текст жителя не обрабатывается, а
  удерживается (см. «Удержание сообщения») и житель получает шаг
  онбординга, а не «принял обращение»;
- повторный вход: житель с домом и согласием актуальной версии проходит
  молча («Дом уже привязан, опишите проблему»); ссылка другого дома —
  предложение добавить второй адрес (`is_primary = false`);
- смена `CONSENT_VERSION` возвращает шаг согласия всем;
- отзыв согласия командой `/revoke` (и текстом «отозвать согласие»):
  `revoked_at`, подтверждение и способ вернуться;
- поддержка inline-клавиатуры в транспорте: `outbox.enqueue_message(...,
  attachments=...)`, `MaxClient.send_message(..., attachments=...)`,
  `FakeMaxClient` сохраняет вложения для проверок;
- `seed_demo.py` печатает готовые ссылки `https://max.ru/<MAX_BOT_USERNAME>?start=<token>`,
  если `MAX_BOT_USERNAME` задан (сейчас печатается только токен);
- живая проверка по настоящей ссылке в MAX на VM (DEPLOY-001).

### Не входит

- поиск дома по введённому адресу — ONBOARD-002. Здесь для
  «токен неизвестен / отозван / без параметра» и «Это не мой дом» — честное
  сообщение с просьбой перейти по ссылке со стенда или из квитанции; в
  ONBOARD-002 эти же точки переключаются на поиск адреса;
- классификация и создание заявки — удержанное сообщение после согласия
  проходит через текущий обработчик `acknowledge_receipt` (заглушка
  BOT-001), настоящая обработка появится в FLOW-001;
- текст политики обработки ПДн как документ — отдельный follow-up
  (см. «Технические требования → Текст согласия»);
- генерация QR-кодов — PILOT-001/DEMO-001 (для проверки достаточно
  ссылки).

## Технические требования

**Разбор `message_callback` — сверить на живом событии до реализации.**
`max_api.md` §5 подтверждает только поля `callback_id` и `button_payload`
по документации, а `schemas.py` сейчас читает их «по месту» без реального
образца. Урок MAX-001 (три расхождения BOT-001 с реальностью): прежде чем
строить логику на полях, получить реальный `message_callback` —
отправить боту кнопку, нажать её, взять сырой `payload` из
`inbound_events` на VM — и по нему поправить `parse_webhook_payload`
(где лежат `user_id`, `chat_id`, `payload` кнопки). Образец сохранить в
`tests/fixtures/max/message_callback.json`, результат — в `max_api.md` §5.
Ответ на нажатие (`POST /answers`, снимает «часики» на кнопке) в
`max_api.md` не подтверждён — использовать только если подтверждается
документацией; иначе не вызывать и отметить в закрытии.

**Состояние онбординга — без отдельной таблицы.** Между `bot_started` и
нажатием кнопки нужно помнить, какой дом предложен. Это кладётся в сам
`payload` кнопки (≤1024 символов, max_api.md §7), а не в новую таблицу
сессий:

| Кнопка | `payload` |
|---|---|
| Согласен | `onb:accept:<token>:<consent_version>` |
| Не согласен | `onb:decline:<token>:<consent_version>` |
| Это не мой дом | `onb:wrong_house:<token>` |
| Добавить этот адрес | `onb:add_house:<token>` |

При нажатии токен разрешается **заново** (ссылку могли отозвать между
показом и нажатием); кнопка со старой версией согласия
(`consent_version` ≠ текущей) не выдаёт согласие, а показывает актуальный
текст заново. Разбор payload — одна функция с явным отказом на
неизвестный формат, без `split` по месту в обработчиках.

**Удержание сообщения до согласия.** architecture.md §7.1: текст,
написанный до согласия, удерживается и обрабатывается после нажатия
«Согласен»; при отказе — закрывается без классификации и без передачи
куда-либо. Реализация:

- в `InboundEventStatus` добавляется `awaiting_consent`, в
  `inbound_events` — колонка `max_user_id` (nullable, индекс),
  заполняется при записи события в вебхуке (сейчас идентификатор жителя
  есть только внутри JSON `payload`, и искать его там — `payload->...`
  без индекса — неудобно и медленно). Миграция `0003`: новое значение в
  CHECK `ck_inbound_events_status` + колонка + индекс;
- шлюз ставит событие в `awaiting_consent` вместо `done`; при согласии
  все события жителя в `awaiting_consent` переводятся в `pending` и
  подхватываются воркером обычным путём (порядок — по `received_at`);
- при отказе — `done` без обработки, в `last_error` — пометка
  `consent_declined` (для диагностики, без текста);
- `claim_batch` и `reclaim_stale_processing` события `awaiting_consent`
  не трогают — проверяется тестом.

**Согласие.** `consents`: `consent_version = CONSENT_VERSION`,
`granted_at = now()`, `source = "deep_link:<label>"` (`label` из
`house_links` — «подъезд»/«квитанция»: это даёт измерение канала в пилоте,
architecture.md §5.1). «Действующее согласие» — последняя запись
пользователя с `revoked_at IS NULL` и `consent_version = CONSENT_VERSION`.
Отзыв — `UPDATE ... SET revoked_at`, не `DELETE` (доказательство согласия
в прошлом, §11.1).

**Привязка дома.** Первая привязка — `is_primary = true`, дальнейшие —
`false` (частичный уникальный индекс `ix_user_houses_one_primary_per_user`
уже гарантирует один основной дом на уровне БД, DB-001). Повторная
привязка того же дома — не ошибка и не дубль (`ON CONFLICT DO NOTHING`
по составному ключу).

**Порядок записи при «Согласен».** `user_houses` + `consents` + перевод
удержанных событий — **одна транзакция**: частично выполненный онбординг
(дом привязан, согласия нет) дал бы молчаливый повторный вход без
согласия.

**Текст согласия** — в `src/upravdom/onboarding/texts.py`, словарь
`{версия: текст}`; отсутствие текста для текущей `CONSENT_VERSION` — ошибка
при старте, а не пустое сообщение жителю. Обязательные элементы (§11.1):
кто обрабатывает, какие данные (дом, идентификатор MAX, текст обращений),
цель, **передача обезличенного фрагмента описания внешнему LLM-сервису**,
способ отзыва (`/revoke`), ссылка `PRIVACY_POLICY_URL`. Пока
`PRIVACY_POLICY_URL` пуст — текст без ссылки и предупреждение в логе при
старте; сам документ политики — follow-up в DOCS-002.

**Тексты сообщений** — все в `texts.py`, не строками в обработчиках: их
будут править по итогам проверки UX, и искать их по коду не нужно.

**Идемпотентность.** MAX может повторить доставку `bot_started`/
`message_callback` (ключ у них составной, слабее `mid`, architecture.md
§3). Повторное «Согласен» не создаёт вторую запись `consents` с той же
версией, если действующая уже есть, и не шлёт второе приглашение.

## Сценарии

| # | Ситуация | Ожидаемое поведение |
|---|---|---|
| 1 | Новый житель, валидный токен | Адрес дома + текст согласия + кнопки «Согласен» / «Не согласен» / «Это не мой дом» |
| 2 | «Согласен» | `user_houses` (primary) + `consents`; «Готово, опишите проблему своими словами» |
| 3 | Написал о проблеме до согласия | Сообщение удержано (`awaiting_consent`), повторно показан шаг согласия; после «Согласен» — сообщение обработано (сейчас — подтверждение приёма) |
| 4 | «Не согласен» | Удержанные сообщения закрыты без обработки; объяснение, почему без согласия нельзя, и как вернуться |
| 5 | «Это не мой дом» | Дом не привязан; просьба перейти по ссылке своего дома (ONBOARD-002 заменит на поиск адреса) |
| 6 | Токен неизвестен / отозван / `payload` пуст | Не ошибка: то же честное сообщение, что в п.5 |
| 7 | Повторный вход, всё действительно | Без шага согласия: «Дом уже привязан, опишите проблему» |
| 8 | Ссылка другого дома при уже привязанном | «Добавить этот адрес?» → `is_primary = false` |
| 9 | `CONSENT_VERSION` повышен | Шаг согласия снова для всех, старые записи не удаляются |
| 10 | `/revoke` | `revoked_at` проставлен, новые сообщения снова упираются в шлюз |
| 11 | Нажата кнопка со старой версией согласия | Согласие не выдано, показан актуальный текст |
| 12 | Повторная доставка того же `bot_started`/нажатия | Одна запись `consents`, одно сообщение |
