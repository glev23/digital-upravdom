# DB-001 — Модель данных и миграции

| Поле | Значение |
|---|---|
| ID | `DB-001` |
| Статус | `done` |
| Требования | architecture.md §3, §4, §5.1–§5.7, §9 |
| Зависимости | INIT-001 |
| Блокирует | BOT-001, DATA-001, TICKET-001, KB-001 |

## Цель

Создать полную схему PostgreSQL из architecture.md §5 одной миграцией Alembic:
19 таблиц с ограничениями, индексами и справочником типов проблем. Инварианты,
от которых зависит корректность сценария (идемпотентность вебхука,
append-only история заявок, уникальность токенов deep-link), обеспечиваются
**базой данных**, а не кодом приложения.

## Scope

### Входит

- SQLAlchemy 2.0 модели для всех таблиц architecture.md §5.7;
- ревизия Alembic `0001` с созданием схемы и откатом;
- ограничения целостности, уникальности и допустимых значений;
- индексы под известные запросы воркера, дедупликации и уведомлений;
- защита append-only для `ticket_events` на уровне БД;
- справочник `problem_types`: seed-файл и его загрузка миграцией или стартовым
  скриптом;
- тесты миграций и ограничений на реальном PostgreSQL.

### Не входит

- демо-данные: УК, РСО, дома, deep-link токены, уведомления (DATA-001);
- репозитории и бизнес-логика модулей (BOT-001, TICKET-001 и далее);
- коллекции Qdrant (KB-001);
- нормативные документы и чанки (KB-001) — только таблицы для них.

## Технические требования

**Таблицы** — по architecture.md §5.1–§5.6 без изменения состава полей. Если
при реализации поле оказывается лишним или недостающим, архитектура правится
с записью в «Истории решений», а не расходится с кодом молча.

**Инварианты на уровне БД:**

| Инвариант | Реализация |
|---|---|
| Повторная доставка события MAX не создаёт второй записи | `UNIQUE (inbound_events.max_event_id)` |
| Один пользователь MAX — одна запись | `UNIQUE (users.max_user_id)` |
| Токен deep-link не повторяется | `UNIQUE (house_links.token)` |
| История заявки не переписывается | триггер, запрещающий `UPDATE` и `DELETE` в `ticket_events` |
| Житель подписан на заявку один раз | `PRIMARY KEY (ticket_id, user_id)` в `ticket_subscribers` |
| Один основной дом у жителя | частичный уникальный индекс по `user_houses (user_id) WHERE is_primary` |
| Статусы и перечисления — из закрытого списка | `CHECK`-ограничения или типы enum для `status`, `responsibility_zone`, `join_reason`, `index_state` |
| `confidence` в допустимом диапазоне | `CHECK (confidence BETWEEN 0 AND 1)` |
| Тип проблемы существует | `FOREIGN KEY tickets.problem_type → problem_types.code` |

**Индексы** под запросы, известные из архитектуры:

- `inbound_events (status, received_at)` — выборка воркером (§3);
- `outbound_messages (status, next_attempt_at)` — отправка с повторами (§7);
- `tickets (house_id, problem_type, status, created_at)` — поиск кандидатов
  дедупликации (§6.5);
- `tickets (management_company_id, created_at)` — арендное измерение (§5.2);
- `notifications (house_id, starts_at)` — рассылка (§5.3);
- `knowledge_documents (source_key, effective_from)` — выбор действующей
  редакции (§5.5).

**Справочник `problem_types`.** Все 11 кодов из architecture.md §4 с
`title`, `default_responsibility_zone`, `resolution_hours` и `norm_reference`.
Нормативные сроки берутся **из первоисточников** (ПП РФ №416, №354) с точной
ссылкой на пункт; в постановке значения намеренно не приводятся, чтобы не
закрепить непроверенную цифру. Где норматив однозначного срока не задаёт,
это указывается явно, а не заполняется «примерно». Источник справочника —
`data/seed/problem_types.json`, чтобы региональная адаптация была заменой
данных, а не кода (architecture.md §4).

**Прочее:**
- поле метаданных чанка называется `chunk_meta`, не `metadata` (§5.5);
- все метки времени — `timestamptz`;
- флаг `is_test_data` на `management_companies` и `resource_organizations`
  обязателен, без значения по умолчанию, — чтобы тестовые данные нельзя было
  создать, не пометив их явно.

## Критерии приёмки

- [x] `alembic upgrade head` на пустой базе создаёт все 19 таблиц; `alembic downgrade base` удаляет их без ошибок.
- [x] Повторная вставка события с тем же `max_event_id` отклоняется базой.
- [x] `UPDATE` и `DELETE` в `ticket_events` отклоняются базой.
- [x] Вторая основная запись дома для того же жителя отклоняется.
- [x] Недопустимое значение статуса или зоны ответственности отклоняется.
- [x] Организацию нельзя создать без явного `is_test_data`.
- [x] `problem_types` содержит все 11 кодов; у 7 есть числовой срок со ссылкой на пункт ПП №354, у 4 (лифт/кровля/МОП/двор) — явный `NULL` с пояснением, что норматива не найдено.
- [x] Схема в БД совпадает с моделями (`alembic check` — no new upgrade operations detected).
- [x] `bash scripts/check.sh` проходит.

## Проверка

```bash
docker compose up -d postgres
uv run alembic -c db/alembic.ini upgrade head
uv run alembic -c db/alembic.ini downgrade base
uv run alembic -c db/alembic.ini upgrade head
uv run pytest tests/integration/test_schema.py
bash scripts/check.sh
```

Ожидаемо: миграция проходит в обе стороны, все тесты ограничений зелёные.

## Результат закрытия

Закрыто 21.09.2026.

**Артефакты:** `src/upravdom/models/` (base.py, enums.py + `pg_enum()` хелпер,
users.py, organizations.py, tickets.py, notifications.py, queues.py,
knowledge.py, observability.py, `__init__.py`); `db/migrations/env.py`
(`target_metadata = Base.metadata`); `db/migrations/versions/0001_initial_schema.py`
(19 таблиц + append-only триггер на `ticket_events`); `data/seed/problem_types.json`
(11 кодов, 7 с числовым сроком из ПП №354, 4 — честный `NULL`);
`scripts/seed_problem_types.py` (идемпотентный upsert), подключён в
`scripts/entrypoint.sh`; `tests/integration/{conftest.py,test_schema.py}` (8 тестов).

**Два реальных бага, найденных и исправленных по ходу (не гипотетические —
воспроизведены на реальном Postgres):**

1. **CHECK-констрейнты на enum-колонках не генерировались вообще.**
   SQLAlchemy 2.0 по умолчанию не создаёт CHECK для `Enum(..., native_enum=False)`
   — нужен явный `create_constraint=True` (в старых версиях это было
   поведением по умолчанию). Без этого `UPDATE tickets SET status =
   'bogus_status'` молча проходил.
2. **Коллизия имён констрейнтов.** Один и тот же Python-enum на двух
   колонках одной таблицы (`responsibility_zone` и `routed_to_org_type` в
   `tickets` — оба `ResponsibilityZone`) получал одинаковое неявное имя
   ограничения — невалидный DDL, из-за которого Alembic autogenerate тихо
   пропускал оба CHECK без единой ошибки в логе. Плюс: CHECK по умолчанию
   строился на именах членов Python-enum (`'UK'`), а не на их значениях
   (`'uk'`) — расхождение с documented lowercase-кодами architecture.md §4.
   Исправлено общим хелпером `pg_enum(enum_cls, name=...)` с обязательным
   уникальным именем и `values_callable=lambda cls: [m.value for m in cls]`.

Оба бага нашлись только потому, что инварианты проверялись сырым SQL
(`UPDATE ... SET status = 'bogus'`), а не через ORM — ORM отклонила бы
плохое значение на стороне Python ещё до похода в базу, и тест бы
«прошёл», ничего не доказав про саму схему.

**Отклонения от постановки:** `notification_deliveries` и `outbound_messages`
получили `created_at`, не перечисленный в architecture.md §5.3/§5.4 —
нужен для сортировки очереди повторов; отмечено комментарием в коде,
architecture.md текстом раздела 5 не менялся (правка точечная и
самоочевидная, не меняет модель отношений).

**Фактические проверки:** все критерии приёмки выше — вживую на реальном
PostgreSQL (не только через pytest): ручной SQL-прогон всех 7 инвариантов
до автоматизации в тестах, `alembic upgrade head → downgrade base → upgrade
head` дважды подряд (до и после фикса CHECK), `alembic check` — без
расхождений, `bash scripts/check.sh` — зелёный (28 файлов mypy, 18 тестов).

**Follow-up:** `default_responsibility_zone` в `problem_types.json` — рабочий
дефолт (всё, кроме `other`, размечено `uk` по границе первого запорного
устройства, ПП №491 п.5), не результат анализа данных; при проектировании
промпта классификатора (CLASSIFY-001) это стоит пересмотреть осознанно, а
не унаследовать молча.
