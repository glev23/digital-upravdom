# CLASSIFY-002 — Семантический кэш и классификация без LLM

| Поле | Значение |
|---|---|
| ID | `CLASSIFY-002` |
| Статус | `done` |
| Требования | architecture.md §6.2 (п. 2, 6, 7), §6.3 (что кэшируется и как инвалидируется), §9 (кэш — одноразовая коллекция), §10 (строки OpenRouter, лимит, Qdrant), §13.2 (режим `--no-llm`) |
| Зависимости | CLASSIFY-001 |
| Блокирует | EVAL-002 |

## Цель

Классификация переживает отказ внешней модели: повторяющиеся обращения
отвечаются из кэша без вызова LLM, а при недоступности OpenRouter решение
принимается локально по похожим размеченным примерам — с честно
пониженной уверенностью и пометкой `fallback_used`. На защите это
отдельная строка таблицы EVAL-002 («цена отказа внешнего сервиса») и
ответ на вопрос «что будет, если бесплатная модель пропадёт».

## Scope

### Входит

- коллекция Qdrant `semantic_cache` и её чтение/запись в `classify()`;
- инвалидация по `OPENROUTER_MODEL`, `PROMPT_VERSION`, `kb_version`;
- набор размеченных примеров-прототипов и их предпосчитанные векторы;
- классификатор без LLM (k ближайших прототипов) — вместо заглушки
  CLASSIFY-001 при `LlmError`;
- шаблонный уточняющий вопрос в режиме без LLM;
- флаг принудительной деградации для EVAL-002 (`--no-llm`).

### Не входит

- измерение точности — EVAL-002;
- кэш ответов на вопросы о правах — RIGHTS-001;
- восстановление кэша после потери тома: коллекция одноразовая (§9).

## Технические требования

**Что кэшируется (§6.3).** Только результат классификации:
`problem_type`, `responsibility_zone`, `confidence`, подтверждённые
`chunk_id`. Адресат (УК/РСО с контактом) в кэш не попадает никогда — он
зависит от дома. Payload записи: решение + `model_name`,
`prompt_version`, `kb_version`, `created_at`. **Текста обращения в
payload нет**, даже маскированного.

**Какие решения кэшируются.** Только ветка `auto` первого прохода,
полученная от **основной** модели:

- решения ниже `CLASSIFY_CONFIDENCE_HIGH` не кэшируются — иначе
  однажды неуверенный ответ становится постоянным;
- решения после уточнения не кэшируются — они зависят от ответа жителя,
  которого нет в ключе;
- решения резервной модели не кэшируются — другое качество, а ключ
  инвалидации привязан к `OPENROUTER_MODEL`.

**Ключ и порог.** Вектор — эмбеддинг **маскированного** текста: имена и
телефоны не делают одинаковые жалобы «разными», а в Qdrant не попадает
вектор сырого текста. Попадание — косинус ≥ `SEMANTIC_CACHE_THRESHOLD`
(0.92, «то же самое», а не «похоже»). Поиск фильтрует payload по
текущим `OPENROUTER_MODEL` + `PROMPT_VERSION` + `kb_version`: записи
другой конфигурации не удаляются, а просто не находятся.

**При попадании** — решение возвращается без LLM, но **основание
перепроверяется**: закэшированные `chunk_id` должны существовать в
текущей базе знаний (при смене `kb_version` запись и так не найдётся, это
вторая страховка). В журнал — `cache_hit = true`, `model_name` записи.

**Классификация без LLM.** `data/classifier/prototypes.json` —
размеченные примеры (`text`, `problem_type`, `responsibility_zone`),
по 5–10 на тип проблемы и на спорные границы зон; векторы
предпосчитаны (`scripts/build_prototypes.py`, по образцу `build_kb.py`) и
держатся **в памяти процесса** (numpy): деградация не зависит от Qdrant,
то есть работает и при отказе обоих внешних компонентов. Решение —
взвешенное голосование k = 5 ближайших; `confidence` — доля голосов
победителя × косинус лучшего, с потолком `CLASSIFY_CONFIDENCE_HIGH − 0.01`:
без LLM и без проверки основания ветка `auto` запрещена, чтобы отказ
модели не превращался в поток уверенных ошибок маршрутизации. Основание —
пункты KB, найденные по тексту (если Qdrant доступен), показываются
жителю как справочные, а не как «решение принято по норме».

**Утечка в метрику.** Прототипы пишутся отдельно от EVAL-001, другим
участником или из других источников, и хранятся отдельно; тест проверяет,
что пересечения текстов с `data/test_cases/` нет. Иначе режим `--no-llm`
в EVAL-002 покажет завышенную точность.

**Шаблонный уточняющий вопрос** в режиме без LLM: при средней
уверенности — вопрос выбора между двумя лучшими типами проблем с
заранее написанными формулировками (`classifier/texts.py`), например
«Это про горячую воду или про отопление?».

**Порядок в `classify()`:** маскирование → кэш (если Qdrant доступен) →
при промахе поиск KB + LLM (CLASSIFY-001) → при `LlmError` — прототипы →
запись в кэш по правилам выше → журнал. Недоступный Qdrant пропускает
кэш и поиск, но не прототипы.

**Флаг для EVAL-002.** Параметр `force_no_llm=True` в `classify()` (не
переменная окружения на всё приложение) — прогон `--no-llm` не должен
требовать перезапуска сервиса.

## Критерии приёмки

- [x] Повторное обращение той же формулировки (с другим телефоном/именем) — попадание в кэш, LLM не вызывается.
- [x] Смена `OPENROUTER_MODEL`, `PROMPT_VERSION` или `kb_version` — промах (три отдельных теста).
- [x] Не кэшируются: решения ниже HIGH, после уточнения, от резервной модели.
- [x] В payload `semantic_cache` нет текста обращения и нет адресата.
- [x] При `LlmError` решение принимается по прототипам, `fallback_used = true`, зона не маршрутизируется автоматически.
- [x] При одновременно недоступных LLM и Qdrant классификация по прототипам работает.
- [x] Тексты прототипов не пересекаются с набором EVAL-001.
- [x] `bash scripts/check.sh` проходит.
