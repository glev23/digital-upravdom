# BOT-001 — Приём и отправка сообщений MAX

| Поле | Значение |
|---|---|
| ID | `BOT-001` |
| Статус | `done` |
| Требования | architecture.md §3, §5.4, §7, §8 (`bot_gateway`), §10; кейс — критерий «Стабильность работы и обработка ошибок» |
| Зависимости | DB-001, MAX-001 |
| Блокирует | ONBOARD-001, NOTIFY-001, FLOW-001 |

## Цель

Построить надёжный транспорт между MAX и приложением: вебхук принимает событие,
проверяет подлинность, сохраняет его и сразу отвечает, воркер обрабатывает
событие асинхронно, ответ уходит через очередь с повторами. Житель мгновенно
получает подтверждение приёма.

Бизнес-логики в задаче нет: обработчик событий — заглушка, которая
подтверждает приём. Задача доказывает, что при повторной доставке, сбое
обработки или недоступности MAX обращение не теряется и не дублируется.

## Scope

### Входит

- `POST /webhook/max` с проверкой подлинности по механизму из MAX-001;
- запись события в `inbound_events` с идемпотентностью по `max_event_id`;
- ответ `200` сразу после записи, `503` при недоступности PostgreSQL;
- воркер на APScheduler: захват, обработка, переходы статусов, повторы;
- восстановление событий, «зависших» в `processing` после падения процесса;
- реестр обработчиков по типу события и заглушка-обработчик;
- клиент MAX за интерфейсом (порт) и его фейковая реализация для тестов;
- отправка из `outbound_messages` с экспоненциальной задержкой и лимитом попыток;
- мгновенное подтверждение приёма жителю;
- сообщение о сбое жителю после исчерпания попыток;
- ограничение частоты сообщений от одного пользователя;
- создание записи `users` при первом событии от пользователя.

### Не входит

- привязка дома и согласие на ПДн (ONBOARD-001);
- классификация, заявки, диалоговая логика (CLASSIFY-001, TICKET-001, FLOW-001);
- публичный HTTPS и регистрация вебхука в MAX (DEPLOY-001);
- уведомления об отключениях (NOTIFY-001) — только общий механизм отправки,
  которым они потом воспользуются.

## Технические требования

**Приём.**
- Проверка подлинности выполняется **до** записи в БД; неподтверждённый запрос
  получает отказ и не создаёт записи. Если MAX-001 установит, что механизма
  подписи нет, применяется замена, зафиксированная там, а не отказ от проверки.
- Вставка — `INSERT ... ON CONFLICT (max_event_id) DO NOTHING`; повтор
  возвращает `200` без повторной обработки (architecture.md §3).
- Ответ отправляется до какой-либо обработки; целевое время ответа — десятки
  миллисекунд.
- При недоступности PostgreSQL — `503`, чтобы MAX повторил доставку
  (architecture.md §10). Поведение MAX при `503` берётся из MAX-001.

**Воркер.**
- Захват пачки событий `pending` через `SELECT ... FOR UPDATE SKIP LOCKED` —
  конкурентные воркеры не берут одно событие дважды.
- Переходы: `pending` → `processing` → `done` | `failed`; `attempts`
  увеличивается при захвате; ошибка пишется в `last_error` без текста
  сообщения жителя.
- Событие в `processing` дольше заданного таймаута считается зависшим и
  возвращается в `pending`, пока не исчерпан лимит попыток.
- После исчерпания попыток — `failed` и сообщение жителю о сбое с контактом
  АДС (architecture.md §10): тишина недопустима.

**Отправка.**
- Обработчики не вызывают API MAX напрямую — только ставят запись в
  `outbound_messages` (architecture.md §7).
- Повтор с экспоненциальной задержкой через `next_attempt_at`, ограниченное
  число попыток; ошибка отправки не роняет воркер.
- Ошибки, которые не исправятся повтором (например, пользователь заблокировал
  бота — если MAX-001 подтвердит такой код ответа), не повторяются.

**Подтверждение приёма.** На каждое содержательное входящее сообщение
в очередь ставится короткое подтверждение («принял обращение, определяю
ответственного»), чтобы житель не ждал молча (architecture.md §3, п. 4).

**Ограничение частоты.** Не больше `RATE_LIMIT_MESSAGES_PER_MINUTE` сообщений
от одного пользователя; сверх лимита — одно вежливое сообщение и пропуск
обработки, без вызова внешних сервисов.

**Порты.** Клиент MAX — интерфейс в `bot_gateway`; реальная реализация на
`httpx` по контракту из MAX-001, фейковая — для тестов. Тесты не ходят в сеть.

**Логи** не содержат текст сообщений жителей и токен.

## Критерии приёмки

- [x] Одно и то же событие, доставленное трижды, даёт одну запись и одну обработку. *(проверено дважды: pytest + живьём через `curl` на полном docker compose)*
- [x] Запрос с неверной подписью (или без неё) отклоняется и не создаёт записи.
- [x] При остановленном PostgreSQL вебхук отвечает `503`. *(проверено через monkeypatch на границе хранилища — не остановкой реального контейнера в тесте, см. «Результат закрытия»)*
- [x] Два конкурентных воркера не обрабатывают одно событие дважды.
- [x] Обработчик, падающий всегда, приводит событие в `failed` после лимита попыток, а житель получает сообщение о сбое.
- [x] Событие, зависшее в `processing` после аварийной остановки, обрабатывается после перезапуска.
- [x] Сбой отправки в MAX не теряет сообщение: оно уходит после восстановления.
- [x] Сообщения сверх лимита частоты не доходят до обработчика.
- [x] В логах нет текста сообщений жителей и токена. *(проверено вживую: текст «нет света в подъезде» в логах контейнера отсутствует)*
- [x] `bash scripts/check.sh` проходит.
- [ ] При наличии токена и публичного адреса (DEPLOY-001) или long polling (MAX-001): сообщение боту в MAX получает подтверждение приёма в мобильной и веб-версии. **Перенесено в DEPLOY-001** — ни публичного адреса, ни подтверждённого MAX-001 контракта пока нет.

## Проверка

```bash
docker compose up -d postgres
uv run pytest tests/unit/bot_gateway tests/integration/test_inbox_postgres.py
bash scripts/check.sh
```

Идемпотентность вручную (подпись формируется по механизму из MAX-001;
пример тела события — из `max_api.md`):

```bash
docker compose up -d
# отправить одно и то же подписанное событие трижды на http://localhost:8000/webhook/max
docker compose exec postgres psql -U upravdom -c "select count(*) from inbound_events;"
```

Ожидаемо: одна запись, один ответ жителю в `outbound_messages`.

## Результат закрытия

Закрыто 22.09.2026.

**Начато до закрытия MAX-001** — по явному запросу пользователя (постановка
формально зависела от обеих задач). Всё, что не требует подтверждённого
контракта MAX, реализовано и проверено полностью; всё, что требует —
изолировано в одном месте и явно помечено:

- `bot_gateway/schemas.py` (`parse_webhook_payload`) — формат payload
  best-effort (Telegram-подобный: `update_id`/`message.from.id`/
  `message.chat.id`/`message.text`), с fallback на детерминированный хэш
  тела, если `update_id` нет;
- `bot_gateway/webhook.py` (`SIGNATURE_HEADER`, `verify_signature`) —
  механизм подписи best-effort (HMAC-SHA256, заголовок
  `X-Max-Signature`), fail-closed без секрета;
- `bot_gateway/max_client.py` (`HttpxMaxClient`) — путь запроса и коды
  постоянных ошибок best-effort.

Когда MAX-001 зафиксирует реальный контракт, правки лягут в эти три
файла, не трогая `inbox.py`/`outbox.py`/`dispatcher.py`/`scheduler.py`.

**Отклонение от постановки, найденное по ходу:** в схеме DB-001 не было
поля для отслеживания давности `processing`-события — без него нельзя
отличить свежий заход в обработку от зависшего после падения воркера.
Добавлена миграция `0002` (`inbound_events.processing_started_at`,
nullable, обратная — `downgrade` удаляет колонку). DB-001 не переоткрывалась
задним числом — это аддитивное расширение уже закрытой задачи, а не её
дефект.

**Изменённые артефакты:** все из таблицы «Артефакты» выше, плюс
`src/upravdom/main.py` (lifespan запускает/останавливает планировщик,
подключён `webhook_router`), `src/upravdom/db.py` (`get_session` —
FastAPI-зависимость), `src/upravdom/config.py` и `.env.example`/`.env`
(`WORKER_*`, `INBOUND_*`, `OUTBOUND_*`, `MAX_API_BASE_URL`),
`pyproject.toml` (mypy override для `apscheduler`).

**Два реальных бага, найденных тестами (не гипотетических):**

1. `outbox.enqueue_message` вставлял JSON-payload через сырой `text()` с
   параметром-словарём — asyncpg не умеет сериализовать `dict` в голом
   SQL-запросе без явного адаптера типа
   (`DataError: invalid input for query argument... descriptor 'encode'
   for 'str' objects doesn't apply to a 'dict' object`). Исправлено:
   Core `insert()` через модель `OutboundMessage`, как уже было сделано в
   `inbox.record_inbound_event`.
2. Тесты, вызывающие `inbox.py`/`outbox.py` (которые сами делают
   `session.commit()`) поверх откатываемой транзакции фикстуры `connection`,
   коммитили внешнюю транзакцию целиком и ломали изоляцию между тестами.
   Исправлено правкой `conftest.py`: `session` fixture теперь создаётся с
   `join_transaction_mode="create_savepoint"` — внутренние `commit()`
   фиксируют только SAVEPOINT, внешний откат по-прежнему отменяет всё.
   Отдельно: `process_inbound_batch`/`process_outbound_batch` используют
   закэшированный на процесс `upravdom.db.get_engine()`, который в
   function-scope `pytest-asyncio` не переживает смену event loop между
   тестами («Event loop is closed») — добавлена `autouse`-фикстура,
   сбрасывающая кэш движка между тестами.

**Фактические проверки:**

- 61 автотест (43 было + 18 новых для BOT-001), все зелёные —
  `bash scripts/check.sh` целиком.
- **Живая проверка на полном `docker compose`** (не только pytest):
  подписанный вебхук отправлен трижды `curl` → `200` все три раза →
  в `inbound_events` ровно одна строка со статусом `done`; запрос с
  неверной подписью → `401`, строка не создана; в `outbound_messages`
  появилось подтверждение приёма (осталось `pending` — нет
  `MAX_API_BASE_URL`, ожидаемо); в `users` создана запись; в логах
  контейнера `app` нет ни текста обращения («нет света в подъезде»),
  ни токена, ни подписи — только метод/путь/код ответа.
- 503 при недоступном хранилище проверен через monkeypatch границы
  `record_inbound_event`, не реальной остановкой Postgres-контейнера в
  автотесте (тяжело и хрупко гонять в CI) — граница поведения та же,
  что требует критерий; реальная остановка проверялась вручную в
  INIT-001 для `/ready` и не переделывалась здесь заново.

**Наблюдение, не воспроизведённое повторно:** `bash scripts/check.sh`
один раз показал `FAILED
test_concurrent_claim_does_not_double_claim`; в изоляции и в трёх
последующих полных прогонах подряд тест зелёный, таблица `inbound_events`
после сбоя была пуста (не проблема мусорных данных между тестами). Момент
сбоя совпал с серией ручных `docker exec psql` команд на тот же
контейнер сразу перед прогоном — вероятная причина: возросшая задержка
на общей Postgres-сессии в этот момент, а не дефект в `claim_batch`
(`FOR UPDATE SKIP LOCKED` — стандартный, проверяемый паттерн). Логику не
менял; если сбой повторится стабильно — вернуться и разобрать отдельно.

**Не сделано / перенесено:**

- Живая проверка через реальный MAX (подтверждение приёма при отправке
  сообщения боту в мобильной/веб-версии) — перенесена в DEPLOY-001, как
  и предусмотрено постановкой: нет ни публичного HTTPS, ни токена с
  подтверждённым контрактом.
- Реальная сеть для `HttpxMaxClient` не проверялась (нет `MAX_API_BASE_URL`)
  — только путь `FakeMaxClient` в тестах и `client=None` (сообщения ждут
  в очереди) вживую.
