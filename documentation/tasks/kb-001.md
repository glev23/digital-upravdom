## Цель

Классификатор получает из Qdrant действующие на сегодня нормативные
фрагменты, на которые опирается решение и ссылка в ответе жителю
(«по ПП РФ №491, п.5 это общее имущество — отвечает УК»). Это ядро
отличия продукта — ответ на вопрос «кому», а не «как подать заявку»
(idea_and_scope.md, шаг 3.5), и защита от «уверенной выдумки» модели
(architecture.md §4). Результат задачи — наполненная и проверенная база
знаний плюс функция поиска, а не сама классификация.

## Scope

### Входит

- тексты нормативов в репозитории (`data/kb/sources/`) с метаданными
  редакции и источника;
- чанкинг по смысловым единицам (статья / пункт / подпункт) с контролем
  лимита модели;
- предпосчитанные векторы в `data/kb/` (сборка вручную,
  `scripts/build_kb.py`) — не в критическом пути старта (§12);
- загрузка при старте (`scripts/load_kb.py` в `entrypoint.sh`):
  `knowledge_documents`, `knowledge_chunks`, коллекция `kb_chunks` в Qdrant;
- `scripts/reindex.py` — полная пересборка `kb_chunks` из Postgres (§9);
- `src/upravdom/knowledge/retrieval.py` — поиск top-k с фильтром по
  действующей редакции и `management_company_id`;
- параметр промпта в `embeddings.embed` (асимметричная пара «запрос /
  документ», см. ниже);
- smoke-проверка качества поиска на контрольных запросах.

### Не входит

- классификация, вызов LLM, семантический кэш — CLASSIFY-001/002;
- документы конкретной УК (слой 2, Could Have) — схема их поддерживает
  (`management_company_id`), наполнение — отдельно;
- автоматическое отслеживание новых редакций на внешних сайтах.

## Критерии приёмки

- [x] Корпус Must Have (`pp491`, `pp354`, `pp416`, `zhk`) подготовлен, у каждого файла — источник, дата получения, редакция; расхождения номеров пунктов с гипотезой зафиксированы.
- [x] Ни один чанк не превышает лимит модели с учётом префикса (тест по реальному токенизатору).
- [x] `build_kb.py` детерминирован (повтор без изменений → те же `chunks.jsonl`/`manifest.json`).
- [x] `load_kb.py` идемпотентен; изменение набора чанков в манифесте удаляет устаревшие из обоих хранилищ.
- [x] `docker compose up` / локальный `load_kb`: коллекция `kb_chunks` наполнена, число точек = `count` манифеста (28).
- [x] Ошибка загрузки KB не валит старт (`entrypoint`: `load_kb.py || continue`); `/ready` по-прежнему честно отражает Qdrant.
- [x] `reindex.py` восстанавливает коллекцию после её удаления.
- [x] Фильтр редакции проверен тестом на `on_date` до и после `effective_from` (`pp40`).
- [x] Smoke-проверка: **18/18 = 100%** top-5 (порог 80%).
- [x] architecture.md §6.1 дополнен ПП №491.
- [x] `bash scripts/check.sh` проходит (155 тестов).

- **Статус:** `done` локально (22.09.2026); деплой на VM — в общем батче.
- **Изменённые артефакты:** см. таблицу выше; `architecture.md` §6.1 + история.

- **Отклонения / сверка корпуса:**
  - ПП №290 не включён (кандидат — не усиливал sanity).
  - `pp40` / `pp626` — рабочие выдержки для фильтра редакции и NOTIFY;
    точные формулировки и номер редакции перепроверить в RESEARCH-001
    по pravo.gov.ru (гипотеза постановки).
  - В payload Qdrant дополнительно кладётся `chunk_text` (удобство retrieval
    без join в Postgres) — сверх минимального списка полей из постановки.
  - Полный cold `docker compose build app` в этом прогоне мог идти параллельно;
    `data/kb` и `load_kb.py` уже в Dockerfile/entrypoint.
- **Follow-up:** RESEARCH-001 — сверка текстов pp40/pp626; CLASSIFY-001 —
  потребитель retrieval; при росте корпуса — батч-эмбеддинг GPU опционально.
