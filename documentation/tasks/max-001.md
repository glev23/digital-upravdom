# MAX-001 — Подтверждённый контракт MAX Bot API

| Поле | Значение |
|---|---|
| ID | `MAX-001` |
| Статус | `done` |
| Требования | architecture.md §3, §7, §7.1; idea_and_scope.md шаг 7 (платформенный бонус); кейс — «Ограничения» пп. 2, 3, 11 и «Сценарии работы платформы MAX» |
| Зависимости | Нет (живая проверка — после получения токена от организаторов) |
| Блокирует | BOT-001, DEPLOY-001, ONBOARD-001 |

## Цель

Заменить предположения о MAX Bot API в архитектуре подтверждёнными фактами.
Сейчас ни один элемент интеграции не проверен: способ проверки подлинности
вебхука, формат событий, передача стартового параметра deep-link, inline-кнопки,
лимиты. На непроверенной поддержке deep-link держится ещё и платформенный
бонус +0,15.

Результат — документ `documentation/max_api.md`, где у каждого факта указаны
источник, дата сверки и статус проверки. Код в этой задаче не пишется.

Кейс прямо требует сверяться с актуальной документацией MAX и историей
изменений API, а не со старыми примерами из сторонних источников.

## Scope

### Входит

Выяснить и зафиксировать по официальной документации MAX:

- **авторизация** запросов к API токеном бота;
- **получение событий:** регистрация вебхука, требования к адресу (HTTPS,
  порт, сертификат), поведение при таймауте и ошибке ответа (повторяет ли
  MAX доставку и сколько раз), **наличие long polling** как способа
  разработки без публичного HTTPS;
- **подлинность вебхука:** есть ли секрет, подпись или иной механизм —
  или его нет, и тогда чем заменяется защита (architecture.md §7);
- **формат событий:** новое сообщение, нажатие inline-кнопки, запуск бота
  пользователем, их идентификаторы — в частности, есть ли уникальный
  идентификатор события для идемпотентности (`max_event_id` в
  architecture.md §3);
- **deep-link со стартовым параметром:** формат ссылки, ограничения на длину
  и символы параметра, в каком событии и поле параметр приходит, работает ли
  это при повторном переходе пользователя, уже начавшего диалог;
- **отправка сообщений:** текст, форматирование, inline-клавиатура,
  обработка нажатия (callback), редактирование отправленного сообщения;
- **лимиты:** частота запросов, длина сообщения, число кнопок;
- **вложения** (фото) — только наличие и формат, для будущей PHOTO-001;
- **мини-приложения:** как подключается к боту, требования к HTTPS, MAX
  Bridge — только общая картина для WEB-001;
- **различия мобильной и веб-версии MAX**, влияющие на сценарий (кейс требует
  работы в обеих);
- **ник бота:** выдан ли бот организаторами уже с ником или ник выбирает
  команда — ник после создания изменить нельзя (ограничение №11 кейса).

Живая проверка при наличии токена:

- запрос информации о боте;
- отправка сообщения себе;
- получение события о входящем сообщении (через long polling, если он есть,
  иначе — после DEPLOY-001);
- переход по deep-link с параметром и фиксация, где параметр пришёл.

### Не входит

- реализация клиента MAX и вебхука (BOT-001);
- публичный HTTPS-адрес и регистрация вебхука на нём (DEPLOY-001);
- сохранение токена где-либо в репозитории, в документе или в выводе команд.

## Технические требования

- **Статус каждого факта** — одно из трёх значений: `подтверждено
  документацией` (ссылка на раздел), `подтверждено живым запросом` (дата,
  без токена в тексте), `не подтверждено` (с планом проверки). Факты из
  сторонних статей, форумов и примеров других проектов допускаются только
  со статусом `не подтверждено`.
- **Дата сверки** указывается для документа целиком и для каждого раздела:
  документация MAX меняется, и перед сдачей её нужно перепроверить.
- **Влияние на архитектуру.** Если факт расходится с architecture.md
  (например, у вебхука нет подписи или стартовый параметр не поддерживается),
  расхождение фиксируется в `max_api.md` в отдельном разделе, а
  architecture.md правится с записью в «Истории решений». Для deep-link
  запасной вариант уже описан в §7.1 — токен передаётся первым сообщением
  по кнопке.
- **Токен** используется только из переменной окружения; в примерах запросов
  вместо значения — `$MAX_BOT_TOKEN`.

- [x] Отдельно и однозначно дан ответ: **поддерживается** — `https://max.ru/<ник>?start=<payload>`, приходит в `bot_started.payload`, ≤128 символов.
- [x] Отдельно дан ответ: **есть** — секрет в заголовке `X-Max-Bot-Api-Secret`, передаётся как есть (не HMAC).
- [x] Отдельно дан ответ: **есть** — `GET /updates`, не для продакшна, но пригоден для разработки без DEPLOY-001.
- [x] Выявленные расхождения с architecture.md внесены в неё с записью в «Истории решений» (ревизия с меткой MAX-001, 22.09.2026).
- [x] Ни в одном файле и выводе нет значения токена.
- [x] При наличии токена выполнены живые проверки из раздела «Входит» — **выполнено 22.09.2026, с подтверждения пользователя**: `GET /me` (бот подтверждён, `t449_hakaton_max_bot`), `POST /subscriptions` (вебхук зарегистрирован), `GET /subscriptions` (подтверждено активной). ## Результат закрытия

Закрыто 22.09.2026.

**Подтверждено документацией** (все со ссылкой и датой в `max_api.md`):
авторизация (`Authorization: <token>`, без `Bearer`), базовый адрес
(`platform-api2.max.ru`), регистрация вебхука (`POST /subscriptions`,
HTTPS:443, доверенный ЦС), подпись вебхука (`X-Max-Bot-Api-Secret`, секрет
как есть), retry-политика (60с×2.5, до 10 раз, 8 часов), формат `Update`
и всех Must Have событий (`message_created`, `bot_started`,
`message_callback`) с точными полями, идемпотентность через
`message.body.mid` (у MAX нет `update_id`), deep-link (`?start=`, ≤128
символов, поле `payload` в `bot_started`), отправка сообщений и
inline-клавиатура, long polling (`GET /updates`) как способ разработки
без публичного HTTPS.

**Не подтверждено (честно оставлено открытым, не подогнано):** различия
мобильной/веб-версии MAX (это клиентское поведение, не контракт API — вне
области Bot API), требования мини-приложений (вне `docs-api`, не
исследовалось — не нужно для Must Have), точные лимиты частоты запросов к
`/messages`, формат загрузки фото для вложений. Все перечислены в
`max_api.md` §10 с пометкой, для какой задачи актуальны (WEB-001, PHOTO-001,
EVAL-002/демо).

**Расхождения с архитектурой, внесённые правки:** architecture.md §3
(идемпотентность через `message.body.mid`, а не выдуманный `update_id`),
§7 (подпись — простое сравнение секрета, не HMAC; base URL; формат
`Authorization`; типы событий; long polling), §7.1 (deep-link подтверждён
буквально), §10 (точные цифры retry) — запись в «Истории решений»,
22.09.2026.

**Платформенный бонус: подтверждён документацией**, не только
предположением — стартовый параметр deep-link существует и работает так,
как заложено в архитектуре (idea_and_scope.md, шаг 7).

**Код BOT-001 приведён в соответствие тем же проходом** (не откладывалось
на отдельный заход — расхождения были найдены уже написанными в коде):
`webhook.py` (заголовок и механизм подписи), `schemas.py` (реальная схема
`Update`, идемпотентность по `mid`), `max_client.py` (`Authorization` без
`Bearer`), `dispatcher.py` (fallback стал `noop_handler`, `acknowledge_receipt`
зарегистрирован только на `message_created` — иначе бот отвечал бы «принял
обращение» на системные события вроде `chat_title_changed`). 63 теста
(было 61), все зелёные, `bash scripts/check.sh` проходит.

**Живая проверка выполнена 22.09.2026** (после закрытия задачи, вместе с
DEPLOY-001, с явного подтверждения пользователя перед первым исходящим
вызовом): `GET /me` подтвердил, что бот уже создан организаторами —
`t449_hakaton_max_bot`, отображаемое имя и описание — заготовки, стоит
заменить. `POST /subscriptions` зарегистрировал вебхук на публичный
адрес DEPLOY-001. По пути обнаружена и исправлена реальная проблема:
`platform-api2.max.ru` использует сертификат Russian Trusted CA
(Минцифры), которого нет в стандартном доверенном хранилище `httpx` —
без фикса `HttpxMaxClient` падал бы на каждом исходящем запросе. Детали
и код — `max_api.md` §3, §9, §11; `architecture.md`, «История решений».
**Реальный диалог проверен 22.09.2026** (после закрытия этой задачи,
пользователем): открыл `t449_hakaton_max_bot` в MAX, написал два
сообщения — оба обработаны с первой попытки, бот ответил на оба через
настоящий MAX API, 0 ошибок. Живая проверка контракта — полная, без
оговорок. Детали — `max_api.md` §11.
