## 1. Компоненты решения

| Компонент | Роль | Обязательность |
|---|---|---|
| **App** (монолит: bot-gateway + worker + onboarding + classify/RAG + dedup + tickets + notifications) | Приём вебхука MAX, привязка жителя к дому и согласие на ПДн, асинхронная обработка обращений, классификация, дедупликация, создание и статус заявок, планировщик уведомлений | Must Have |
| **PostgreSQL** | Источник правды: пользователи, дома, заявки, события заявок, очереди входящих/исходящих сообщений, нормативы, журнал классификаций | Must Have |
| **Qdrant** | Векторное хранилище: коллекция чанков базы знаний (перестраиваемая проекция) + коллекция семантического кэша (одноразовая) | Must Have |
| **OpenRouter (внешний сервис)** | LLM: принимает решение о классификации обращения и формулирует ответы на вопросы о правах | **Must Have — с деградацией** (см. раздел 10) |
| **Web-мини-приложение (React)** | Просмотр истории обращений по дому | Could Have — условно, см. `idea_and_scope.md`, шаг 7 |

Внутри `App` два модуля добавлены в ревизии 3 и требуют отдельного упоминания, потому что меняют основной сценарий, а не дополняют его:

- **`onboarding`** — привязка жителя к дому через deep-link со стартовым параметром и однократное согласие на обработку ПДн. Must Have: без привязки к дому система не знает адресата и норматива, без согласия обработка обращений юридически невозможна (§7.1, §11).
- **`dedup`** — схлопывание массовых обращений об одной аварии в одну заявку с несколькими подписчиками. Should Have; перенесено из «задела в модели данных» в функциональность (обоснование — `idea_and_scope.md`, MoSCoW). Архитектурно оплачено заранее: вектор обращения уже считается и хранится.

**Роль LLM.** Классификация обращения — это решение по смыслу свободного текста с опорой на найденные нормативные фрагменты, и его принимает LLM. Это Must Have путь основного сценария. Отказ внешнего API не останавливает сценарий: система деградирует до классификации по чистому similarity search (раздел 10), с понижением точности и явной пометкой в журнале. Формулировка «ключевая метрика не зависит от LLM» из первой редакции документа отменена как неверная — метрика зависит от LLM, а устойчивость обеспечивается деградацией и семантическим кэшем, а не отказом от модели.

MVP — монолитный `App` + два хранилища, без разбивки на отдельные бизнес-сервисы. Границы будущих сервисов фиксируются как внутренние интерфейсы (раздел 8), а не контейнерами.

## 2. Технологический стек

- **Backend:** Python 3.12+, менеджер зависимостей — **uv** (`pyproject.toml` + `uv.lock`).
- **Веб-фреймворк:** **FastAPI** — async, типизация, автогенерация OpenAPI-схемы.
- **ORM + миграции:** SQLAlchemy 2.0 + **Alembic**.
- **Реляционная БД:** PostgreSQL 16.
- **Векторная БД:** Qdrant.
- **Embedding-модель:** **sergeyzh/BERTA** — 128M параметров, dim **768**, max tokens **512**, лицензия **MIT**. Инструктивная (E5-style): нужен префикс-промпт перед текстом.
- **Инференс эмбеддингов — ONNX Runtime, без torch в финальном образе** (SPIKE-001, `src/upravdom/embeddings.py`). Модель в ONNX весит ~490 МБ — больше лимита GitHub 100 МБ/файл, поэтому **не коммитится в репозиторий**. `docker/app.Dockerfile` — multi-stage: стейдж `exporter` ставит torch/optimum, экспортирует модель (`scripts/export_onnx.py`) и отбрасывается; в финальный образ копируется только результат экспорта, рантайм торч не видит вообще. Локально для venv-разработки — тот же `scripts/export_onnx.py` в dev-группе `embedding-export`, результат в `data/model/` (гитигнорится). Векторы ONNX совпадают с torch-эталоном (cosine ~1.0 на 50 фразах), задержка — единицы–десятки мс на CPU (не узкое место, раздел 14). Время холодной сборки: вариант A (torch в одном стейдже) — 194 с; актуальный multi-stage ONNX — **187 с** на машине команды (22.09.2026, `torch==…+cpu` в exporter; см. spike-001.md).
- **LLM:** через **OpenRouter API**; конкретная модель — в `OPENROUTER_MODEL`, не хардкодится. Указывается также резервная модель `OPENROUTER_MODEL_FALLBACK` — бесплатные модели на OpenRouter могут стать недоступны без предупреждения.
- **Планировщик задач:** **APScheduler** в процессе `App` — обслуживает воркер очереди входящих, ретраи исходящих и рассылку уведомлений.
- **Интеграция с MAX:** webhook + REST к MAX Bot API — перед реализацией сверка с актуальной документацией MAX.
- **Web (если дойдём до мини-приложения):** JS/React, компоненты MAX UI.
- **Качество кода:** ruff, mypy, pytest — конфиг в `pyproject.toml`.
- **Контейнеризация:** Docker + Docker Compose.

## 3. Обработка входящего сообщения: асинхронность и идемпотентность

Синхронная обработка вебхука недопустима: полный путь (эмбеддинг → поиск → LLM) занимает секунды, а MAX при отсутствии ответа за 30 секунд повторяет доставку с экспоненциальным backoff (60 с, ×2.5, до 10 попыток, автоотписка через 8 часов без успеха — подтверждено MAX-001, `max_api.md` §3), и повтор без защиты создаёт дубликат заявки.

**Схема обработки:**

1. `POST /webhook/max` принимает событие, **проверяет подлинность** (раздел 11) и немедленно записывает его в `inbound_events` с уникальным `max_event_id`.
2. Если `max_event_id` уже есть — запись отбрасывается на уникальном индексе, обработка не повторяется. Идемпотентность обеспечивается БД, а не логикой приложения.

**`max_event_id` — не готовое поле из MAX.** У объекта `Update` в MAX нет
сквозного `update_id` (подтверждено MAX-001, `max_api.md` §5). Ключ
идемпотентности строится по типу события: для `message_created` — это
`message.body.mid` (уникальный ID сообщения от MAX); для событий без
вложенного сообщения (`bot_started` и т.п.) естественного уникального
идентификатора нет — используется составной ключ `(chat_id, timestamp,
update_type)`, не гарантированно уникальный при действительно
одновременных событиях, но рабочий компромисс для MVP.
3. Эндпоинт отвечает `200` сразу после записи — до какой-либо обработки.
4. Жителю немедленно отправляется подтверждение приёма («принял обращение, определяю ответственного») — пользователь не ждёт молча несколько секунд.
5. Воркер (APScheduler) забирает событие из `inbound_events` со статусом `pending`, обрабатывает (раздел 6), пишет результат и ставит исходящее сообщение в `outbound_messages`.
6. Отправка в MAX идёт из `outbound_messages` с ретраями — сетевой сбой на исходящем пути не теряет ответ.

**Состояния `inbound_events`:** `pending` → `processing` → `done` | `failed`. Ограниченное число попыток, после исчерпания — `failed` + событие в журнал; житель получает честное сообщение о сбое, а не тишину.

## 4. Таксономия классификации и порог уверенности

Ключевая метрика продукта — точность маршрутизации, поэтому выход классификатора определён строго, а не как свободный текст.

**Две независимые оси** (в первой редакции они были слиты в одно поле `category` — разделены):

- `responsibility_zone` — кто отвечает: `uk` · `rso` · `owner` · `municipality` · `unknown`
- `problem_type` — что именно произошло: `cold_water` · `hot_water` · `heating` · `sewage` · `electricity` · `gas` · `elevator` · `roof_leak` · `common_area` · `yard` · `other`

Перечень `problem_type` хранится не в коде, а в таблице-справочнике `problem_types` вместе с нормативным сроком устранения и ссылкой на норматив. Это делает нормативы **переменной частью**: адаптация под регион с иными требованиями — это новый seed справочника, а не правка кода.

**Порог уверенности.** LLM возвращает решение вместе с `confidence` (0..1). Поведение:

| Уверенность | Поведение |
|---|---|
| ≥ 0.75 | Заявка создаётся и маршрутизируется автоматически |
| 0.45 – 0.75 | Один уточняющий вопрос жителю, после ответа — повторная классификация |
| < 0.45 | Система честно сообщает, что не берётся определить ответственного, даёт общий контакт УК и создаёт заявку с `responsibility_zone = unknown` для разбора диспетчером |

Пороговые значения — стартовые, калибруются на тестовом наборе (раздел 13) до защиты. Ветка «не уверен» обязательна: кейс прямо требует предусматривать ситуацию, когда надёжного ответа недостаточно, и не выдавать предположение модели за официальный факт.

**Обоснование ответа.** Вместе с решением сохраняются идентификаторы нормативных чанков, на которых оно построено, и в ответе жителю приводится ссылка на норматив (например, ПП РФ №416 о сроках устранения). Это требование кейса к работе с официальными данными и одновременно защита от «уверенной выдумки» модели.

## 5. Модель данных (PostgreSQL)

### 5.1 Пользователи и дома

**`users`** — `id`, `max_user_id` (unique), `created_at`
**`houses`** — `id`, `address_raw`, `fias_id` (nullable), `region_code`, `management_company_id` (FK, nullable), `created_at`
**`user_houses`** — `user_id` (FK), `house_id` (FK), `is_primary`, `created_at` — связь житель↔дом. Без неё основной сценарий не проходится: система не знает адрес обратившегося. Привязка выполняется один раз при первом обращении (онбординг) и переиспользуется дальше.
**`management_companies`** — `id`, `name`, `region_code`, `ads_phone`, `ads_hours`, `is_test_data`, `created_at`
**`resource_organizations`** — `id`, `name`, `region_code`, `resource_type`, `contact`, `is_test_data`, `created_at` — адресат маршрутизации, когда зона ответственности `rso`. Без этой таблицы половина решений классификатора некуда направить.

**`house_resource_orgs`** — `house_id` (FK), `resource_type`, `resource_organization_id` (FK), `valid_from`, `valid_to` (nullable) — какая РСО поставляет конкретный ресурс в конкретный дом. Связь «дом → ресурс → организация» именно потому вынесена в таблицу, что она и есть основная стоимость подключения новой УК (`idea_and_scope.md`, чек-лист онбординга, шаг 2) — то есть переменная часть, которая должна заполняться данными, а не кодом.

**`house_links`** — `id`, `house_id` (FK), `token` (unique), `label`, `is_active`, `created_at`, `revoked_at` (nullable) — deep-link'и на привязку дома (§7.1). Отдельная таблица, а не `house_id` в ссылке напрямую: непрозрачный токен не позволяет подобрать чужой дом перебором, ссылку можно отозвать при смене УК, а `label` отличает стенд в подъезде от квитанции, что даёт измерение эффективности канала в пилоте.

**`consents`** — `id`, `user_id` (FK), `consent_version`, `granted_at`, `revoked_at` (nullable), `source` — факт согласия на обработку персональных данных (§11). Версия хранится вместе с фактом: при изменении текста согласия старые записи перестают действовать и согласие запрашивается повторно, а не считается выданным задним числом. Отзыв — не удаление строки, а `revoked_at`: доказательство наличия согласия в прошлом должно сохраняться.

Флаг `is_test_data` на обеих организационных таблицах — техническая реализация требования кейса явно обозначать смоделированные данные.

### 5.2 Заявки

**`problem_types`** — `code` (PK), `title`, `default_responsibility_zone`, `resolution_hours`, `norm_reference` — справочник типов проблем и нормативных сроков (ПП РФ №416).
**`tickets`** — `id`, `user_id` (FK), `house_id` (FK), `management_company_id` (FK — арендное измерение, см. ниже), `raw_text`, `problem_type` (FK → `problem_types.code`), `responsibility_zone`, `confidence`, `routed_to_org_type`, `routed_to_org_id`, `status`, `due_at`, `embedding_point_id`, `source_event_id` (FK → `inbound_events`), `created_at`, `updated_at`
**`ticket_events`** — `id`, `ticket_id` (FK), `event_type`, `from_status`, `to_status`, `actor`, `payload`, `created_at` — **append-only**. Заявленная ценность продукта — сквозной статус, не теряющийся при передаче между организациями; одно мутабельное поле `status` этого не выражает, история переходов выражает.

**`ticket_subscribers`** — `ticket_id` (FK), `user_id` (FK), `is_author`, `joined_at`, `join_reason` (`author` / `dedup_auto` / `manual`) — кто получает уведомления о судьбе заявки. Таблица подписчиков, а не одно поле `user_id` в `tickets`, — прямое следствие дедупликации: при массовой аварии заявка одна, а жителей, ожидающих по ней ответа, десятки. `is_author` сохраняется, потому что автор первичного описания — единственный, с кем диспетчер может уточнить детали.

В `tickets` для дедупликации добавлены `dedup_group_id` (nullable) и `duplicate_of_ticket_id` (nullable, FK → `tickets.id`). Дубликат остаётся отдельной строкой со статусом `merged`, а не исчезает: обращение жителя не должно пропадать из системы только потому, что оно оказалось сорок вторым по счёту.

`management_companies_id` в `tickets` — это арендное (tenant) измерение. Оно заложено сразу по той же логике, по которой в Must Have попал эмбеддинг сообщения: дёшево добавить сейчас, дорого прошивать через все выборки и фильтры поиска на этапе тиража на десятки УК.

### 5.3 Уведомления

**`notifications`** — `id`, `house_id` (FK), `type` (`planned_outage` / `emergency_outage`), `resource_type`, `starts_at`, `ends_at`, `message`, `source` (`test_data` / `manual`), `created_at`
**`notification_deliveries`** — `id`, `notification_id` (FK), `user_id` (FK), `status`, `sent_at`, `error` — кому фактически доставлено, что позволяет повторить неудачные отправки и показать результат рассылки.

Источник данных об отключениях в MVP — **смоделированные записи**, загружаемые seed-скриптом или создаваемые вручную через служебный эндпоинт; реальной интеграции с РСО/ГИС ЖКХ нет, это явно обозначается в README (ограничение №10 кейса).

### 5.4 Очереди сообщений

**`inbound_events`** — `id`, `max_event_id` (unique), `payload`, `status`, `attempts`, `last_error`, `received_at`, `processed_at`
**`outbound_messages`** — `id`, `max_chat_id`, `payload`, `status`, `attempts`, `next_attempt_at`, `sent_at`, `last_error`

Обе таблицы — простой durable outbox/inbox на Postgres, без брокера. Для нагрузки MVP этого достаточно, а отдельный Redis/RabbitMQ был бы избыточным компонентом.

### 5.5 База знаний

**`knowledge_documents`** — `id`, `source_key`, `title`, `version`, `effective_from`, `effective_to` (nullable), `region_code` (nullable), `management_company_id` (nullable), `checksum`, `created_at`
**`knowledge_chunks`** — `id`, `document_id` (FK), `chunk_text`, `chunk_meta` (JSONB), `qdrant_point_id`, `index_state`, `created_at`

Документы **неизменяемы и версионны**: изменение норматива — это новая версия документа с новым `effective_from`, а не правка старого. Поиск фильтрует действующую на текущую дату редакцию. Это не теоретическая предосторожность: ПП РФ №40 вступает в силу 01.09.2026, то есть смена редакции происходит прямо в окне жизни проекта.

Поле названо `chunk_meta`, а не `metadata` — `metadata` конфликтует с атрибутом `Base.metadata` в декларативных моделях SQLAlchemy.

### 5.6 Наблюдаемость

**`classification_logs`** — `id`, `inbound_event_id` (FK), `ticket_id` (FK, nullable), `message_masked`, `problem_type`, `responsibility_zone`, `confidence`, `cache_hit`, `fallback_used`, `used_chunk_ids`, `model_name`, `prompt_version`, `kb_version`, `latency_ms`, `created_at`

Эта таблица закрывает сразу три задачи: доказательная база метрики точности на защите, основание ответа для жителя (какие нормы использованы) и диагностика деградаций. Текст в журнале хранится в маскированном виде (раздел 11).

### 5.7 Полный перечень таблиц

`users` · `houses` · `user_houses` · `house_links` · `consents` · `house_requests` · `management_companies` · `resource_organizations` · `house_resource_orgs` · `problem_types` · `tickets` · `ticket_subscribers` · `ticket_events` · `notifications` · `notification_deliveries` · `inbound_events` · `outbound_messages` · `knowledge_documents` · `knowledge_chunks` · `classification_logs` (+ служебная `alembic_version`).

Добавлены в ревизии 3: `house_links` и `consents` (онбординг и согласие, §7.1/§11), `house_resource_orgs` (адресат РСО по дому — ключевая переменная часть при онбординге УК), `ticket_subscribers` (дедупликация, §6.5).

## 6. RAG-пайплайн

### 6.1 Подготовка базы знаний

1. **Источник (Must Have):** тексты ЖК РФ (ст. 36, 161, 162), ПП РФ №491 (состав общего имущества и границы эксплуатационной ответственности — главная норма «УК или собственник»), №416, №354, №626 (уведомления о плановом отключении ГВС через ГИС ЖКХ и Госуслуги), №40 (новая редакция п. 27 и 30 ПП №416 — взаимодействие УК с жителями через MAX с 01.09.2026) — обрабатываются заранее, не в рантайме. Тексты пунктов — **дословные** из официальной редакции (Garant, сверка 22.09.2026), а не пересказ: бот цитирует их жителю со ссылкой на пункт. Кандидат на расширение корпуса — ПП РФ №290 (минимальный перечень работ).
2. **Чанкинг:** по смысловым единицам (статья/пункт), каждый чанк укладывается в лимит модели (≤512 токенов с учётом префикса `search_document:`); в начало чанка — заголовок-контекст («ПП РФ №491, п. 5»).
3. **Эмбеддинг:** BERTA через ONNX Runtime (`src/upravdom/embeddings.py`), dim 768; асимметричная пара промптов `search_query:` / `search_document:`.
4. **Хранение:** текст и метаданные — в `knowledge_chunks`; вектор — в коллекции `kb_chunks` Qdrant, payload содержит `chunk_id`, `document_id`, `source_key`, `ref`, `chunk_text`, `effective_from`/`effective_to`, `region_code`, `management_company_id`.
5. **Слой 2 (Could Have):** документы конкретной УК добавляются как новые чанки с заполненным `management_company_id` — фильтруются при поиске, схема при онбординге новой УК не меняется.

Векторы базы знаний **предпосчитаны и хранятся в репозитории** (`data/kb/`), а не вычисляются при каждом старте — см. раздел 12.

### 6.2 Обработка обращения

1. Текст сообщения → эмбеддинг (BERTA, CPU).
2. **Семантический кэш:** поиск ближайшего соседа в `semantic_cache` с порогом similarity ≥ 0.92 (не «похоже», а «то же самое»). Попадание — готовая категория без вызова LLM.
3. При промахе — retrieval top-k (k = 3–5) по `kb_chunks` с фильтром по действующей редакции и, при наличии, по `management_company_id`.
4. **LLM (OpenRouter) принимает решение о классификации**, используя найденные чанки как контекст, и возвращает `problem_type`, `responsibility_zone`, `confidence`.
5. Решение проходит проверку по порогу уверенности (раздел 4), результат пишется в `classification_logs`.
6. Пара «эмбеддинг → решение» сохраняется в `semantic_cache`.
7. **Деградация:** при таймауте или ошибке LLM классификация выполняется по чистому similarity search без LLM, в журнале ставится `fallback_used = true`.

### 6.3 Что именно кэшируется и как инвалидируется

Кэш хранит **только результат классификации** (`problem_type`, `responsibility_zone`) — то, что зависит исключительно от текста обращения. Адресат маршрутизации (конкретная УК или РСО с контактом) в кэш не попадает никогда: он определяется домом обратившегося уже после классификации. Иначе житель одного дома получил бы контакт аварийной службы другого.

Запись кэша хранит в payload `model_name`, `prompt_version` и `kb_version`. Запись, посчитанная при других значениях, не переиспользуется: смена модели в `OPENROUTER_MODEL`, правка промпта или обновление нормативов автоматически выводят старые записи из оборота. Без этого кэш тихо отравлял бы метрику точности результатами предыдущей конфигурации.

### 6.4 Ответы на вопросы о правах (Should Have)

Найденные top-k чанки передаются в LLM для формулировки ответа человеческим языком, с обязательной ссылкой на норматив. Путь независим от классификации; при недоступности LLM функция отключается с честным сообщением, основной сценарий не затрагивается.

### 6.5 Дедупликация массовых обращений (Should Have)

Запускается после классификации, до создания заявки. Вектор обращения уже посчитан на шаге 6.2 — дополнительной стоимости у этого шага почти нет.

**Условия склейки — все одновременно:**

| Условие | Значение | Почему именно так |
|---|---|---|
| Тот же дом | `house_id` совпадает | Одинаковая протечка в разных домах — разные аварии |
| Тот же тип проблемы | `problem_type` совпадает | Защита от склейки «нет воды» и «нет света» по похожему тону сообщения |
| Открытая заявка | статус не в терминальном состоянии | Закрытая заявка не должна собирать новые обращения |
| Временное окно | по умолчанию 6 часов | За пределами окна это уже новая авария, даже если формулировка совпала |
| Похожесть описания | cosine ≥ 0.88 | Консервативно: ниже кэшевого порога 0.92, но заметно выше «примерно про то же» |

Поиск кандидатов идёт **по заявкам этого дома**, а не по всей коллекции: выборка мала, поэтому сравнение делается напрямую по сохранённым векторам без отдельного обращения к Qdrant, и недоступность Qdrant не ломает дедупликацию.

**Поведение при склейке.** Создаётся запись `tickets` со статусом `merged` и заполненным `duplicate_of_ticket_id`; житель добавляется в `ticket_subscribers` головной заявки с `join_reason = dedup_auto` и получает сообщение вида «по этой проблеме уже есть заявка №N, статус — в работе, срок по нормативу — до 18:40; я подписал вас на обновления». В `ticket_events` головной заявки пишется событие о присоединении — диспетчер видит реальный масштаб аварии (сколько квартир сообщило), а не одну строку.

**Обязательный выход из склейки.** В том же сообщении — кнопка «Это другая проблема». Нажатие переводит заявку из `merged` в обычный статус, снимает подписку и пишет событие. Ложная склейка дороже пропущенного дубля: пропущенный дубль стоит диспетчеру лишней строки, а ложная склейка означает, что житель считает свою проблему принятой, тогда как её потеряли. Поэтому выход из склейки — Must Have внутри Should Have фичи, а не улучшение.

**Деградация.** Если вектор обращения по какой-либо причине отсутствует (`tickets.embedding_point_id` пуст), дедупликация просто не срабатывает и заявка создаётся обычным образом. Ни один отказ в этом модуле не блокирует основной сценарий.

**Метрики модуля** (`idea_and_scope.md`, шаг 5): доля корректно схлопнутых обращений и доля ложных склеек. Вторая важнее и измеряется отдельно.

## 7. Интеграция с MAX

- **Webhook:** единая точка `POST /webhook/max`, регистрируется через `POST /subscriptions` (HTTPS, порт 443, сертификат доверенного ЦС — self-signed не принимается) с `update_types` из подтверждённого списка (`max_api.md` §5) — принимает все входящие события по формату MAX Bot API.
- **Подлинность входящего запроса проверяется обязательно.** Подтверждено MAX-001 (`max_api.md` §4): `secret`, заданный при создании подписки, MAX возвращает **в неизменном виде** в заголовке `X-Max-Bot-Api-Secret` — не HMAC-подпись тела, а прямое сравнение строки (константное время). Незаверенный вебхук означает, что любой, кто узнал URL, создаёт заявки от чужого имени.
- **Типы входящих сообщений:** Must Have — свободный текст (`message_created`) и нажатия inline-кнопок (`message_callback`); онбординг — `bot_started` с полем `payload` (раздел 7.1); Could Have — фото как вложение к заявке.
- **Исходящие сообщения:** только через очередь `outbound_messages` с ограниченным числом повторов и экспоненциальной задержкой. Прямая отправка из обработчика запрещена — сетевой сбой в этот момент терял бы ответ жителю безвозвратно. Отправка — `POST /messages` на `https://platform-api2.max.ru` (подтверждено MAX-001) с `Authorization: <token>` **без схемы `Bearer`** — частая ошибка при переносе кода с других мессенджер-API.
- **Два способа адресации исходящего** (STATUS-001). Ответ в текущем диалоге идёт по `chat_id` из входящего события. Уведомление, которое бот инициирует сам (смена статуса заявки, переадресация, отключения NOTIFY-001), адресуется по `user_id`: в `users` хранится только `max_user_id`, а `chat_id` диалога с ботом ему не равен и угадывать его нельзя. `POST /messages` принимает оба (`max_api.md` §7). В очереди способ различается ключом `user_id` в `payload` — тем же приёмом, что `callback_id` для `POST /answers`; колонка `outbound_messages.max_chat_id` остаётся ключом доставки и порядка и хранит в этом случае тот же `max_user_id`. Отдельная колонка и миграция не понадобились.
- **Токен бота:** `MAX_BOT_TOKEN` в окружении, в репозиторий не попадает; шаблон — в `.env.example`.
- **Long polling (`GET /updates`)** — подтверждённая MAX-001 альтернатива вебхуку для разработки без публичного HTTPS: `timeout` 0–90 с, `limit` 1–1000, курсор `marker`. Не для продакшна (сам MAX это пишет в документации — не наше решение), но снимает жёсткую зависимость живой проверки BOT-001/ONBOARD-001 от DEPLOY-001.
- **Контракт подтверждён** MAX-001 — `documentation/max_api.md`, дата сверки 22.09.2026. Перед сдачей перепроверить ссылки заново (документация MAX меняется).

### 7.1 Онбординг: привязка дома и согласие на ПДн

Первый контакт жителя с ботом — это не сообщение о проблеме, а два условия, без которых сценарий не может продолжиться: система должна знать **дом** (иначе нет ни адресата, ни норматива, ни уведомлений) и иметь **согласие на обработку ПДн** (иначе обработка обращения незаконна). Оба шага выполняются один раз и переиспользуются дальше.

**Основной путь — deep-link со стартовым параметром.**

1. При онбординге УК для каждого дома генерируется запись в `house_links` с непрозрачным токеном; из неё собирается deep-link `https://max.ru/<ник_бота>?start=<token>` и QR-код. **Подтверждено MAX-001** (`max_api.md` §6): формат именно такой, параметр ограничен 128 символами без спецсимволов/кириллицы — непрозрачный токен (UUID/base62) укладывается без проблем; значение приходит в поле `payload` события `bot_started`. Комплект передаётся УК для стендов в подъездах и квитанций.
2. Житель сканирует QR → MAX открывает диалог с ботом и присылает событие `bot_started` с `payload = token`.
3. Бот разрешает токен в `house_id`, показывает подтверждение — **какой именно дом распознан** — и текст согласия с двумя кнопками и ссылкой на политику.
4. После согласия создаются `user_houses` (`is_primary = true`) и `consents`; бот сразу переходит к приглашению описать проблему.

Показ распознанного адреса обязателен: токен может быть на другом подъезде или устареть после смены УК, и молчаливая привязка к чужому дому отправит заявку не в ту организацию, никак этого не обнаружив.

**Запасной путь — ввод адреса.** Житель может прийти по нику бота, из поиска или по пересланной ссылке без параметра, с отозванным токеном или нажать «Это не мой дом». Тогда бот просит адрес текстом и ищет среди `houses` без внешней ФИАС/DaData: нормализация (город/типы улиц сняты, `ё→е`), **точный** номер дома и нечёткое сходство улицы (`difflib`, порог 0.75). До 5 вариантов кнопками + «Моего дома нет в списке»; выбор ведёт на тот же шаг согласия, что deep-link, с `consents.source = address_search`. На демо-объёме полный скан таблицы достаточен; при росте — `pg_trgm` по нормализованному адресу (лестница §16).

**Если дом не найден** — житель не остаётся ни с чем: бот честно сообщает, что этот дом пока не подключён, отдаёт общий контакт (`FALLBACK_CONTACT_TEXT`) и предлагает «Ввести адрес ещё раз» или «Оставить адрес». По явной кнопке адрес пишется в `house_requests` (`new` / `connected` / `rejected`); обращение не теряется, заявка в УК не создаётся.

**Порядок шагов.** Согласие запрашивается **до** обработки первого содержательного сообщения, а не после. Если житель написал о проблеме раньше, чем дал согласие, текст удерживается в `inbound_events` и обрабатывается только после нажатия кнопки; при отказе событие закрывается без классификации и без передачи чего-либо во внешний сервис.

**Повторный вход.** Житель с действующим согласием актуальной версии и привязанным домом проходит онбординг молча — бот сразу готов принять описание проблемы. Смена `CONSENT_VERSION` возвращает шаг согласия для всех, переход по deep-link другого дома предлагает добавить второй адрес (`user_houses` допускает несколько, `is_primary` определяет дом по умолчанию).

**Отзыв согласия** — командой в боте: проставляется `revoked_at`, обработка новых обращений прекращается, житель получает подтверждение и способ вернуться.

**Платформенный бонус.** Deep-link со стартовым параметром — возможность MAX сверх минимальных требований задания, заявляемая на бонус +0,15 (`idea_and_scope.md`, шаг 7). Поэтому она не опциональна и входит в пошаговый сценарий проверки в README (§13).

## 8. Границы модулей

Монолит внутри разделён на модули с явными интерфейсами — это те же границы, по которым сервисы разносятся на шаге 2 лестницы масштабирования:

| Модуль | Ответственность |
|---|---|
| `bot_gateway` | Приём и верификация вебхука, запись в `inbound_events`, отправка из `outbound_messages` |
| `onboarding` | Разрешение deep-link токена в дом, привязка `user_houses`, согласие на ПДн и его версионирование, запасной путь поиска адреса |
| `flow` | Оркестрация основного сценария в MAX: подтверждение приёма, классификация, уточнение, создание заявки, статус по номеру |
| `classifier` | Эмбеддинг, кэш, retrieval, вызов LLM, порог уверенности, журнал |
| `dedup` | Поиск открытой заявки по тому же дому и типу проблемы, склейка, подписка жителя, выход из склейки |
| `tickets` | Создание заявок, переходы статусов, `ticket_events`, расчёт `due_at` по нормативу, рассылка подписчикам |
| `notifications` | Планирование и рассылка уведомлений, `notification_deliveries` |
| `knowledge` | Загрузка, версионирование и индексация нормативных документов |

Границы реализуются как **интерфейсы уровня Python (порты)**, а не как HTTP-эндпоинты внутри одного процесса: сетевой вызов самого себя добавил бы задержку и точки отказа без какой-либо пользы.

**Решение по собственному API.** По ограничению №6 кейса наличие собственного API само по себе баллов не даёт, а по формату сдачи объявленный API порождает обязательства: полный HTTPS-адрес, `openapi.yaml`, `DATA-API.yaml`, тестовые учётные записи и корректное прохождение обязательных проверок. Поэтому наружу выставляются только: `POST /webhook/max`, `GET /health`, `GET /ready` и служебные эндпоинты сидирования демо-данных. Полноценный публичный API объявляется только если к моменту сдачи он реально готов и проверяем — иначе он превращается в риск потери баллов, а не в преимущество.

## 9. Консистентность данных: Postgres ↔ Qdrant

Postgres — источник правды, Qdrant — производное хранилище. Записи в оба хранилища не транзакционны, поэтому поведение при расхождении определено заранее:

- `knowledge_chunks.index_state` фиксирует состояние индексации (`pending` / `indexed` / `failed`). Чанк, не попавший в Qdrant, виден в БД и переиндексируется.
- `scripts/reindex.py` полностью пересобирает коллекцию `kb_chunks` из Postgres. Потеря или повреждение векторного хранилища не является потерей данных — это восстановимая проекция.
- Коллекция `semantic_cache` не восстанавливается и не должна: её потеря стоит денег и миллисекунд, но не корректности.
- `tickets.embedding_point_id` заполняется после успешной записи вектора; пустое значение означает, что заявка создана, но в дедупликацию не попадёт — заявка при этом полностью рабочая.

Принцип: **ни одна пользовательская операция не блокируется недоступностью Qdrant в части, которая может быть выполнена без него.**

## 10. Матрица отказов и деградация

| Отказ | Поведение системы | Что видит житель |
|---|---|---|
| **OpenRouter (LLM)** недоступен или таймаут | Классификация деградирует на similarity search без LLM, `fallback_used = true`; ответы на вопросы о правах временно отключены | Заявка создаётся; при низкой уверенности — честное «не берусь определить точно» + общий контакт УК |
| **Qdrant** недоступен | Классификация переходит на `problem_type` по умолчанию из справочника и ветку `unknown`; заявка создаётся всегда | Заявка принята, маршрутизация уточняется диспетчером |
| **PostgreSQL** недоступен | Вебхук отвечает `503`, событие не подтверждается — MAX повторит доставку с backoff 60с→×2.5, до 10 раз за 8 часов (подтверждено MAX-001); данные не теряются | Отложенный ответ после восстановления |
| **MAX API** недоступен на исходящем пути | Сообщение остаётся в `outbound_messages`, повторные попытки с задержкой | Ответ приходит с задержкой, а не теряется |
| **Превышен лимит запросов OpenRouter** | Переключение на `OPENROUTER_MODEL_FALLBACK`, при повторной неудаче — та же деградация, что при отказе LLM | Как при отказе LLM |
| **Сообщение не удалось обработать N раз** | `inbound_events.status = failed`, запись в журнал | Явное сообщение о сбое с контактом АДС, а не тишина |
| **Deep-link токен неизвестен, отозван или отсутствует** | Переход на запасной путь — поиск дома по введённому адресу (§7.1) | Просьба указать адрес, а не ошибка |
| **Дом не найден ни одним путём** | Обращение сохраняется без `house_id`, заявка не создаётся | Честное «этот дом пока не подключён» + общий контакт, обращение зафиксировано |
| **Согласие на ПДн не выдано** | Событие закрывается без классификации, во внешний сервис не уходит ничего | Объяснение, почему без согласия нельзя, и возможность вернуться |
| **Дедупликация не сработала (нет вектора)** | Заявка создаётся обычным образом, склейка пропускается | Ничего — сценарий не меняется |

Требование кейса «после ошибки пользователь может продолжить работу без полного перезапуска решения» выполняется тем, что ни один из отказов выше не оставляет систему в состоянии, требующем рестарта: очереди переживают сбой, а деградация обратима автоматически.

Дополнительно вводится ограничение частоты запросов на пользователя — защита от исчерпания лимитов внешнего API при демонстрации.

## 11. Безопасность и работа с персональными данными

- **Секреты** (`MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`, `OPENROUTER_API_KEY`, пароль БД) — только в окружении, в репозитории — `.env.example` в корне, без значений (§12).
- **Верификация вебхука** — обязательна (раздел 7).
- **Маскирование перед отправкой во внешнюю модель.** Свободный текст жителя может содержать номер квартиры, телефон и ФИО. В OpenRouter уходит минимально необходимый фрагмент после `upravdom.masking.mask()` — плейсхолдеры `[ТЕЛЕФОН]` / `[EMAIL]` / `[КВАРТИРА]` / `[ФИО]` / `[НОМЕР]`; тип `MaskedText` обязателен на входе промпта CLASSIFY-001/RIGHTS-001 (mypy). Немаскированный текст остаётся в `tickets.raw_text` внутри системы — он нужен диспетчеру. ФИО — правила и словарь имён (не NER), решение MASK-001.
- **Журналы** хранят только маскированный текст. `inbound_events.last_error` / сообщения исключений воркера — тип ошибки, не текст обращения.
- **В README явно указывается**, какие данные обрабатываются, что передаётся внешнему сервису и какие данные являются смоделированными.
- Зависимость от внешнего LLM-провайдера — осознанное решение для MVP. В целевой архитектуре реального внедрения провайдер заменяется на модель в собственном контуре; это переменная часть, изолированная за интерфейсом модуля `classifier`.
- **Порты `postgres` и `qdrant` публикуются на хост нестандартными портами** (§12.1) — это решение ревизии 4, отличается от исходного «не публикуются наружу». Причина — локальная разработка приложения через venv на хосте (а не только в контейнере) требует достучаться до хранилищ по `localhost`. Риск ограничен: это порты на машине разработчика или проверяющего, а не на публичном сервере — внешний доступ к ним закрыт периметром хоста. В целевом развёртывании пилота (DEPLOY-001 и далее) эти порты наружу не публикуются — правило из первой редакции остаётся верным для продакшна, дев-исключение его не отменяет.

### 11.1 Согласие на обработку персональных данных (152-ФЗ)

Продукт обрабатывает персональные данные, и это не пограничный случай: адрес дома известен из привязки, идентификатор пользователя MAX постоянен, а в свободный текст житель сам добавляет номер квартиры, телефон и ФИО («я из 42-й, Иванова, перезвоните»). Совокупность этих данных позволяет определить конкретного человека.

**Что реализовано:**

| Требование | Реализация |
|---|---|
| Согласие до начала обработки | Шаг онбординга (§7.1), выполняется **до** классификации первого содержательного сообщения |
| Фиксация факта и момента | Таблица `consents`: `user_id`, `consent_version`, `granted_at`, `source` |
| Актуальность текста согласия | `CONSENT_VERSION` в окружении; при изменении текста версия повышается и согласие запрашивается заново, а не наследуется |
| Информирование о передаче третьему лицу | В тексте согласия прямо сказано, что обезличенный фрагмент описания передаётся внешнему LLM-сервису для определения типа проблемы |
| Отзыв согласия | Команда в боте, `revoked_at`; обработка новых обращений прекращается |
| Доказательство согласия постфактум | Отзыв не удаляет запись, а проставляет дату — история сохраняется |
| Минимизация | Во внешний сервис уходит маскированный фрагмент, а не сообщение целиком; в журналы — только маскированный текст |
| Прозрачность для пользователя | `PRIVACY_POLICY_URL` — ссылка на политику показывается на шаге согласия |

**Что осознанно не реализуется в MVP и обозначается как ограничение:** обезличивание или удаление данных по запросу субъекта, сроки хранения и их автоматическое применение, поручение на обработку между нами и УК (без него пилот с реальной УК невозможен — это шаг 8 чек-листа онбординга в `idea_and_scope.md`), размещение данных в соответствии с требованиями о локализации. Для MVP на смоделированных данных это допустимо; для пилота с реальными жителями — обязательные предварительные условия, и они перечислены в README в разделе ограничений, а не умалчиваются.

**Почему это часть архитектуры, а не юридическое приложение:** согласие стоит на критическом пути основного сценария и может его прервать (отказ → событие закрывается без обработки), а его версия влияет на то, пройдёт ли постоянный пользователь онбординг молча или повторно. Это поведение системы, и оно описано там же, где остальное поведение.

## 12. Docker-конфигурация

**Контейнеры:**

| Контейнер | Порт | Назначение |
|---|---|---|
| `app` | 8000 (хост и сеть) | Webhook, health/ready, воркер и планировщик в том же процессе |
| `postgres` | 5432 внутри сети · `${POSTGRES_PORT:-55432}` на хосте | Реляционное хранилище |
| `qdrant` | 6333 внутри сети · `${QDRANT_PORT:-56333}` на хосте | Векторное хранилище |
| `web` *(опционально, Could Have)* | 3000 | React-мини-приложение |

### 12.1 Два адреса хранилищ: контейнер `app` и venv на хосте

`app` внутри `docker compose up` и локальный процесс, запущенный через venv на
хосте для разработки, обращаются к тем же Postgres и Qdrant **по разным
адресам** — это осознанная развилка, а не рассинхрон:

| Кто обращается | `DATABASE_URL` / `QDRANT_URL` | Почему |
|---|---|---|
| Контейнер `app` (полный `docker compose up`, в т.ч. у проверяющего) | `postgres:5432` / `qdrant:6333` — имена сервисов и внутренние порты compose-сети | Контейнеры видят друг друга по имени сервиса; `localhost` внутри контейнера — это сам контейнер, а не сосед по сети |
| Локальный процесс через venv (разработка) | `localhost:${POSTGRES_PORT}` / `localhost:${QDRANT_PORT}` | Процесс на хосте не состоит в compose-сети и стучится в контейнеры только через порты, пробитые наружу |

Технически это решается так: значения в `.env` (`DATABASE_URL`, `QDRANT_URL`)
рассчитаны на **хостовый** сценарий (localhost + нестандартный порт) — их
читает locally-run venv-процесс через `pydantic-settings`. Сервис `app` в
`compose.yaml` **переопределяет** эти же переменные явным `environment:` на
внутренние `postgres:5432` / `qdrant:6333` — Compose отдаёт приоритет
`environment:` перед `env_file:` для одного и того же ключа, поэтому
`docker compose up` работает корректно без правки `.env` под каждый сценарий
запуска. `POSTGRES_PORT` и `QDRANT_PORT` в `.env` используются только для
пробития портов наружу в секции `ports:` контейнеров `postgres`/`qdrant` —
на поведение `app` внутри compose-сети они не влияют.

Нестандартные порты (`55432`, `56333`, а не `5432`/`6333`) выбраны, чтобы
`docker compose up` не конфликтовал с Postgres/Qdrant, уже установленными
локально на машине разработчика.

**Тома (обязательны).** `postgres_data` и `qdrant_data` — именованные volumes. Кейс требует описать порядок остановки и повторного запуска решения; без томов после `docker compose down` проверяющий получил бы пустую базу знаний и потерянные заявки, то есть невоспроизводимый сценарий.

**Бюджет сборки ≤5 минут — три решения, принятые явно:**

1. **Веса модели запекаются в образ** отдельным слоем (`huggingface_hub.snapshot_download` до копирования исходников), чтобы слой кэшировался и не пересобирался при каждой правке кода. Модель — 128M параметров, это приемлемый объём; CUDA-зависимости исключены (раздел 2).
2. **Векторы базы знаний предпосчитаны** и лежат в `data/kb/` в репозитории. При старте выполняется только загрузка готовых векторов в Qdrant, а не чанкинг и инференс по всему корпусу нормативов. Пересчёт запускается вручную `scripts/build_kb.py` при обновлении документов — в критический путь сборки и старта он не входит.
3. **Зависимости ставятся через `uv` с кэшируемым слоем `uv.lock`**; базовый образ — `python:3.12-slim`.

**Запуск одной командой.** `docker compose up` поднимает всё и приводит систему в рабочее состояние: миграции Alembic, загрузка справочников (`problem_types`, тестовые УК и РСО), загрузка предпосчитанных векторов в Qdrant, старт приложения. Отдельный ручной шаг подготовки не требуется — это прямое требование формата сдачи.

**Если бюджет сборки всё же не выдерживается** (проверяется замером до сдачи), применяется запасной вариант: веса модели не запекаются в образ, а монтируются томом и загружаются при первом старте — сборка остаётся тонкой, стоимость переносится на первый запуск.

Вынесение эмбеддингов во внешний API как способ уложиться в бюджет **не применяется**: OpenRouter — это API чат-моделей, эмбеддинги он не отдаёт, а подключение стороннего провайдера эмбеддингов добавило бы сетевую зависимость в тот самый путь, который задуман как автономный резерв при отказе LLM. Локальная CPU-модель остаётся основным и единственным вариантом.

**`.env.example` — в корне репозитория.** Это обязательный артефакт сдачи, и проверяющий ищет его там, куда смотрит первым, — рядом с `compose.yaml`. Каталог `credentials/` оставлен для локальных копий секретов и целиком игнорируется git, кроме собственного README со ссылкой на корневой шаблон.

Фактический состав (совпадение файла и этого раздела проверяется перед сдачей — рассинхрон между документацией и конфигурацией бьёт по критерию «переданные материалы соответствуют зафиксированной версии решения»):

## 13. Тестовые данные и сценарий проверки

### 13.1 Тестовый набор описаний проблем

`data/test_cases/accident_descriptions.json` — 40–60 записей вида:

```json
{
  "id": "acc-017",
  "text": "второй день из стены за ванной сифонит, уже плинтус повело",
  "expected_problem_type": "cold_water",
  "expected_zone": "uk",
  "norm_reference": "ПП РФ №491, п. 5",
  "source_kind": "public_portal",
  "difficulty": "hard",
  "annotator": "<участник, не писавший промпт>",
  "is_test_data": true
}
```

Требования к набору (обоснование — `idea_and_scope.md`, шаг 5):

- **Формулировки из реальных источников**, обезличенные, сохранённые как есть — с просторечием, опечатками и неполнотой. `source_kind` фиксирует происхождение. Сочинённые фразы допускаются только как отдельная помеченная подгруппа и в основную цифру не входят.
- **Разметку делает участник, не писавший промпт и не подбиравший чанки** (`annotator`), со ссылкой на норму в `norm_reference`. Это защита от измерения совпадения промпта с фантазией его автора.
- **`difficulty`** отделяет заведомо спорные случаи (граница «первый запорный вентиль», описание без названия ресурса, смешанная проблема) — по ним точность считается отдельно, и низкая цифра там объяснима, а не является провалом.
- Весь набор помечен `is_test_data` и обозначен в README как подготовленный (ограничение №10 кейса).

`data/test_cases/dedup_cases.json` — группы разных описаний одной аварии в одном доме плюс контрольные пары «похоже, но разные проблемы», для измерения доли ложных склеек.

### 13.2 Прогоны и baseline

Абсолютная цифра точности недоказательна: неизвестно, много это или мало. Поэтому `scripts/run_accuracy_check.py` прогоняет один и тот же набор в четырёх режимах и печатает их рядом.

| Режим | Ключ | Что моделирует |
|---|---|---|
| Меню категорий | `--baseline=menu` | Форма с рубрикатором, как в существующих сервисах: считается доля описаний, однозначно ложащихся в категорию без домысливания |
| Ключевые слова | `--baseline=keywords` | Классификатор по словарю — то, что даёт конструктор ботов без ИИ |
| Продукт | *(по умолчанию)* | RAG + LLM, основной путь |
| Деградация | `--no-llm` | Только similarity search (§10) — цена отказа внешнего сервиса |

Точность считается **раздельно по двум осям** (`problem_type` и `responsibility_zone`) и отдельно по подгруппе `difficulty = hard`. Вывод — таблица «режим × ось × точность», которая идёт в презентацию как есть. Убедителен разрыв между режимами, а не абсолютное число.

`scripts/run_dedup_check.py` — доля корректно схлопнутых групп и доля ложных склеек на `dedup_cases.json`. Вторая цифра важнее и показывается всегда, даже если она хуже первой (§6.5).

Калибровка порогов `CLASSIFY_CONFIDENCE_HIGH` / `LOW` и порога склейки выполняется на этом наборе **до** защиты, и факт калибровки фиксируется: пороги, подобранные на том же наборе, на котором меряется точность, завышают результат — это ограничение проговаривается честно, а не скрывается.
- `scripts/seed_demo.py` — детерминированное демо-состояние: тестовые УК и РСО, дома, смоделированные уведомления об отключениях.
- **Проверка повторяемости:** основной сценарий проходится дважды подряд на одном и том же состоянии — требование «решение стабильно работает при повторном прохождении основного сценария».
- **Проверка остановки и перезапуска:** `docker compose down` → `up` → заявка, созданная до остановки, доступна по статусу.
- Контакты АДС/РСО — тестовые, помечены `is_test_data`, обозначены в README.
- **Пошаговый сценарий для README:** перейти по deep-link (QR тестового дома) → увидеть распознанный адрес и дать согласие на обработку ПДн → написать боту свободным текстом → получить мгновенное подтверждение приёма → получить определённую зону ответственности со ссылкой на норматив и номер заявки → запросить статус по номеру → отправить второе похожее сообщение от другого пользователя того же дома и увидеть присоединение к существующей заявке → получить тестовое уведомление об отключении.
- **Проверка запасного пути:** открыть бота без параметра `start` → ввести адрес текстом → выбрать дом из предложенных → дальше сценарий совпадает с основным.
- **Проверка выхода из склейки:** нажать «Это другая проблема» на сообщении о присоединении → убедиться, что создана отдельная заявка со своим номером.

## 14. Оценка нагрузки и узкое место

Расчёт нужен, чтобы лестница масштабирования (раздел 16) опиралась на цифры, а не на ощущения.

| Этап | Масштаб | Оценка потока обращений |
|---|---|---|
| Пилот | 1–2 дома, ~200 квартир | единицы обращений в сутки |
| Одна УК | ~100 домов, ~10 тыс. квартир | десятки–сотни обращений в сутки |
| Регион | десятки тысяч домов | тысячи обращений в сутки, пики при крупных авариях |

**Что не является узким местом.** Вся база знаний — величина порядка 10⁴–10⁵ чанков; при dim 768 и float32 это ≈ 300 МБ векторов даже в верхней оценке. Qdrant такой объём держит в памяти одного узла без обсуждения. Приложение stateless (состояние в Postgres), поэтому масштабируется репликами тривиально. Эмбеддинг на CPU — десятки миллисекунд.

**Что является узким местом — LLM.** Это единственный компонент с внешним лимитом, платной стоимостью за обращение и задержкой в секундах. Отсюда следуют три вывода, которые определяют приоритеты развития:

1. Семантический кэш — не микрооптимизация, а несущий элемент экономики решения: при массовых однотипных обращениях (крупная авария в районе — сотни сообщений об одном и том же) он снимает основную часть вызовов.
2. Пики нагрузки поглощаются очередью `inbound_events`, а не увеличением числа реплик: при аварийном всплеске система обрабатывает поток с задержкой, но не теряет обращения и не упирается в лимит провайдера.
3. Настоящий переход на следующий масштаб — это не «добавить балансировщик», а перенос инференса в собственный контур (своя модель, батчинг запросов) и отказ от поштучной оплаты внешнего API.

## 15. Известные ограничения и риски

Из `idea_and_scope.md` (Won't Have), переносится как техническое ограничение:
- Нет событийно-распределённой инфраструктуры (микросервисы + L7 + service mesh) — сознательно, см. раздел 16.
- Нет реальной интеграции с системами конкретной УК / ГИС ЖКХ — данные тестовые и смоделированные, помечены явно.
- Демо ограничено 1–2 городами/домами.
- Нет отдельного сценария для диспетчера УК — только как получатель в архитектуре. Дедупликация (§6.5) даёт ему ценность без собственного интерфейса, но рабочего места диспетчера в MVP нет.
- Нет админки онбординга УК — подключение выполняется скриптами и вручную; автоматизация вынесена на второй виток тиража (§16).
- Обработка ПДн закрыта частично: согласие с версионированием есть, сроков хранения, удаления по запросу субъекта и поручения на обработку с УК — нет (§11.1). Для MVP на смоделированных данных допустимо, для пилота с реальными жителями — обязательное предусловие.

**Технические риски:**

| Риск | Смягчение |
|---|---|
| Зависимость классификации от внешнего LLM | Деградация на similarity search, семантический кэш, резервная модель; проседание точности измерено заранее (раздел 13) |
| Бесплатная модель на OpenRouter может стать недоступной | Модель не хардкодится, задана резервная; замер перед сдачей |
| RAG не находит нужный чанк на редкой формулировке | Тестовый набор, настройка top-k и порогов, ветка «не уверен» вместо уверенной ошибки |
| Бюджет сборки ≤5 минут | Замер до сдачи, запасной вариант с монтированием весов (раздел 12) |
| Передача пользовательского текста внешнему сервису | Маскирование, минимизация payload, раскрытие в README (раздел 11) |
| Лицензии зависимостей | BERTA — MIT (проверено); остальные зависимости проверяются перед сдачей |
| Ложная склейка при дедупликации (проблему жителя потеряли) | Консервативный порог 0.88, рамки одного дома и окна 6 часов, явное сообщение о присоединении и кнопка «Это другая проблема» (§6.5) |
| Deep-link привязал к чужому дому (устаревший QR после смены УК) | Показ распознанного адреса до подтверждения, отзыв ссылки через `house_links.revoked_at` (§7.1) |
| Обработка ПДн без полного комплекта юридических условий | Согласие с версионированием реализовано (§11.1); отсутствующее в MVP (сроки хранения, поручение на обработку с УК, удаление по запросу) вынесено в ограничения README как предусловие пилота |
| Пороги калибруются на том же наборе, на котором меряется точность | Факт проговаривается явно; подгруппа `difficulty = hard` считается отдельно (§13.2) |

## 16. План эволюции (лестница масштабирования)

Согласовано с разделом «Масштабирование» в `idea_and_scope.md` и с оценкой нагрузки из раздела 14:

1. **MVP / пилот (1–2 УК):** `app` + `postgres` + `qdrant`, по одному экземпляру, без балансировщиков. Триггер перехода — не число пользователей, а появление второй УК со своими документами и справочниками.
2. **Тираж на регион (десятки УК):** модули из раздела 8 становятся отдельными сервисами по тем же границам — по-прежнему по одному экземпляру каждого; арендное измерение (`management_company_id`) уже заложено в модели данных, поэтому разделение не требует переписывания выборок.

   **Настоящий триггер этого шага — не нагрузка, а ручной труд онбординга.** Подключение УК (чек-лист из 8 шагов в `idea_and_scope.md`) выполняется руками начиная со второй УК и перестаёт масштабироваться примерно на пятой. Поэтому приоритет второго витка — не разнесение сервисов, а **админка онбординга**, закрывающая шаги, которые иначе делаются вручную:

   | Возможность админки | Какой шаг чек-листа закрывает |
   |---|---|
   | Импорт реестра домов УК и сверка с ФИАС | 1 |
   | Ведение таблицы «дом → ресурс → организация → контакт» (`house_resource_orgs`) | 2 |
   | Автопроверка контактов АДС/РСО на доступность по расписанию | 3 |
   | Массовая генерация `house_links` и комплектов QR на дом | 4 |
   | Загрузка региональных документов как новой версии базы знаний | 5 |
   | Настройка канала выгрузки заявок на сторону УК | 6 |

   Без этого списка «тираж на десятки УК» — обещание, а не план: сервисы можно разнести за неделю, а подключение тридцатой УК без автоматизации шагов 1–4 остаётся неделей ручной работы на каждую.
3. **Массовый тираж (сотни УК/регионов):** реплики stateless-сервисов за L7-балансировкой, перенос LLM-инференса в собственный контур с батчингом, ClickHouse для аналитики по регионам и УК. Именно здесь, а не раньше, инфраструктурное усложнение оправдано нагрузкой.

## История решений

**[22.09.2026] STATUS-001 — уведомления подписчиков и адресация по `user_id`.**
Смена статуса, событие `status_changed` и постановка уведомления каждому
подписчику — одна транзакция: статус без уведомления (или наоборот) житель
увидит как рассинхрон. Получатели отбираются запросом с условием
действующего согласия актуальной версии (§11.1), а не фильтром в вызывающем
коде. Переадресация (`reroute`) — отдельная ось от статуса: меняется адресат
и пишется событие `routed`, статус остаётся прежним; закрытая и склеенная
заявка не переадресуется. Адресация исходящего по `user_id` вместо `chat_id`
описана в §7; выбран вариант «`user_id` в payload очереди», а не «сохранять
`chat_id` при каждом входящем событии» — он не требует миграции и не зависит
от того, писал ли житель боту после последнего рестарта. В ленте истории
служебное `routed` из `create_ticket` (РСО по ресурсу не нашлась, ушли на УК)
жителю не показывается: для него никакой передачи не было — событие
отличается по ключу `to`, который пишет только `reroute`. Число
присоединившихся считается по текущим подписчикам, а не по событиям
`subscriber_joined`: после выхода из склейки (DEDUP-001) оно должно
уменьшаться, а события append-only.
